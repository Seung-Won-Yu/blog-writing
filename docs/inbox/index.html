“에이전트가 DB를 삭제하는 시대” 에이전틱 시스템 확산이 바꾼 LLM 보안 위협 지형도

기술의 빠른 발전과 다양한 비즈니스 활용 사례의 등장으로 기업의 생성형 AI 기술 도입이 폭발적으로 늘어나고 있다. 다만 대규모 언어 모델(LLM)은 유해한 결과물을 실수로 생성하거나, 정보를 유출하거나, 위협 행위자에게 노출될 수 있다. 기술이 발전하고 공격자가 시스템을 침해하는 새로운 방법을 찾아냄에 따라 이런 취약점도 변화하고 있다. 기업 입장에서는 부정적인 언론 보도, 컴플라이언스 또는 사이버보안 노출, 법적 책임, 집단 소송 등의 위험이 존재한다. LLM 위험의 최신 동향을 따라잡기 위해, 오픈 월드와이드 애플리케이션 시큐리티 프로젝트(OWASP)가 LLM 애플리케이션의 10대 핵심 취약점 목록을 업데이트했다. 처음으로 전문가 투표와 함께 실제 사고 데이터가 목록 반영에 활용됐다. 프롬프트 인젝션과 민감정보 노출은 가장 심각한 2대 위협으로서의 지위를 유지했으며, 과도한 에이전시(허용 범위를 벗어난 에이전틱 작업)는 OWASP 목록에서 3위로 올라섰다. 챗봇에서 API를 호출하고 코드를 실행하는 에이전틱 시스템으로 진화한 양상을 반영한 변화다. AI 리소스의 무제한 소비 같은 문제는 중요도가 높아진 반면, 부적절한 출력 처리에 따른 위험은 출력 새니타이제이션의 광범위한 활용 덕분에 목록 하위권으로 내려갔다. 이런 변화는 생성형 AI 분야가 얼마나 빠르게 진화하고 있는지를 보여주며, 새로운 기술이 시장에 등장함에 따라 목록은 조만간 또 달라질 가능성이 크다. OWASP에 따르면, 이 목록은 시스템을 공격하고 방어하는 보안 실무자들의 판단과 현장에서 실제로 발생한 사고 기록을 종합해 상호 교차 검증한 결과물이다. 목록의 목적은 개발자와 기업에 잠재적인 보안 위험을 알리는 동시에, LLM 애플리케이션의 보안 태세를 개선하기 위한 완화 전략을 제시하는 데 있다. 기업은 상위 항목부터 시작해 10개 범주 전체에 걸쳐 개선 작업을 진행해야 한다. 1. 프롬프트 인젝션 프롬프트 인젝션은 2023년 초 처음 공개된 이후 줄곧 OWASP 목록의 수위를 차지하고 있다. 이 공격 기법은 LLM이 공격자의 의도를 인지하지 못한 채 실행하도록 유도하는 악의적인 입력을 사용한다. 직접적인 ‘탈옥’이나 파일·웹사이트 같은 외부 입력의 조작을 통해 데이터 유출, 사회공학, 기타 문제로 이어질 수 있다. 예를 들어, 사용자는 프롬프트를 작성해 기업 챗봇을 속여 접근 권한이 없는 독점 정보를 노출하도록 하거나, 애플리케이션의 오작동을 유발하는 숨겨진 명령이 담긴 텍스트·이미지·오디오 파일을 업로드할 수 있다. 또 프롬프트 인젝션에는 도구 출력, 중간 추론, 영구 메모리를 악의적 목적으로 조작하는 크로스 모달 공격도 포함된다. OWASP는 프롬프트 인젝션 위험을 줄이기 위해 다음을 권고한다. 시스템 프롬프트에서 모델의 역할과 기능을 제한한다. 가장 민감한 작업에는 루프 내 인간 검토를 추가해 무단 작업 여부를 확인하는 추가 승인 단계를 마련한다. 엄격한 출력 스키마를 정의하고, 신뢰할 수 있는 애플리케이션 코드로 모든 응답을 검증한다. 입력과 출력(텍스트, 이미지, 오디오, 구조화 데이터)을 유해 콘텐츠 기준으로 스캔하고, 민감하거나 무단의 콘텐츠가 모델에 도달하거나 사용자에게 반환되기 전에 차단한다. 자격증명과 상태 변경 기능은 모델이 아닌 애플리케이션 코드에서 관리하며, 각 작업에 최소 권한 원칙을 적용한다. 2. 민감정보 노출 ‘데이터 유출’이라고도 불리는 민감정보 노출은, LLM이 출력 시 보호 데이터, 독점 알고리즘, 기타 기밀 정보를 드러내는 취약점으로, 무단 접근, 개인정보 침해, 기타 보안 침해로 이어질 수 있다. 민감 데이터는 최초 학습, 파인튜닝 또는 임베딩 과정, 사용자 프롬프트 입력 등 다양한 경로로 LLM에 유입될 수 있다. 모델이 정보에 접근하면 다른 무단 사용자에게 노출될 가능성이 생긴다. 예방 조치는 다음과 같다. 데이터 새니타이제이션 및 스크러빙을 활용해 학습이나 추론 과정에서 LLM이 민감 데이터에 접근하지 못하도록 한다. 사용자 입력에 필터를 적용해 민감 데이터 업로드를 방지하거나, 기밀 정보를 식별해 제거하거나 마스킹한다. 추론 과정에서 LLM이 데이터 소스에 접근해야 할 때는 엄격한 접근 통제와 최소 권한 원칙을 적용한다. 3. 과도한 에이전시 에이전틱 시스템이 기업에서 더욱 보편화됨에 따라, 이 취약점은 6위에서 상승했다. 과도한 에이전시는 LLM이 지나치게 많은 작업 실행 권한을 보유하는 취약점으로, 통상 과도한 기능, 과도한 권한, 불충분한 감독에서 비롯된다. OWASP에 따르면, LLM이 환각 현상을 일으키거나, 프롬프트 인젝션·악성 플러그인·잘못 작성된 프롬프트의 피해자가 되거나, 단순히 성능이 낮은 모델인 경우 피해를 야기하는 작업이 실행될 수 있다. 전문가 투표와 사고 데이터를 근거로 한 과도한 에이전시의 순위 급등은 에이전틱 위험에 대한 업계의 우려가 타당함을 입증한다고, AI 클라우드 보안 전문 업체 시스디그(Sysdig)의 수석 사이버보안 전략가 크리스털 모린은 밝혔다. 모린은 “LLM은 텍스트를 생성하는 단계에서 실제 권한과 도구 접근권을 갖고 영향 반경이 큰 작업을 실행하는 단계로 진화했다”라고 말했다. 또 “OWASP의 업데이트된 Top 10 목록은 실제 사례를 기반으로 구축된 것으로, 기업이 오늘날 더 나은 애플리케이션 보안을 우선시하는 데 활용할 수 있다”고 덧붙였다. 보안 테스트 전문 업체 펜테스트툴스닷컴(Pentest-Tools.com)의 보안 매니저 다니엘 베체네아는 현재 프로덕션 자격증명으로 에이전트를 운영하는 기업이 충분히 많아 사고 기록에 실제로 나타나고 있다고 전했다. 베체네아는 두 가지 사례를 근거로 들었다. “첫 번째는 2026년 4월, 코딩 에이전트 커서(Cursor)가 포켓OS(PocketOS)에서 스테이징 작업을 수행하던 중 자격증명 불일치가 발생해 작업 범위를 벗어난 곳에서 관련 없는 파일에 저장된 루트 수준의 API 토큰을 찾아내고, 그 토큰으로 클라우드 인프라 플랫폼 레일웨이(Railway)의 MCP 볼륨을 삭제한 사건이다”라고 설명했다. “레일웨이가 볼륨 수준의 백업을 동일한 볼륨 내부에 저장하고 있었기 때문에 백업도 데이터와 함께 사라졌으며, 가장 최근의 복구 가능한 사본은 3개월 이전의 것이었다”고 부연했다. 또 다른 고프로파일 사례에서는, 온라인 코딩 플랫폼 레플릿(Replit)의 에이전트가 코드 프리즈 선언 기간 중 SaaS 커뮤니티 기업 사스트르(SaaStr)의 프로덕션 데이터베이스를 삭제한 뒤, 복구가 불가능하다고 허위로 주장했다. 베체네아는 “두 사례 모두 공격자와는 무관하다”고 말했다. 또 “자격증명의 범위가 그 작업보다 넓게 설정돼 있었고, 파괴적이고 되돌릴 수 없는 작업에 대한 강제 게이트가 없었다. 두 경우 모두 서면으로 작성된 가드레일이 존재했지만 작동하지 않았다. 두 사례는 프롬프트에 담긴 규칙이 통제 수단이 아님을 강력하게 상기시켜 준다”고 강조했다. 베체네아는 기업이 위험에 선제 대응하기 위해서는 연결된 도구를 통해 에이전트가 접근할 수 있는 범위와, 접근 시 개입하는 메커니즘이 있는지를 테스트해야 한다고 조언했다. 예방 조치는 다음과 같다. LLM이 호출할 수 있는 플러그인과 도구, 그 안에 구현된 기능을 최소한으로 제한한다. 셸 명령 실행이나 URL 가져오기 같은 개방형 함수는 피하고, 더 세분화된 기능을 활용한다. LLM, 플러그인, 도구에 시스템에 대해 부여되는 권한을 최소로 제한한다. 사용자 인가와 보안 범위를 추적해, 사용자를 대신해 수행하는 작업이 그 사용자의 컨텍스트 안에서 필요한 최소 권한으로 다운스트림 시스템에서 실행되도록 보장한다. 4. 공급망 취약점 이전 3위였던 공급망 취약점은 서드파티 컴포넌트, 변조되거나 오래된 사전 학습 모델, 또는 손상된 학습 데이터 세트와 관련된다. 이 범주에는 이제 모델 컨텍스트 프로토콜(MCP) 서버와 모델 아티팩트가 강조 항목으로 추가됐다. 오픈 액세스 LLM과 새로운 파인튜닝 기법의 확산은 추가적인 공급망 위험을 초래했으며, 특히 공개 리포지터리나 협업 플랫폼에서 모델을 가져올 때 더욱 두드러진다. 원본 모델을 만든 개발자가 학습 데이터를 제대로 검증하지 않아 개인정보, 소프트웨어 라이선싱, 저작권 침해로 이어지는 경우도 이 범주에 속한다. OWASP에 따르면 편향된 결과, 보안 침해, 시스템 장애로 이어질 수 있다. 예방 조치는 다음과 같다. 데이터 소스와 공급업체를 철저히 검증한다. 신뢰할 수 있는 플러그인만 사용하고 요건 충족 여부를 테스트하며, 외부 모델과 공급업체를 활용할 때는 모델 및 코드 서명을 적용한다. 무단 플러그인과 구식 컴포넌트(모델과 아티팩트 포함)에 대해 환경을 스캔하고, 문제 해결을 위한 패치 정책을 수립한다. 서드파티 모델 선택 시 잠재적인 취약점, 편향, 악성 기능을 배포 전에 파악하기 위해 포괄적인 AI 레드 팀 및 평가 프로세스를 활용한다. 5. 데이터 및 모델 포이즈닝 OWASP에 따르면, 데이터 및 모델 포이즈닝은 사전 학습 데이터나 파인튜닝·임베딩 과정에서 사용되는 데이터를 조작해 취약점, 백도어, 편향을 심는 것으로, 모델의 안전성을 해칠 수 있다. 예를 들어, 학습 데이터 세트에 접근한 악의적인 공격자나 내부자는 데이터를 변조해 모델이 잘못된 지침이나 권고를 제공하도록 만들어 기업에 피해를 입히거나 공격자에게 이익을 줄 수 있다. 예방 조치는 다음과 같다. 학습 데이터의 공급망을 검증하며, 외부에서 가져온 경우에는 특히 주의한다. 다양한 활용 사례에 맞게 별도의 학습 데이터 또는 파인튜닝을 통해 서로 다른 모델을 구성해 더욱 세분화되고 정확한 생성형 AI 출력을 만든다. 모델이 의도하지 않은 데이터 소스를 크롤링하지 못하도록 충분한 샌드박싱을 보장한다. 특정 학습 데이터 또는 데이터 소스 범주에 대해 엄격한 검증 또는 입력 필터를 적용해 위조 데이터의 양을 통제한다. 6. 무제한 소비 이전에 ‘모델 서비스 거부’라고 불렸던 무제한 소비는, 공격자가 LLM으로 하여금 과도하게 많은 리소스를 사용하게 만들어 다른 사용자의 서비스 품질 저하와 잠재적으로 높은 리소스 비용을 유발하는 취약점이다. OWASP에 따르면, LLM의 집약적인 리소스 사용, 사용자 입력의 예측 불가능성, 개발자들 사이의 전반적인 낮은 인식으로 인해 이 문제의 심각성이 커지고 있다. 예를 들어 공격자는 자동화를 이용해 기업 챗봇에 복잡한 쿼리를 폭발적으로 발송할 수 있는데, 각 쿼리는 응답하는 데 시간이 걸리고 비용(일명 ‘지갑 거부(denial of wallet)’)도 소모된다. 무제한 소비에는 모델 탈취도 포함된다. 공격자가 충분한 양의 질문을 던져 원본 모델을 사실상 역공학하거나, 원본 모델을 활용해 새 모델 구축에 쓸 합성 데이터를 생성하는 방식이다. 예방 조치는 다음과 같다. 입력 유효성 검사와 새니타이제이션을 구현해 사용자 입력이 정해진 한도를 준수하고 악성 콘텐츠를 걸러내도록 한다. 요청 또는 단계별로 리소스 사용량을 제한해 복잡한 부분이 포함된 요청이 천천히 처리되도록 하고, 개별 사용자 또는 IP 주소별로 API 속도 제한을 적용하거나, LLM 응답에 반응하는 시스템에서 대기 중인 작업 수 또는 전체 작업 수를 제한한다. 리소스 사용량을 지속적으로 모니터링해 비정상적인 급등이나 패턴을 파악한다. 시스템이 과부하 상태에서도 완전 장애 대신 부분 기능을 유지하며 점진적으로 성능을 저하시키도록 설계한다. 7. 잘못된 정보 LLM은 때때로 사실과 다르거나, 부적절하거나, 안전하지 않은 콘텐츠를 생성하는 경향이 있다. 시장 조사 업체 옴디아(Omdia)의 수석 사이버보안 애널리스트 릭 터너는 이런 ‘환각’ 현상이 위험할 수 있다고 지적했다. 기업의 보안 애널리스트가 LLM을 활용하는 경우가 대표적이다. 터너는 “터무니없는 답이 돌아와서 애널리스트가 쉽게 알아채면 잘못을 지적하고 알고리즘을 추가로 학습시키는 데 도움을 줄 수 있다”라며 “하지만 환각이 매우 그럴듯해 실제처럼 보인다면 어떻게 되겠느냐”고 물었다. 환각은 기업이 고객 서비스 챗봇처럼 LLM을 직접 일반 사용자에게 배포할 때 더욱 큰 위험으로 작용한다. 제공된 정보가 위험하거나, 불법이거나, 부정확한 경우 기업은 금전적 손해, 명성 훼손, 법적 위험을 감수해야 한다. 잘못된 정보의 영향은 과잉 의존으로 인해 증폭된다. 사용자가 충분한 검증 없이 LLM 생성 콘텐츠를 과도하게 신뢰하는 현상이다. 핵심 예방 조치는 다음과 같다. 출력물이 권위 있는 출처를 기반으로 하도록 요구하고, 행동에 옮기기 전에 주장을 검증한다. 승인 워크플로와 시스템 검사를 도입한다. 주장, 근거, 결과를 기록하고 적대적 시나리오를 테스트한다. 오해를 유발하는 시나리오에 대해 워크플로를 정기적으로 점검한다. 최소 권한, 샌드박싱, 속도 제한을 적용해 사고의 잠재적 영향을 제한한다. 8. 숨겨진 컨텍스트 노출 숨겨진 프롬프트 노출은 이전의 ‘시스템 프롬프트 유출’ 범주를 확장해 숨겨진 컨텍스트 범위 문제를 포함한다. 시스템 프롬프트는 LLM에 대화를 안내하기 위해 제공되는 초기 지침으로, 민감한 지침, 운영 매개변수, 보안 제어, 비즈니스 로직, 비공개 기업 정보를 담을 수 있다. 기업은 시스템 프롬프트가 기밀로 유지된다고 잘못 가정할 수 있지만, 실제로 노출될 가능성이 있다. OWASP에 따르면, 문제는 공격자가 시스템 프롬프트를 손에 넣을 수 있다는 것 자체가 아니라, 기업이 API 키와 인증 정보를 포함한 민감한 정보를 처음부터 프롬프트에 담고 있다는 점이다. 개발자는 숨겨진 컨텍스트가 잠재적으로 발견될 수 있다는 전제 아래 작업해야 한다. 핵심 예방 조치는 다음과 같다. API 키, 인증 정보, 데이터베이스 정보 같은 민감한 정보는 시스템 프롬프트와 분리해, 모델이 직접 접근할 수 없는 시스템에 저장한다. 모델 동작 제어를 시스템 프롬프트에 의존하지 말고, 유해 콘텐츠 감지 같은 제어 기능을 외부 시스템에서 구현한다. LLM 외부에 가드레일을 배포해 모델 출력을 검사하고 모델이 예상대로 작동하는지 확인한다. 권한 분리, 인가 확인 같은 중요한 보안 제어는 LLM과 독립적으로, 결정론적이고 감사 가능한 방식으로 구현한다. 워크플로가 서로 다른 접근 수준이 필요한 여러 작업을 포함하는 경우, 각각 필요한 최소 권한으로 구성된 복수의 에이전트를 활용한다. 9. 벡터 및 임베딩 취약점 기업은 LLM에 벡터 데이터베이스와 검색 증강 생성(RAG) 시스템을 결합해 활용하는 경우가 많다. 프롬프트를 LLM에 전달하기 전에 기업 데이터 저장소에서 관련성 높고 최신 정보를 불러오는 방식이다. 이런 환경에서 공격자는 접근 권한이 없는 정보를 시스템이 검색하도록 속이거나, 데이터 소스를 직접 공격해 모델을 오염시키고 잘못된 정보를 제공하도록 만들 수 있다. OWASP에 따르면, 벡터 및 임베딩 취약점은 LLM이나 프롬프트 자체가 아닌 RAG 스타일 시스템의 검색 기반에서 발생하는 오류다. 임베딩과 벡터 저장소는 기존 데이터 저장소와 동일한 접근 제어 및 감사 가능성이 갖춰지지 않은 경우가 많아 별도의 공격 표면을 제공한다고 OWASP는 지적한다. 예를 들어, 멀티테넌트 또는 필터링이 제대로 되지 않은 벡터 저장소는 테넌트 경계를 넘어서거나 사용자 인가 범위를 초과하는 문서를 반환해 공격자에게 데이터를 유출할 수 있다. 핵심 예방 조치는 다음과 같다. 세밀한 접근 제어와 권한 인식 벡터·임베딩 저장소를 구현하고, 데이터 세트를 엄격하게 분리해 사용자가 LLM을 통해 접근 권한이 없는 정보를 얻지 못하도록 한다. 신뢰할 수 있고 검증된 출처의 정보만 수용하고 처리하는 강력한 데이터 검증 파이프라인을 구축한다. 이력서 같은 사용자 제출 콘텐츠에는 숨겨진 텍스트를 감지하고 표시하는 텍스트 추출 도구를 사용한다. 결합된 데이터 세트를 철저히 검토하고 분류해 데이터 불일치 오류를 방지하고 접근 수준을 통제한다. 10. 부적절한 출력 처리 부적절한 출력 처리는 LLM이 생성한 출력물이 다운스트림 컴포넌트와 시스템으로 전달되기 전에 충분한 유효성 검사, 새니타이제이션, 처리를 거치지 않는 취약점을 말한다. LLM 생성 콘텐츠는 프롬프트 입력으로 제어할 수 있기 때문에, 이 동작은 사용자에게 추가 기능에 대한 간접 접근을 부여하는 것과 유사하다. AI 어시스턴트가 대규모로 생성하는 불안전한 코드를 포함하도록 확장됐다. 예를 들어, LLM의 출력이 시스템 셸이나 유사한 함수로 직접 전달되면 원격 코드 실행이 발생할 수 있다. 예방 조치는 다음과 같다. 모델을 다른 사용자와 동일하게 취급하며 제로 트러스트 방식을 채택하고, 모델에서 백엔드 함수로 전달되는 응답에 적절한 입력 유효성 검사를 적용한다. OWASP ASVS(애플리케이션 보안 검증 표준) 가이드라인을 따라 효과적인 입력 유효성 검사와 새니타이제이션을 보장하고, 원치 않는 코드 실행을 방지하기 위해 출력을 인코딩한다. dl-itworldkorea@foundryco.com

애플워치 시리즈 12와 울트라 4에서 애플은 실용적이고 흥미로운 새 음성 기반 AI 기능을 선보인다. 새로운 S11 프로세서는 배터리 수명을 단축하지 않고 음성을 지속적으로 청취하고 (가볍게) 처리할 수 있는 하드웨어를 탑재했다. 애플은 S11 프로세서의 상시 처리 능력을 활용해 네 가지 새로운 AI 기반 기능을 선보이며, 브랜딩을 빠뜨리는 법이 없는 만큼 이 기능 모음을 ‘오디오 인텔리전스’라고 명명했다. 상시 샤잠 : 워치가 주변 음악을 감지하고 샤잠을 통해 자동으로 곡을 식별하며, 스마트 스택 위젯에 결과를 표시한다. 기존 애플워치도 수동으로 지원하던 기능이지만, 새롭게 달라진 점은 픽셀 스마트폰처럼 백그라운드에서 상시 작동한다는 것이다. 소리 인식 : 홈팟과 아이폰에서 지원하던 기능이 이제 애플워치에도 탑재된다. 현관 벨, 화재 경보기, 사이렌 등의 소리를 워치가 감지하면 시각적 알림을 받을 수 있다. 기존에는 아이폰이 가까이 있어야 했지만, 시리즈 12와 울트라 4는 독립적으로 작동한다. 라이브 리와인드 : 디지털 크라운을 두 번 누르면 주변에서 나온 최근 15초 발화 내용을 텍스트로 확인할 수 있다. 이후 시리에게 질문하거나 시리 앱에 저장할 수 있다. 시리 리캡 : 시리 앱에서 전체 대화의 요약본을 확인할 수 있어, 세부 내용을 잊거나 별도로 메모할 필요가 없다. 처음 두 기능은 별다른 논란거리가 아니다. 기존에 있던 기능이며, 달라진 점은 애플워치가 아이폰 개입 없이 백그라운드에서 단독으로 처리한다는 것뿐이다. 나머지 두 기능은 올해 말 베타로 출시될 예정으로, 논란의 중심에 서 있다. 과연 애플워치가 사용자 주변 소리를 항상 녹음하고 있는 것일까? 애플은 오디오 인텔리전스에 대한 보안 백서 를 공개해 작동 방식과 프라이버시 보호 방법을 상세히 설명했다. 읽어볼 만한 자료이며, 핵심 내용은 다음과 같다. 라이브 리와인드의 작동 원리 애플워치 시리즈 12와 울트라 4에서는 마이크로 입력되는 음성이 시큐어 인클레이브 내 소형 버퍼에 지속적으로 유입된다. 많은 애플 제품에서 이미 적용되는 방식으로, “헤이 시리” 호출을 인식하는 원리와 동일하다. 새 데이터가 유입될 때마다 이전 데이터를 덮어쓰는 롤링 버퍼 구조다. 시큐어 인클레이브는 운영체제, 앱, 심지어 애플도 접근할 수 없는 완전히 분리된 하드웨어 블록으로, 페이스 ID와 터치 ID 데이터가 저장되는 곳이기도 하다. 라이브 리와인드는 놓친 내용을 프라이버시 침해 없이 확인하게 해준다. Apple 디지털 크라운을 두 번 누르면 버퍼에 저장된 최근 15초 분량이 암호화된 보안 전송을 통해 아이폰으로 전달되고, AI 모델이 텍스트로 변환한다. 변환은 아이폰의 시큐어 인클레이브 내에서 이루어지므로, iOS 나머지 영역, 앱, 사용자, 애플 모두 음성 데이터에 접근할 수 없다. 순수한 음성-텍스트 변환만 이루어지며, 발화자를 식별하거나 구분하지 않는다. 음성 데이터는 변환 직후 즉시 폐기된다. 변환된 텍스트는 애플워치 화면에 표시되며, 시리에게 질문하거나 시리 앱에 저장하지 않는 한 별도로 보관되지 않는다. 시리 앱 데이터는 종단간 암호화되어 기기 간에 동기화되며, 대화를 30일, 1년, 또는 영구 보관하도록 자동 삭제 주기를 설정할 수 있다. 법원 명령이 있더라도 애플은 데이터를 복호화할 수 없으며, 복호화 키는 오직 사용자만 보유한다. 한 가지 더 주목할 점이 있다. 라이브 리와인드를 실행하면 무음 모드이거나 헤드폰이 연결된 상태에서도 애플워치 스피커에서 알림음이 울린다. 라이브 리와인드가 사용자 자신과 주변인의 프라이버시를 보호하는 방식은 다음과 같다. 음성 원본 데이터는 사용자, 시스템, 애플, 앱 그 어느 쪽도 접근할 수 없으며, 텍스트로 변환된 후 종단간 암호화된 시리 앱에 선택적으로 저장될 뿐이다. 시리 리캡의 작동 원리 시리 리캡도 유사한 방식으로 작동하지만, 처리 단계가 더 많다. 항상 켜두거나, 수동으로만 활성화하거나, 작동하지 않을 특정 장소와 시간대를 지정하는 방식으로 설정할 수 있다. 먼저, 소형 경량 모델이 대화가 실제로 이루어지고 있는지 감지한다. 대화가 감지되면 암호화된 보안 음성 버퍼가 암호화 데이터 전송을 통해 아이폰으로 전달되어 처리된다. 텍스트로 압축 변환되고, 음성 원본 데이터는 즉시 폐기된다. OS, 앱, 사용자, 애플 모두 원본 데이터에 접근할 수 없다. 변환된 텍스트는 잠재적으로 유해한 표현을 걸러내는 안전 필터를 거친다. 이후 요약에 도움이 되는 관련 맥락 데이터(청취 중인 음악, 관련 일정 항목, 현재 도시 등 개략적인 위치 정보 등)와 함께 암호화되어 애플의 프라이빗 클라우드 컴퓨트 서버로 전송된다. Apple 프라이빗 클라우드 컴퓨트는 제목과 핵심 요약본을 생성한다. 공원이나 마트처럼 일반적인 장소명은 유지하되, 구체적인 장소명이나 금융 정보 등 식별 가능한 민감 정보는 제거한다. 요약본은 암호화된 상태로 기기로 전송되어 시리 앱의 새 리캡 탭에 저장된다. 프라이빗 클라우드 컴퓨트 서버의 모든 데이터는 처리 직후 즉시 폐기되며, 애플은 어떤 데이터도 보관하지 않는다. 리캡 탭의 요약본은 별도로 저장하지 않으면 7일 후 자동 삭제된다. 라이브 리와인드와 마찬가지로 시리 리캡도 녹음 파일을 생성하지 않으며, 발화자를 식별하지 않고, 축자 기록도 남기지 않는다. 처리 단계 어디에서도 사용자, 앱, 애플 중 누구도 음성 데이터에 접근할 수 없다. 마지막으로, 라이브 리와인드와 시리 리캡은 만 13세 미만 사용자에게는 지원되지 않는다. 만 18세 미만 자녀 계정 사용자는 부모 또는 보호자가 직접 기능을 활성화해야 한다. dl-itworldkorea@foundryco.com

“도구보다 강력한 조직 구조” AI 집착 없이 생산성 3배를 달성하다

18개월 전 실리콘밸리의 한 컨퍼런스에서 AI 에이전트가 프로덕션 품질의 코드를 작성하는 모습을 실시간으로 본 후, 필자는 엔지니어링 모델의 변화를 예감했다. 그로부터 몇 주 후 필자가 소속한 팀은 AI 도입 여부를 논의하는 단계를 이미 넘어서 AI 에이전트 중심의 법률 소프트웨어 구축 방식을 어디까지 재설계할지를 고민하게 됐다. 그 결과 R&D 기업 전체에서 엔지니어 1인당 산출량은 약 3배 증가했다. 분기당 릴리즈는 약 2배 증가했으며, 배포 횟수는 82회에서 155회 이상으로 증가했고, 지난 18개월 동안 코드 100만 라인당 고객 보고 결함은 65% 감소했다. DORA 메트릭, 주기 시간, 개발자당 병합 요청 수, 기준선 대비 개발자당 변경 코드 라인 수를 사용해 추적했으며, 모든 지표가 개선됐다. 개선을 이끈 주된 동력은 도구보다는 기업의 업무 방식이다. 그간 대화를 나눈 많은 CTO는 어떤 형태로든 AI 코딩 파일럿을 진행하면서 더 빠른 프로토타이핑, 개선된 테스트 커버리지, 신속한 초안 작성 같은 성과를 얻고 있었다. 그러나 개발 수명 주기 자체를 바꾼 CTO는 거의 없다. 성과의 핵심은 바로 이 지점에 있다. 지난 18개월 동안 AI 중심의 제품 개발 수명 주기가 재구축됐다. 요구사항, 개발, 테스트, 보안, 배포, 거버넌스가 모두 바뀌었으며 일부는 이전과 완전히 달라졌다. 그 과정에서 많은 시행착오를 겪었다. 여기서 얻은 교훈을 처음부터 알았다면 수 개월을 절약할 수 있었을 것이다. 인수인계를 없앤 데서 가장 큰 효과 기존 방식에서는 기능이 출시되려면 제품 → 개발 → QA → 보안 → 배포 운영으로 최소 4단계의 인수인계를 거쳤다. 각 인수인계 단계마다 대기 시간이 발생해 시간과 문맥이 손실됐다. 기능 코딩이 1일 만에 끝나도 다른 팀의 백로그와 우선순위 때문에 2주 동안 진행이 멈추곤 했다. 구조 변경을 통해 한 팀이 기능을 처음부터 끝까지 담당하고, AI 에이전트가 각 단계의 반복적 업무를 처리하는 방식으로 전환했다. 사양에서 병합 요청까지 15일이 걸렸던 기능이 현재 약 4시간에 완료된다. 중요한 것은 생성 코드의 라인 수가 아닌 아이디어부터 배포까지의 총 소요 시간을 측정하고, 병목 지점을 찾는 것이다. 바로 그곳에서 숨겨진 성과를 발굴할 수 있다. 거버넌스로 도입 가속화 대다수 엔지니어링 기업은 혁신 증명 후 거버넌스를 추가한다. 순서를 뒤집은 접근이 이루어졌다. 법률 소프트웨어를 개발하는 분야에서는 중요 사안에 틀린 답을 제시하면 고객에게 큰 손해가 발생한다. 따라서 빠르게 진행하고 나중에 정리하는 방식은 불가능하다. 초기 파일럿 팀을 넘어 확장하기 전에 AI가 생산하는 모든 결과물에 대한 코드 리뷰, 보안 스캔, 품질 기준이 수립됐다. 신뢰도 점수를 사용해 일상적 승인은 자동 통과시키고, 기준 이하의 모든 사안은 인력 검토로 넘긴다. 보안 및 품질 게이트는 최종 체크포인트가 아닌 파이프라인 전 단계에서 실행된다. 이런 거버넌스 구축은 도입 가속화를 크게 앞당겼다. 엔지니어는 시스템을 신뢰했으므로 에이전트 코드가 리뷰를 통과하는지, 취약점이 발생하는지, 모델 오류 시 책임 범위가 무엇인지 더 이상 우려할 필요가 없었다. 18개월 전 AI 지원 병합 요청은 전체의 약 3%였으나 현재 68%에 도달했으며, 기업 전 엔지니어가 AI를 사용하는 가운데 같은 기간 취약점 밀도는 76% 감소했다. 거버넌스를 먼저 확립하고 도입을 진행하는 이 방식은 일반적 관행과 정반대다. 선택한 도구에 대한 숙련도 높이기 더 나은 모델과 에이전트가 거의 매주 출시된다. 초기에는 평가에 에너지를 쏟았지만, 어느 순간부터 평가를 중단하고 소수의 코딩 에이전트로 표준화했다. 최신 기술 추적보다 선택한 도구의 깊이 있는 이해에서 더 큰 효과를 얻었다. 코딩 에이전트의 강점과 한계를 파악하고, 실제 작동 방식 중심으로 워크플로우를 조정했다. 다음 릴리즈의 약속된 기능이 Python의 멀티프로세싱과 Airflow, 그리고 관련된 문제 해결기 1편

저희 팀은 데이터 입수 플랫폼의 배치 워크플로를 Airflow 2.10.2로 운영하고 있습니다. 2025년 4월 Airflow 3.0이 릴리스되었고, UI 개선과 다양한 신규 기능이 포함되었습니다. 이 변화가 저희 운영 환경에 필요하다고 판단했고 도입을 위한 PoC(Proof of Concept)를 진행했습니다. 이 글은 그 PoC 과정에서 Python의 멀티프로세싱 방식 중 하나인 fork로 인해 발생한 문제를 발견해 해결하고 기여한 과정을 다루는 시리즈의 1편입니다. 1편에서는 이 문제를 이해하는 데 필요한 배경지식을 다룹니다. Airflow가 task를 실행할 때 요구되는 조건을 살펴보고, 이를 만족하는 Python 멀티프로세싱 방식을 비교한 뒤, Airflow가 실제로 채택한 방식과 그 한계를 설명합니다. 2편에서는 이 한계가 Airflow에 실제로 어떤 문제를 일으켰는지, 원인과 해결 과정을 다룹니다. Airflow의 task 실행 요구 사항 Apache Airflow 는 Python으로 작성된 워크플로 오케스트레이션 도구입니다. 사용자는 task들 사이의 의존 관계를 Dag 로 정의하고, Airflow는 정해진 스케줄에 따라 그 task들을 실행합니다. Dag는 task 집합과 그 사이의 의존 관계, 실행 순서를 정의하는 Airflow의 기본 단위입니다. task 실행에는 병렬성과 격리성이라는 두 가지 핵심적인 요구 사항이 있으며, Airflow는 이를 모두 만족해야 합니다. 병렬성 병렬성은 여러 task를 동시에 수행할 수 있는 능력입니다. Airflow는 정해진 스케줄에 따라 다수의 task를 실행해야 하므로 병렬성이 필요합니다. 그런데 Airflow는 Python으로 작성된 도구입니다. Python의 표준 구현체인 CPython 에는 GIL(Global Interpreter Lock) 이 있습니다. 이 때문에 하나의 인터프리터 안에서는 스레드가 아무리 많아도 Python 바이트코드는 한 순간에 하나만 실행됩니다. 즉, 멀티코어 CPU에서도 Python 코드는 동시에 코어 하나에서만 실행됩니다. CPU 집약적인(CPU-bound) 작업에서 멀티코어의 병렬 처리 이점을 얻지 못합니다. Airflow는 이 제약을 극복해야 합니다. 격리성 각 task의 수행이 부모 프로세스와 다른 task에 영향을 주지 않아야 합니다. 여기서 부모 프로세스는 task를 실행하는 프로세스를 생성한 상위 프로세스를 뜻합니다. Airflow는 사용자가 작성한 코드가 task로 실행되는 구조입니다. 심한 경우 해당 task가 부모 프로세스 전체를 종료시킬 수도 있으며, 이는 전체 task의 장애로 이어질 수 있습니다. Airflow가 격리성을 필요로 하는 이유는 하나 더 있습니다. Python은 모듈을 전역( sys.modules )으로 관리하며, 한 번 등록된 모듈을 전역에서 삭제하거나 갱신하기가 어렵습니다. 런타임에 import된 모듈은 코드가 바뀌어도 이를 다시 등록하기가 매우 어렵다는 뜻입니다. 가령 사용자는 task에서 import mypackage.plugins 와 같이 본인이 작성한 모듈을 불러옵니다. 격리성이 보장되지 않는다면, 해당 모듈은 Git-Sync 를 통해 변경이 일어나도 반영되지 않음을 의미합니다. task가 등록한 모듈은 task 완료와 함께 폐기되어야 합니다. Airflow의 멀티프로세싱 도입 Airflow는 앞서 살펴본 두 요구 사항을 만족하기 위해 멀티프로세싱을 사용했습니다. 즉, task 하나당 프로세스를 하나씩 생성해 그 안에서 실행하고, 종료 시 폐기하는 것입니다. 이를 통해 진정한 CPU 병렬성을 얻을 수 있습니다. 또한 task의 비정상 종료가 부모 프로세스에 영향을 주지 않게 하고, 부모 프로세스의 전역 모듈이 오염되는 것을 막습니다. task 종료 시 프로세스를 폐기함으로써 격리성을 보장할 수 있습니다. Python의 멀티프로세싱 방식 Airflow가 멀티프로세싱을 택했다면, 다음 질문은 프로세스를 어떻게 만드느냐입니다. 동의 없는 녹음이 불러온 법정 다툼, AI 노트 필기 앱의 법적 리스크

AI 노트테이킹 앱은 회의 녹음, 대화 요약 생성, 회의 후 액션 아이템 제안 등의 목적으로 직장인 사이에서 점점 더 널리 활용되고 있다. 직접 노트를 필기하는 대신 회의에 집중할 수 있게 해준다는 생산성 향상 효과를 약속하지만, AI 도구의 부상은 동시에 개인정보 보호 관련 의문을 불러일으키고 있다. 특히 회의 참여자들로부터 사전 동의를 받는 절차가 핵심 쟁점으로 부상했으며, 그 우려가 커지면서 AI 노트테이킹 도구를 판매하는 소프트웨어 업체를 상대로 한 소송이 잇따르고 있다. 근본적인 문제 자체는 새로운 것이 아니다. 구술 녹음기로 전화 통화를 녹음하는 것은 오래전부터 가능했고, 몰래 녹음에 관한 법률도 수십 년 전부터 존재해 왔다. 그러나 데스크톱이나 스마트폰 앱을 통해 AI 노트테이커에 손쉽게 접근할 수 있게 되면서, 나중에 참고하기 위해 대화를 녹음하는 행위가 그 어느 때보다 쉬워졌다. 기술 활용 과정에서 제기되는 까다로운 질문 중 하나는 소프트웨어 업체 서버로 전송되는 대화 데이터의 처리 방식이다. 녹음본과 녹취록이 각 업체의 AI 모델 학습에 활용되거나 생체 음성 지문 생성에 쓰이는 것은 아닌지에 대한 의문도 제기된다. 이 같은 관행들이 현재 미국 법원에서 쟁점으로 다뤄지고 있다. 3,500만 명의 사용자를 보유했다는 AI 노트테이킹 서비스 업체 오터(Otter)는 지난해 캘리포니아 연방 법원에서 집단 소송의 대상이 됐다. 소장에서는 오터가 개인들의 동의 없이 녹음하고, 그 음성을 자사 음성 인식 AI 도구 학습에 활용했다고 주장했다. 지난달 담당 판사는 주요 청구에 대한 오터의 각하 신청을 기각했으며, 다만 소송 범위는 축소됐다. 지난해 말 일리노이주 법원에 제기된 또 다른 소송에서는 AI 회의 관리 서비스 업체 파이어플라이즈(Fireflies)가 피소됐다. 소장에 따르면 파이어플라이즈가 사용자 동의 없이 생체 음성 지문을 수집·저장해 일리노이 생체인식 정보 개인정보보호법(BIPA)을 위반했다는 혐의다. 파이어플라이즈는 개인 2,000만 명 이상과 100만 개 이상의 기업을 고객으로 두고 있다고 밝히고 있다. 올해 초에는 미국 워싱턴주 법원에서 집단 소송이 제기됐다. 마이크로소프트 협업 앱 팀즈의 실시간 전사(轉寫) 기능이 동의 없이 생체 데이터를 수집함으로써 BIPA를 위반하고 있다는 주장이다. 가장 최근에는 풍부한 자금을 확보한 신생업체 그래놀라(Granola)가 모든 회의 참여자의 인지 없이 작동하도록 제품을 설계해 전자통신 개인정보보호법(ECPA)을 위반했다는 소장이 제출됐다. 소장은 또한 그래놀라가 동의 없이 대화 데이터를 자사 AI 모델 학습에 활용하고 있다는 주장도 담고 있다. 제기된 소송 중 어느 것도 아직 해결되지 않았으며, 제품 및 서비스의 설계·제공 과정에서 어느 업체가 법을 위반했는지도 불분명하다. 다만 일련의 소송들은 AI 노트테이커 사용을 허용하는 기업이 녹음 사전 동의와 대화 데이터 처리 방식이라는 두 측면 모두에서 신중하게 고려해야 할 사항들을 부각시키고 있다. 더 넓게 보면, 이번 소송은 AI 노트테이킹 앱, 스마트 글라스, 기타 녹음 장치 등 타인을 더 쉽게 녹음할 수 있게 해주는 신기술에 기존의 개인정보 보호 및 동의 규정이 어떻게 적용되는지에 관한 의문을 제기하고 있다. 미국 법무법인 반스 앤 손버그 파트너이자 데이터 보안·개인정보 보호법 실무 그룹 창립 멤버 겸 공동 의장인 브라이언 맥기니스와 소송의 핵심 쟁점, 예상 결과, 기업의 AI 노트테이킹 앱 안전 활용 방안에 대해 이야기를 나눴다. 유명 AI 노트테이킹 앱을 상대로 한 소송이 이미 여러 건 제기됐다. 각 소송간 주요 공통점은 무엇이며, 업체는 어떤 법률을 위반한 혐의를 받고 있는가? 맥기니스는 소송들의 공통된 주장이 기업이 녹음에 동의하지 않았거나 적절한 고지를 받지 못한 사람들의 통신 내용을 포착했다는 것이라고 설명했다. 또한 일부 소송에서는 회의 데이터가 AI 모델 학습에 활용되며, 데이터가 처리된 이후에는 동의 철회가 사실상 불가능하다는 점도 주장됐다. 맥기니스는 연방 및 주 차원의 다양한 청구가 존재한다고 밝혔다. 연방 도청 법규인 전자통신 개인정보보호법(ECPA)이 대표적이다. 일반 원칙에 따르면 전자통신 개인정보보호법은 일방 당사자가 동의할 경우 감청을 허용하는데, 법정 예외 조항과 기술이 불법 감청 또는 제3자 도청에 해당하는지 여부에 관한 쟁점이 전제된다. 맥기니스는 “사용자가 동의하면 20명 규모의 회의에서도 충분한 것으로 간주되며, 나머지 참여자들의 동의까지 반드시 받을 필요는 없다”고 설명했다. 그러나 캘리포니아주를 비롯한 소수의 주는 ‘쌍방 동의(two-party consent)’ 주에 해당하여, 통화에 참여한 모든 개인의 동의가 필요하다. 노트테이커를 활성화한 당사자의 동의만으로는 부족하고 녹음 대상이 되는 다른 참여자들의 동의도 받아야 하며, 이와 관련한 주법이 별도로 마련돼 있다. 또한 맥기니스는 이 맥락에서 캘리포니아 개인정보침해방지법(CIPA)이 활용되고 있다고 전했다. 전화 도청을 위해 설계된 도청 법규가 현재는 인터넷에도 적용되는 추세여서, 관련 소송이 다수 제기되고 있다. 생체 데이터 활용과 관련해서는 어떤 쟁점이 있는가? 생체 데이터 규제 법안을 도입하는 주(州)가 증가하는 추세 속에서, 특히 일리노이 BIPA가 특히 두드러진다. 개인이 법률 위반 기업을 직접 제소할 수 있는 사적 소송권을 부여하고 있기 때문이다. 오디오 녹음이나 알고리즘을 실행하지 않는 단순 영상 녹화의 경우 반드시 생체 정보가 수집되는 것은 아니다. 그러나 특정인을 식별하기 시작하는 순간 얼굴 특징이나 음성 지문처럼 법령상 생체 정보의 정의에 포함되는 정보가 녹음된다. 단순한 개인정보 수집을 넘어 훨씬 민감하고 규제 수준이 높은 생체 정보까지 수집하게 되는 셈이다. AI 노트테이커가 녹음한 내용이 음성 지문 같은 형태의 생체 정보를 생성하는 데 활용될 수 있다는 점이 이번 소송의 핵심 논거라는 지적이다. 사진 저장·처리 전문 업체 셔터플라이(Shutterfly)가 일리노이주에서 얼굴 스캐닝 관련 소송에 휘말려 업계 관행이 일부 바뀐 사례처럼, BIPA로 인한 소송과 업계 변화는 이미 전례가 있다. 적지 않은 기업이 이 법률을 피하기 위해 일리노이주 진출 자체를 꺼리는 것도 같은 맥락으로 볼 수 있다. 그러나 고객사 입장에서는 회의 참여자가 누구이고 회의 시점에 어느 위치에 있는지 정확히 파악하기 어렵다. 따라서 이런 도구를 활용하려면 생체인식 법률을 준수하며 개별 동의를 받거나, 생체 관련 법률을 운용하는 주를 피하는 방법 중 하나를 선택해야 한다. 탐지를 최소화한 채 최대한 폭넓게 활용하는 것을 목표로 하는 앱에는 이 또한 하나의 도전 과제가 될 수밖에 없다는 점에서 주목된다. 이번 소송이 어떤 방향으로 결론날 것으로 보는가? 향후 새로운 법률 제정 없이 이런 도구의 사용 자체가 전면 금지될 가능성은 낮다는 전망이 유력하다. 맥기니스는 도구 활용 방식에 대한 변화와 통제 요건이 도입되는 결과가 훨씬 더 가능성이 높으며, 가장 명확한 형태는 팝업 고지창이 될 것으로 전망했다. 또한, “회의 녹음 사실, 담당자 정보, 개인정보 처리방침과 이용약관을 고지하고 동의 여부를 묻는 팝업 형태로, 녹음 대상이 되는 모든 참여자로부터 명시적 사전 동의를 받는 방식이 될 것”이라고 설명했다. 또한 맥기니스는 회의 참여자 한 명의 동의만으로 나머지 전원을 자동 녹음할 수 있다는 논리는 법적으로 위험에 처할 가능성이 있으며, 전원 동의를 요건으로 하는 기준으로 대체될 수도 있다고 지적했다. 그래놀라 소송은 한층 새롭고 흥미로운 유형의 사례다. 그래놀라의 마케팅 일부가 다른 참여자들이 도구의 존재를 인식하지 못하는 것을 특징으로 내세우고 있으며, 소장에서도 제품이 다른 참여자들에게 고지 없이 작동하도록 설계됐다고 주장하기 때문이다. 맥기니스는 이런 유형의 행위가 모든 참여자에게 고지하거나 동의를 받지 않을 경우 불법으로 간주해 전면 금지하는 판결로 이어질 가능성도 배제할 수 없다고 설명했다. 맥기니스는 이런 논의가 AI 노트테이킹을 넘어 더 넓은 영역으로 확장될 때 더욱 흥미로워진다고 말했다. 메타 글라스나 여러 종류의 AI 웨어러블이 대표적인 예다. 그래놀라에는 애플 워치 앱이 있으며, 스마트폰 뒷면에 부착하는 상시 녹음 기기 플라우드 노트(Plaud Note)처럼 다양한 웨어러블 또는 물리적 기기도 있다. 온라인 회의에서는 고지와 동의를 구조적으로 주고받을 수 있지만, 이런 기기를 사용하면 길을 걷다가 타인을 녹음하거나 카페에서 전혀 모르는 옆 테이블 손님을 녹음하는 상황으로 나아갈 우려도 있다. 사람들에게 고지하기 위한 디지털 인터페이스가 없는 현실 공간에서는 동의와 고지를 어떻게 받아야 하는지에 대한 의문이 남는다. 맥기니스는 “종이와 펜으로 동의서를 받아야 하는 것인지, 직접 말로 알려야 하는 것인지—일련의 소송들이 이제 막 답을 찾아가기 시작한 흥미로운 문제다. 동의를 어떻게 받을 것인지, 문서나 화면 없이 고지를 어떻게 전달할 것인지는 법이 반드시 풀어야 할 흥미로운 질문”이라고 전했다. 직장 내 AI 필기 앱의 활용이 증가하고 있다. 기업이 안전하게 기술을 도입하려면 어떻게 해야 하는가? 맥기니스는 클라이언트로부터 많은 문의를 받고 있으며, 업계가 처리 방식에 대해 상당히 혼란스러워하는 상황이라고 전했다. 기업 내 AI 광범위 도입 및 생산성 향상에 대한 압박이 있고 직원도 도구를 선호하지만, 자신도 모르는 사이 회의가 녹음됐거나 녹취록 내용이 실제 발언과 달랐다는 우려도 기업 내에서 적지 않다는 게 클라이언트의 공통된 반응이었다. 현재 상태에서 이런 도구가 합법적이라고 단정 지어 말하기 어렵다는 게 맥기니스의 입장이다. 합법적이고 안전하게 사용할 방법은 존재하지만, 소프트웨어 업체가 기본 제공하는 기능 이상을 갖춰야 할 가능성이 크다. 그래놀라의 경우, 특정 고지 기능이 기본값으로 비활성화 상태에서 출시된다는 게 맥기니스의 설명이다. 영상·음성 워터마킹과 팝업 고지창을 켤 수 있지만, 법적·개인정보 준수 체계를 설정하고 구현하는 책임은 결국 개인 사용자에게 돌아간다. 가장 엄격한 주의 법률을 기준으로 삼아야 한다는 것이 맥기니스의 권고다. 소송 위험을 줄이려면 통화 참여자 전원의 동의를 받아야 하며, 구두 동의도 가능하지만 서면 동의가 더 확실하다. 내부 AI 노트테이킹 정책 수립이 필수라는 것도 권고 사항이다. Vulnerability Localization Benchmark: Measuring Agentic Security Analysis at Repository Scale

Language-model agents increasingly operate over complete software repositories, yet cybersecurity evaluations primarily measure whether they can detect, reproduce, or repair vulnerabilities rather than whether they can locate the relevant code. We study vulnerability localization: given a weakness class and an unfamiliar repository, identify the implementation files associated with that weakness. We introduce the Vulnerability Localization Benchmark (VLoc Bench), comprising 500 real world vulnerabilities from 290 repositories across six package ecosystems and 147 CWE categories. Each task pairs repository snapshots immediately before and after a security fix. On the vulnerable snapshot, an agent receives only the CWE description and read-only terminal access and must return the affected files; on the patched snapshot, it must determine that the recorded vulnerability is no longer present. We evaluate 27 language models and four static-analysis tools under a common agent interface. Repository-scale vulnerability localization remains difficult: the strongest system achieves 0.229 File F1, and 38.4% of tasks receive no correct localization from any evaluated model. We further find that stronger localization does not imply reliable behavior after remediation: systems that identify vulnerable files effectively can still report unsupported locations on patched repositories. These results establish vulnerability localization as a distinct repository-scale capability and provide a setting for studying both how security agents search for vulnerable code and when they should refrain from reporting it.

Pilot Early, Commit Late: A Real-Options Model of Enterprise AI Adoption under Rapid Technological Progress

Artificial intelligence presents firms with an unusual timing problem. The technology frontier is improving rapidly, implementation is partly irreversible, and organization-specific capabilities are accumulated through action. This paper develops a two-period decision model of AI deployment under uncertainty in which a firm chooses among immediate deployment, a limited pilot, and waiting. Deployment earns current operating value but exposes the firm to architectural obsolescence; waiting preserves the option to adopt after the frontier is observed; a pilot sacrifices current operating value to build organization-specific learning without full commitment. The model yields five central timing results and a sixth comparative result on where learning occurs. First, a mean-preserving increase in frontier uncertainty raises the value of waiting and piloting but leaves immediate deployment unchanged when its payoff is affine in the frontier. Second, faster expected frontier progress can reduce the relative attractiveness of immediate deployment when deployed architecture captures only a limited share of future improvement. Third, a pilot dominates waiting exactly when the expected value of the capability it builds exceeds its cost. Fourth, sufficiently valuable organization-specific learning creates a nonempty region in which "pilot early, commit late" is optimal. Fifth, there is a closed-form modularity threshold above which immediate deployment dominates the best outside option. Sixth, production learning and pilot-specific learning affect the timing margin differently.
