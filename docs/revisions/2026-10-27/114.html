AI가 코드를 더 많이 만들수록 ‘덜 만드는 판단’이 중요해지는 이유

2026. 10. 27 내용 확인·보완

설정 하나를 바꾸려고 들어갔는데 검색창, 추천 카드, 애니메이션부터 만나는 화면이 있다. 각각은 잘 만든 기능이어도 내가 하려던 일은 더 멀어진다. AI로 기능을 빠르게 붙일 수 있을수록 ‘만들 수 있다’와 ‘지금 이 화면에 필요하다’를 구분하는 판단이 중요해진다.

코드가 늘어나는 속도와 사용자가 일을 끝내는 속도는 다르다

디자이너 Jakub Krehel의 글 ‘Less is more, more or less’는 AI가 추가를 쉽게 만드는 만큼 무엇을 넣지 않을지 이해하는 일이 중요하다고 주장한다. 메뉴 애니메이션 사례도 소개하지만, 모든 애니메이션을 없애야 한다는 실험 법칙으로 읽을 필요는 없다.

내가 여기서 가져온 기준은 결과를 보는 순서다. 먼저 사용자가 끝내려는 동작을 정하고, 새 기능이 그 동작을 줄이는지 본다. 마지막으로 코드와 화면이 얼마나 늘었는지 살핀다. 코드 줄 수만 줄이면 오류 설명이나 필요한 확인 단계까지 사라질 수 있다.

추가 제안을 세 칸에 나누면 보류할 이유가 보인다

다음은 실제 서비스의 개선 성과가 아니라, 파일을 제출하는 화면을 가정한 판단 예시다. 같은 기능도 사용 빈도와 실패 비용에 따라 선택이 달라진다.

제안된 기능도움이 되는 조건먼저 확인할 것
업로드 전 파일 요약내용을 확인하고 제출해야 함요약이 원본 확인을 대체하지 않는가
여러 단계의 전환 효과현재 진행 상태를 이해하는 데 필요다음 동작을 기다리게만 하는가
자동 제출대상과 내용이 명확하고 실패를 처리 가능잘못된 파일을 되돌릴 수 있는가
추천 기능 묶음사용자가 다음 작업을 찾는 중지금 제출하려던 일을 가리는가
기존 본문 중간 광고 위치

AI에게 ‘기능을 더 넣어줘’ 대신 이렇게 요청한다

범위를 비워 두면 도구가 친절함을 기능 추가로 해석할 수 있다. 먼저 변하면 안 되는 동작과 확인할 결과를 적는다.

사용자 목표: 파일 한 개를 확인하고 지정된 위치에 제출한다.
유지할 것: 현재 제출 경로와 오류 안내.
바꿀 것: 파일 선택 뒤 이름과 크기를 확인하는 부분만.
제외할 것: 자동 제출, 추천 카드, 새 계정 기능.
확인: 다른 파일을 다시 골라도 마지막으로 고른 파일만 제출되는지 본다.

이 요청문은 그대로 복사하면 모든 제품에 맞는 정답이 아니다. 핵심은 AI가 마음대로 좋은 기능을 정의하도록 두지 않고, 사용자의 일과 변경 범위를 연결하는 것이다.

작동 확인 다음에는 ‘불편이 줄었나’를 본다

버튼이 눌리고 테스트가 통과했다는 사실은 필요하지만 충분하지 않다. 사용자가 어느 버튼을 눌러야 할지 더 헷갈리게 됐다면 기능은 작동해도 흐름은 나빠졌을 수 있다. 반대로 확인 단계가 하나 늘었어도 잘못된 제출을 줄이는 데 필요할 수 있다.

  1. 현재 화면에서 목표 동작까지의 순서를 적는다.
  2. 변경 화면에서도 같은 순서를 적어 새로 고민해야 하는 선택을 찾는다.
  3. 잘못된 파일·빈 입력처럼 한 가지 실패 조건을 넣어 되돌아갈 수 있는지 본다.
  4. 추가한 요소가 어느 단계에 도움을 주는지 설명되지 않으면 보류한다.

시간이나 성공률을 측정했다면 실제 조건과 함께 기록한다. 측정하지 않았다면 ‘더 빠르다’ 대신 선택 단계가 줄었는지, 상태가 드러나는지처럼 관찰한 변화만 설명한다.

덜 만드는 판단은 필요한 설명을 지우는 일이 아니다

단순함을 핑계로 오류 메시지를 없애거나 접근성을 낮추면 사용자가 추측할 일이 늘어난다. 남길 것은 사용자가 현재 상태를 이해하고 다음 행동을 고르는 데 필요한 정보다. 덜 만들자는 기준은 화면의 장식 수가 아니라 사용자의 불필요한 고민이다.

AI가 구현을 도울수록 사람은 어떤 문제를 풀지, 무엇을 건드리지 않을지 더 분명히 설명해야 한다. 이 글의 파일 제출 사례와 요청문은 그 판단을 연습하기 위한 편집 예시이며, 실제 사용성 실험에서 나온 성과 수치는 아니다.
