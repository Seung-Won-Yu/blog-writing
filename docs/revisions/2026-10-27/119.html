Ghostty는 왜 Zig를 택했을까? 언어보다 먼저 볼 터미널 구조

2026. 10. 27 내용 확인·보완

검은 창에 글자를 보여 주는 터미널을 만드는 데 왜 프로그래밍 언어와 화면 기술이 여러 개 필요할까. Ghostty를 보면 답은 ‘Zig가 빨라서’ 한마디로 끝나지 않는다. 터미널의 공통 동작과 운영체제다운 화면을 나누고, 두 부분을 연결한 구조가 중요한 선택이다.

Zig를 고른 출발점과 제품의 구조를 나눠 보자

미첼 하시모토는 2025년 Terminal Trove 인터뷰에서 터미널·셸 등 여러 층의 동작을 더 알고 싶었고 Zig와 그래픽 프로그래밍을 배울 프로젝트를 찾던 중 Ghostty를 시작했다고 설명한다. 처음부터 모든 언어를 벤치마크해 Zig가 가장 빨랐다고 결론 낸 이야기는 아니다.

프로젝트가 이어지면서 목표는 속도·기능·각 운영체제에 자연스러운 화면을 함께 갖추는 쪽으로 구체화됐다. 언어 선택의 개인적 출발점과 이후 제품이 해결한 과제를 구분하면 ‘유명한 프로젝트가 쓰니 내 앱도 같은 언어’라는 성급한 결론을 피할 수 있다.

터미널은 명령을 실행하는 셸과 다르다

터미널 에뮬레이터는 입력을 전달하고 프로그램이 보낸 글자와 제어 신호를 화면에 표현하는 앱이다. 셸은 그 안에서 명령을 해석하는 프로그램이다. 터미널 앱을 바꿨다고 셸의 모든 동작이나 실행하는 프로그램의 성능이 함께 바뀌는 것은 아니다.

Ghostty 공식 설명은 공통 핵심인 libghostty와 운영체제별 화면을 나눈다. 이 분리가 있어야 같은 터미널 동작을 공유하면서도 macOS와 Linux의 화면 관례를 따를 수 있다.

부분Ghostty 설명에 나온 구성쉽게 말하면
공통 핵심Zig 기반 libghostty문자 처리·글꼴·화면 그리기의 공통 엔진
macOS 화면Swift와 AppKit·SwiftUI맥의 창·탭·시스템 기능을 다루는 외피
Linux 화면Zig와 GTK4 C API리눅스 데스크톱 관례에 맞춘 외피
기존 본문 중간 광고 위치

서로 다른 언어를 붙이는 경계가 설계의 핵심이다

인터뷰에서 하시모토는 Zig 코드를 C ABI와 호환되는 라이브러리로 만들고 운영체제별 화면에서 연결하는 구조를 설명한다. ABI는 서로 다른 코드가 함수를 부르고 값을 주고받을 때 지키는 연결 규칙이라고 이해하면 된다.

배달 서비스에 비유하면 주문 처리 규칙은 공유하되, 매장마다 다른 출입구와 안내판은 따로 맞추는 방식이다. 공통 엔진에 모든 화면 관례를 억지로 넣지 않아도 된다. 이 비유는 구조를 설명하기 위한 것이며 Ghostty 내부의 모든 구현을 대응시킨 설계도는 아니다.

내 프로젝트에는 언어 이름보다 이 질문을 가져오자

작은 앱의 화면 하나를 만들면서 처음부터 다중 언어 구조를 도입할 필요는 없다. 연결 경계가 늘면 빌드·배포·디버깅 부담도 생긴다. 공통 부분을 분리할 이유가 실제로 있는지 먼저 본다.

  1. 두 플랫폼에서 완전히 같은 규칙과 달라야 하는 화면 동작을 적는다.
  2. 현재 문제가 계산·입출력·화면 갱신 중 어디에 있는지 확인한다.
  3. 공통 코드를 분리했을 때 테스트할 입력과 결과를 정의한다.
  4. 언어를 추가해 얻는 이득과 연결·배포 부담을 함께 비교한다.

Ghostty가 쓰는 언어만 보고 내 프로그램의 병목을 설명할 수는 없다. 터미널이 빠르다는 말도 시작 시간·스크롤·입력 반응처럼 측정 대상에 따라 달라진다. 이 글에서는 실행 속도 비교나 특정 플랫폼의 우열을 측정하지 않았다.

왜 Zig인가를 물었다면, 무엇을 분리했는지도 보자

Ghostty의 흥미로운 점은 하나의 언어로 모든 것을 통일하지 않았다는 데 있다. 공통 엔진에는 Zig를 쓰고, 화면은 운영체제의 기술과 연결한다. 언어 선택을 제품의 요구와 연결해 읽으면 유행하는 언어 소개보다 내 설계에 남는 질문이 많아진다.

인터뷰와 공식 설명을 바탕으로 정리했으며 직접 빌드·성능 측정한 사용기는 아니다. 라이브러리 API의 현재 안정성이나 지원 범위는 도입 시점의 공식 문서를 별도로 확인한다.
