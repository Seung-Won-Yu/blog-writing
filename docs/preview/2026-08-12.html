새 채팅을 열 때마다 빌드 명령과 코드 규칙을 다시 설명하는 일, 그리고 코딩 도구에서 내가 고른 로컬 모델을 써 보고 싶은 일은 닮아 보이지만 서로 다른 문제다. GitHub Copilot for JetBrains의 최신 업데이트는 이 둘을 한꺼번에 추가했다. Copilot Memory는 저장소의 규칙과 사용자 선호를 다음 작업으로 이어 주고, Ollama 연결은 사용할 모델 제공자를 바꾼다. 둘을 함께 켠다고 모든 Copilot 처리가 자동으로 로컬·비공개가 되는 것은 아니다. 기능의 경계부터 구분해야 설정도 안전해진다.

GitHub Copilot for JetBrains에 메모리와 Ollama 지원 추가

GitHub가 JetBrains용 Copilot에 저장소 규칙과 사용자 선호를 이어 주는 메모리, Ollama BYOK 제공자, 기업 관리 설정과 여러 사용성 개선을 추가했다. 메모리와 로컬 모델 선택은 서로 다른 데이터 경계를 가지므로 각각 검증해야 한다.

같은 업데이트에 들어왔지만 해결하는 문제는 다르다

GitHub가 8월 11일 공개한 JetBrains용 Copilot 업데이트의 눈에 띄는 항목은 지속 메모리와 Ollama 지원이다. JetBrains Marketplace의 1.15.0-261 계열 플러그인 변경 내역에도 두 기능이 함께 적혀 있으며, 해당 계열은 JetBrains 2026.1 빌드부터 호환된다. 그래서 하나의 ‘로컬 AI 기능’처럼 보기 쉽지만 실제로는 서로 다른 층을 바꾼다.

메모리는 ‘무엇을 기억할지’를 다루고 Ollama는 ‘어떤 모델로 답을 만들지’를 다룬다. 메모리를 끈 채 Ollama만 쓸 수도 있고, GitHub가 제공하는 모델을 쓰면서 메모리만 켤 수도 있다. 이 구분을 알아야 개인정보와 저장소 코드가 어디에 남는지 확인할 질문도 정확해진다.

메모리는 대화 저장보다 좁고 구조적이다

GitHub 문서에서 Copilot Memory가 다루는 것은 저장소 단위의 사실과 사용자 단위의 선호다. 코딩 규칙, 아키텍처 결정, 빌드 명령, 프로젝트 규칙 같은 항목이 저장소 사실에 해당한다. 선호는 답변 방식처럼 한 사용자가 여러 저장소에서 이어 쓰려는 정보다. 저장소 사실에는 근거가 붙고 현재 브랜치를 기준으로 다시 확인되므로, 단순히 예전 채팅을 통째로 불러오는 기능과는 다르다.

공유 범위도 알아둘 필요가 있다. 저장소에 쓰기 권한이 있고 메모리를 켠 사용자가 만든 저장소 사실은 같은 저장소에서 메모리를 사용할 권한이 있는 구성원과 공유될 수 있다. 반면 사용자 선호는 해당 사용자에게만 보인다. 저장소 소유자는 저장된 사실을 검토하고 삭제할 수 있고, 사용되거나 다시 검증되지 않은 사실과 선호는 28일 뒤 자동 삭제된다. 다만 사용되면 기간이 다시 시작될 수 있다.

현재 메모리는 공개 미리보기다. 기능과 적용 범위가 바뀔 수 있다는 뜻이다. 개인용 유료 플랜에서는 기본 활성화될 수 있고, 조직·기업 계정은 관리자가 정책을 허용한 뒤 사용자가 끌 수 있다. 팀에서 쓰려면 편리함보다 먼저 ‘저장소 사실에 넣지 말아야 할 정보’와 검토 책임자를 정하는 편이 안전하다.

 

Ollama를 고르면 모델 경로가 바뀐다

이번 업데이트에서 Ollama는 BYOK 제공자로 추가됐다. JetBrains 안에서 제공자를 구성하고 설치된 모델을 선택할 수 있다. 인터넷 연결이나 외부 API 사용을 줄이고 싶은 개인 실험, 사내에서 승인한 로컬 모델 비교, 비용과 응답 시간을 직접 통제하려는 상황에 유용하다. 하지만 ‘Ollama 모델을 선택했다’는 사실만으로 Copilot 플러그인의 모든 기능과 데이터가 로컬 장치 안에서 끝난다고 결론 내릴 수는 없다.

실제 경계는 기능별로 확인해야 한다. 선택한 모델에 전달되는 프롬프트와 코드 범위, Copilot 서비스가 처리하는 인증·텔레메트리·도구 호출, MCP 서버와 외부 도구가 받는 데이터는 같은 문제가 아니다. 민감한 저장소라면 네트워크 요청과 로그, 조직 정책을 별도로 확인하고 승인된 테스트 데이터로 먼저 동작을 관찰해야 한다.

모델 자체의 능력도 변수다. 로컬 모델은 장비 메모리와 GPU, 컨텍스트 길이, 도구 호출 지원에 따라 답변 품질과 속도가 크게 달라진다. 큰 모델 이름만 보고 고르기보다 현재 프로젝트에서 자주 하는 코드 설명, 테스트 작성, 리팩터링 한 가지를 정해 응답 시간과 수정 정확도를 함께 비교하는 편이 낫다.

둘을 함께 켤 때는 작은 저장소로 먼저 확인한다

업무 저장소에서 바로 켜기보다 민감한 값이 없는 작은 예제 저장소를 준비한다. README에 빌드 명령 하나와 코드 규칙 하나를 적고, 첫 세션에서 이를 설명한 뒤 새 세션을 연다. Copilot이 같은 규칙을 다시 불러오는지, 근거가 현재 브랜치 내용과 맞는지 확인한다. 그다음 브랜치에서 규칙을 바꾸고 오래된 사실을 그대로 적용하지 않는지도 본다.

  • JetBrains IDE와 Copilot 플러그인의 호환 버전을 확인한다.
  • 민감하지 않은 저장소에서 기억할 규칙을 한두 개만 만든다.
  • 새 세션과 다른 브랜치에서 기억의 근거와 최신성을 확인한다.
  • Ollama 제공자를 연결하고 모델 하나를 골라 같은 작업을 반복한다.
  • 응답 품질·속도·도구 호출과 네트워크 요청을 비교한 뒤 범위를 넓힌다.

예를 들어 ‘테스트는 특정 명령으로 실행한다’는 규칙을 기억시킨 뒤 파일 구조와 명령을 바꿔 본다. 새 세션이 예전 명령을 고집하면 저장된 사실을 검토하거나 삭제해야 한다. Ollama 모델을 바꿨을 때는 같은 수정 요청으로 diff 크기, 테스트 통과 여부, 응답 시간을 기록한다. 메모리의 정확성과 모델의 성능을 한 번에 평가하지 말고 한 변수씩 바꾸는 것이 핵심이다.

팀에서는 모델보다 정책 순서가 먼저다

GitHub는 이번 릴리스에서 기업 관리 설정도 확대했다. 관리자는 플러그인 사용 가능 여부, MCP 서버 접근, 권한 우회 동작, OpenTelemetry 관련 설정을 통제할 수 있다. 메모리 정책도 조직과 기업 수준에서 관리된다. 개인이 로컬 모델을 실행할 수 있다는 것과 회사 코드에서 사용해도 된다는 것은 다른 판단이다.

결국 좋은 설정은 기능을 많이 켠 상태가 아니라 문제 하나마다 책임지는 기능이 분명한 상태다. 메모리는 반복되는 프로젝트 문맥을 줄이는 데 쓰고, Ollama는 모델 선택과 실행 환경을 시험하는 데 쓴다. 두 기능의 결과가 만족스럽더라도 팀 저장소에서는 관리자 정책과 로그 범위를 확인한 뒤 적용해야 한다.

이번 업데이트의 가치는 기능 수보다 경계를 나눠 준 데 있다. 반복 설명이 문제라면 메모리를 검증하고, 모델 선택권이 필요하다면 Ollama를 시험하면 된다. 둘을 함께 쓸 때도 저장되는 정보와 모델로 전달되는 정보를 따로 확인해야 한다. 작은 테스트 저장소에서 기억의 정확성, 모델의 품질과 속도, 조직 정책을 차례로 점검하면 편리함은 얻고 뜻밖의 정보 노출이나 오래된 규칙 적용은 줄일 수 있다. JetBrains 플러그인과 IDE 호환 버전을 먼저 확인한 뒤, 민감하지 않은 테스트 저장소에서 메모리 한 항목과 Ollama 모델 한 개만 켜고 새 세션·브랜치 변경·모델 전환을 차례로 검증한다.
