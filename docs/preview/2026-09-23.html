  • 첫 실행이 무거우면 /lsp logs, compile_commands.json, 인덱스 완료 뒤의 두 번째 탐색을 순서대로 확인한다.
  • WCI를 꺼도 언어 서버는 남지만 탐색은 다른 파싱 경로로 돌아가 느려질 수 있고, 설정은 프로젝트가 아닌 사용자 전역에 적용된다.

먼저 알아둘 말

WCI
Whole Codebase Indexing의 약자로, 열지 않은 파일까지 포함해 프로젝트 전체 심볼 관계를 저장하는 방식이다.
심볼
함수·클래스·변수처럼 코드에서 이름으로 정의되고 참조되는 대상을 뜻한다.
compile_commands.json
각 C++ 파일을 어떤 옵션과 include 경로로 컴파일하는지 기록한 데이터다. 언어 서버가 타입과 헤더 관계를 이해하는 데 쓴다.
주문형 파싱
미리 만든 전체 인덱스 대신 요청이 들어온 파일과 주변 정보를 그때 분석하는 방식이다.

핵심 해설 · GitHub Changelog · 2026. 9. 22

GitHub Copilot CLI, C++ 전체 코드베이스 인덱싱 기본 활성화

GitHub는 Copilot CLI의 Microsoft C++ Language Server가 전체 프로젝트 심볼을 지속 인덱스로 만들고 정의·참조·구현 찾기에 재사용하도록 WCI를 기본 활성화했다. 첫 구축은 시간과 메모리를 더 쓸 수 있으며 진행은 /lsp logs에서 확인한다.

첫 실행이 느린 것은 재사용할 지도를 만드는 시간이다

WCI는 C++ 프로젝트의 심볼 관계를 지속 인덱스로 만들어 정의·참조·구현 찾기에 재사용한다. 첫 구축은 무거울 수 있지만 완료 뒤에는 다시 쓴다. 열지 않은 파일까지 포함하므로 같은 관계를 요청마다 처음부터 찾는 일을 줄인다.

첫 프로젝트를 열 때는 색인을 처음 구축하므로 시간이 더 걸리고 CPU와 메모리 사용이 잠시 늘 수 있다. 큰 저장소에서 이 구간만 보고 실패라고 판단하면 안 된다. GitHub는 초기 구축이 끝난 뒤 인덱스를 재사용하고 변경된 코드에 맞춰 갱신한다고 설명한다.

  • /lsp logs에서 전체 코드베이스 인덱싱이 진행 중인지 완료됐는지 확인한다.
  • 언어 서버가 읽는 compile_commands.json 경로와 실제 빌드 구성이 맞는지 본다.
  • 같은 정의 찾기와 참조 찾기를 첫 실행과 인덱스 완료 뒤에 각각 반복한다.
  • 지속적인 자원 압박이 확인될 때만 사용자 전역 state.json에서 WCI를 끄고 세션을 재시작한다.

빨라지는 것은 답변 전체가 아니라 심볼 탐색 경로다

이번 발표가 직접 가리키는 대상은 Go to Definition, Find References, 구현 찾기, 심볼 검색이다. Copilot의 모든 답변 속도나 코드 생성 품질이 같은 비율로 좋아진다는 뜻은 아니다. 성능 배수도 공식 발표에 제시되지 않았다.

큰 C++ 저장소에서는 한 이름을 정확히 해석하려고 include 그래프, 매크로, 템플릿, 빌드 옵션을 함께 봐야 한다. 독립 자료도 코드가 커지고 빌드가 불완전할수록 스마트 탐색이 느려지거나 잘못된 선언으로 갈 수 있다고 설명한다. WCI는 그 관계를 재사용해 반복 작업을 줄인다.

compile_commands가 틀리면 빠른 색인도 엉뚱한 지도를 만든다

Microsoft C++ Language Server는 프로젝트의 컴파일 정보를 사용해 타입, 심볼, include와 파일 간 관계를 해석한다. 같은 소스라도 매크로와 include 경로, 표준 버전이 다르면 보이는 정의가 달라질 수 있으므로 compile_commands.json이 실제 빌드 구성을 가리키는지 먼저 봐야 한다.

제외 설정도 경계를 구분해야 한다. 문서에 따르면 cpp-lsp.json의 filesExclude와 searchExclude는 추가 디렉터리 스캔을 조정하지만, compile_commands.json에 명시된 번역 단위를 지우지는 않는다. 색인 크기를 줄이려다 빌드 입력까지 빠졌다고 오해하지 않도록 설정의 역할을 나눠야 한다.

두 번째 탐색이 판단 기준을 더 잘 보여 준다

첫 탐색과 같은 함수에서 정의 찾기와 참조 찾기를 다시 실행해 본다. 첫 번째는 인덱스를 만드는 시간과 요청 시간이 섞일 수 있지만, 두 번째는 재사용 효과를 확인하기 쉽다. 결과 파일과 참조 개수도 함께 비교해야 빠르지만 틀린 탐색을 성공으로 착각하지 않는다.

Meta의 대규모 코드 인덱싱 사례에서도 C++은 긴 컴파일 시간과 넓은 의존 관계 때문에 미리 색인하는 이점이 큰 언어로 꼽힌다. 동시에 헤더 하나가 바뀌면 그것을 포함하는 파일까지 다시 처리해야 해 갱신 비용이 생긴다. 지속 인덱스는 비용을 없애는 기능이 아니라, 같은 분석을 반복하지 않도록 위치를 바꾸는 기능이다.

계속 무거울 때만 사용자 전역 설정을 바꾼다

초기 색인이 끝난 뒤에도 시스템이 계속 압박받거나 저장소 특성상 인덱스 이득이 작다면 WCI를 끌 수 있다. 설정은 프로젝트의 cpp-lsp.json이나 Copilot CLI의 lsp.json이 아니라 사용자별 state.json의 use_symbol_index에 둔다. 즉 한 저장소만의 선택이 아니라 그 사용자의 모든 저장소에 적용된다.

파일에는 인증 데이터와 다른 사용자 설정이 함께 있을 수 있으므로 예제 JSON으로 통째로 덮어쓰거나 저장소에 커밋하면 안 된다. 기존 객체에서 해당 값만 바꾸고 실행 중인 Copilot CLI 세션을 닫은 뒤 다시 시작해야 적용된다. 다시 켤 때도 값을 true로 되돌리고 재시작한다.

인덱스가 없어도 텍스트 검색은 마지막 안전망으로 남는다

빌드 정보가 깨졌거나 생성 헤더가 빠져 구조적 탐색이 모호하면 rg 같은 텍스트 검색과 Git 기록을 함께 쓴다. WCI를 끈 뒤의 주문형 파싱도 남지만, 텍스트 검색은 컴파일이 되지 않는 상태에서도 실제 문자열과 파일 위치를 보여 준다.

따라서 선택은 WCI와 텍스트 검색 중 하나를 버리는 문제가 아니다. WCI로 정의와 참조 관계를 빠르게 좁히고, 결과가 의심스러울 때 텍스트 검색과 빌드 로그로 확인한다. 색인 완료 뒤 같은 탐색이 빨라지고 결과도 빌드 구성과 맞는다면 이번 변경을 제대로 활용한 것이다.

색인 완료 뒤 같은 심볼 탐색의 대기가 줄고 결과가 올바르면 WCI를 유지하며, 자원 부담이 계속될 때만 비활성화를 검토한다.
