PDF 텍스트 추출은 언제 OCR이 필요할까: AI 입력 준비 기준

페이지별 텍스트 상태와 OCR 보조 파일의 누락 경계를 나눠 AI 입력을 준비한다.

글자가 보이는데 추출 결과는 왜 비어 있을까

PDF에 올바른 텍스트가 있으면 먼저 추출하고, 이미지 속 글자만 있는 페이지는 OCR을 검토한다. 글자가 나온 뒤에도 누락·읽기 순서·표의 대응을 확인해야 AI에 넘길 준비가 끝난다.

  • 문제가 생긴 PDF의 본문·표·스캔 페이지를 각각 골라 화면과 복사한 문장을 대조한다.
  • 텍스트가 없거나 일부만 있으면 페이지별로 추출·OCR·수동 검토 경로를 정한다.
  • 혼합 PDF는 OCR 보조 텍스트 파일만 믿지 않고 최종 PDF 전체에서 다시 추출한다.
  • 필요한 문장·숫자·읽기 순서가 맞는 페이지에만 다음 AI 처리 단계를 허용한다.

PDF 설명서를 읽는 AI 도우미를 만든다고 가정해 보자. 화면에는 설치 안내가 또렷한데 추출한 문자열에는 제품명만 남았다. 모델을 바꾸기 전에 확인할 것은, 필요한 본문이 이미지인지 실제 텍스트인지다. 이는 실행 사례가 아니라 처리 경계를 설명하는 가상 장면이다.

여기서 말하는 AI 입력 준비는 PDF를 문자열로 바꿔 검색·요약 파이프라인에 넣는 경로다. PDF 화면 자체를 이해하는 멀티모달 서비스의 내부 처리 방식까지 같은 규칙이라고 가정하지 않는다.

pypdf는 글자를 읽지만 사진을 해독하지 않는다

pypdf는 PDF에 저장된 텍스트를 추출하는 도구다. 스캔 이미지만 있는 페이지의 글자를 새로 인식하는 OCR 엔진은 아니다. 이미지 속 글자가 눈에 잘 보인다는 사실만으로 추출 API가 그 문장을 반환할 수 있는 것은 아니다.

반대로 스캔처럼 보이는 문서에서도 복사가 될 수 있다. OCR 프로그램이 페이지 이미지 뒤에 인식한 텍스트 레이어를 넣은 경우다. 추출기는 그 레이어를 읽을 수 있지만, 거기에 저장된 오인식까지 올바른 문장으로 고쳐 주지는 않는다.

그래서 복사 가능 여부는 첫 단서로만 쓴다. 제목은 선택되지만 본문은 이미지일 수 있고, 배경에 오래된 OCR 문장이 남아 있을 수도 있다. 화면의 문장과 복사한 문장을 대조해야 데이터가 있는 상태와 쓸 수 있는 상태를 구분한다.

이미 정상 텍스트가 있는 페이지를 전부 이미지로 바꿔 다시 인식할 이유도 약하다. 원래 글자 데이터를 버리고 시각적 추정 단계를 추가하기 때문이다. 다만 추출 결과가 깨지는 글꼴·인코딩 등은 별도로 조사할 예외다.

OCR은 이미지의 모양에서 문자를 추정하는 단계다. Tesseract는 그 인식 엔진이고, OCRmyPDF는 PDF 페이지를 처리해 검색 가능한 텍스트 레이어를 붙이는 애플리케이션이다. PDF 입출력 흐름과 이미지 인식 엔진을 구분하면 필요한 도구 범위가 줄어든다.

입력이 낱장 이미지이고 문자 인식 자체를 다뤄야 한다면 Tesseract 문서가 출발점이다. 여러 페이지 PDF의 모양을 유지하며 검색 가능한 사본을 만들려면 OCRmyPDF의 입력·출력과 기존 텍스트 처리 규칙부터 읽는다. 이것은 문서에 따른 역할 구분이며 성능 순위가 아니다.
