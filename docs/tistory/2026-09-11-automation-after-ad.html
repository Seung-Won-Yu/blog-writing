행동 증거: ‘돌렸다’가 아니라 무엇이 끝났는지 본다

첫 층에서는 에이전트의 요약보다 명령, 종료 코드, 실패 로그를 본다. 변경 전 실패가 재현됐는지, 수정 뒤 같은 검사가 통과했는지, 기존 테스트가 그대로 유지됐는지가 최소 조건이다. 실행하지 못한 검사는 미통과가 아니라 미확인으로 구분한다.

REAP 연구는 생산 세션에서 평가 과제를 만들 때 테스트 관련성 검증과 여러 번의 안정성 검사를 추가했다. 실제 개발 프롬프트를 썼다는 사실만으로 평가가 믿을 만해지는 것은 아니며, 흔들리는 환경과 무관한 테스트를 먼저 걸러야 한다는 뜻이다.

상태 증거: 완료 문장보다 화면과 파일을 본다

에이전트가 ‘예약을 만들었다’고 말해도 데이터베이스에 예약이 없으면 결과는 실패다. Anthropic은 평가에서 대화 기록과 최종 상태를 구분한다. 코딩 작업도 같은 원리로 빌드 산출물, 브라우저 화면, 생성 파일, 데이터 상태를 직접 확인해야 한다.

OpenAI의 agent-first 개발 사례도 애플리케이션 UI, 로그, 지표를 에이전트가 직접 읽게 만들었다. 테스트만 추가한 것이 아니라 작업 트리마다 앱을 띄우고 브라우저로 실패와 수정을 재현해 실제 결과를 검증할 수 있게 한 점이 중요하다.

경계 증거: 테스트가 묻지 않은 질문을 한 번 더 낸다

기능 테스트는 정상 흐름에 강하지만 권한 우회, 네트워크 단절, 중간 실패 뒤 롤백, 느린 데이터처럼 비용이 큰 경계를 모두 담지 못할 수 있다. 변경이 닿는 신뢰 경계를 하나 고르고 부정 사례, 정적 분석, 계약 테스트, 실패 주입 중 맞는 검사를 더한다.

검증 층마다 묻는 다른 질문
층질문증거놓치기 쉬운 것
행동검사를 실제로 실행했나명령·종료 코드·로그검사 밖 요구
상태사용자 결과가 남았나화면·파일·데이터드문 경계
경계실패 비용이 큰 조건도 버티나부정 사례·롤백·정적 검사명세에 없는 위험
사람 검토요구와 위험 판단이 맞나독립 리뷰·운영 관찰자동 기준의 편향

형식 검증도 명세의 바깥까지 보증하지 않는다

테스트보다 강한 선택도 있다. Vero는 Lean 4 저장소에서 구현과 증명을 함께 만들게 하고 모든 명세, 빌드, 허용된 공리까지 확인한다. 가장 강한 설정은 코드와 증명 모드에서 43개 저장소 과제 중 27개를 완전히 해결했다.

동시에 이 수치는 형식 검증이 만능이라는 뜻이 아니다. 개별 명세 통과율은 더 높았지만 저장소 전체 완료는 어려웠고, 더 단순하고 증명하기 쉬운 구현이 성능을 희생할 수도 있었다. 증명은 명세가 적은 성질만 보장하므로 명세 품질과 제품 판단은 여전히 남는다.

사람 검토는 마지막에 코드를 전부 다시 쓰는 일이 아니다

사람은 자동 검사가 약한 질문에 집중해야 한다. 요청이 실제 사용자 문제와 맞는지, 데이터와 권한 경계가 적절한지, 되돌리기 비용을 받아들일 수 있는지 본다. 저위험 변경은 표본 검토로 줄이고 고위험 변경은 독립 리뷰를 필수로 둔다.

Anthropic은 코드 기반, 모델 기반, 사람 평가를 조합하고 모델 판정은 사람 기준으로 보정하라고 설명한다. OpenAI도 코딩 에이전트 결과를 사람이 검토하고 배포 전 검증할 것을 권한다. 자동 검토는 사람을 없애는 장치보다 사람이 볼 위치를 좁히는 장치에 가깝다.

근거와 한계: 한 연구의 실패율을 팀의 확률로 쓰지 않는다

Building to the Test는 두 에이전트, 한 UI 재구현 과제, 18회 실행을 다뤘다. Vero는 Lean 4와 형식 명세가 있는 43개 과제다. 두 결과를 일반적인 실패 확률이나 특정 제품의 순위로 옮길 수 없다. 여기서 가져올 수 있는 것은 테스트 신호와 요청 전체를 분리해 보라는 설계 원칙이다.

팀에 도입하려면 실패 비용을 먼저 정한다. 낮으면 테스트와 실제 상태 확인으로 시작하고, 높으면 경계 검사와 독립 리뷰를 더한다. 새로운 운영 실패가 나오면 그 사례를 회귀 테스트로 만들고 검증 사다리의 빈 층을 보강한다.

다음 에이전트 작업에는 테스트 명령과 함께 사용자가 보게 될 최종 상태 한 가지, 실패 비용이 큰 경계 한 가지, 사람이 승인할 지점을 완료 조건으로 적는다.
