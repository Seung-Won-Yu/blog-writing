액션 사용자는 uses 버전부터 줄인다

GitHub는 자사 액션의 최신 버전이 Node 24를 지원한다고 안내한다. 서드파티 액션은 저장소 릴리스와 action.yml을 직접 확인해야 한다. 예를 들어 gitleaks-action은 v3에서 node20을 node24로 바꾸고 의존성을 다시 묶었다고 릴리스에 기록했다.

rg -n 'uses:[[:space:]]+[^ ]+@' .github/workflows
rg -n "using:[[:space:]]*['\"]node(20|24)['\"]" --glob 'action.y*ml' .

메이저 버전을 올릴 때는 입력 이름, 출력 값, 권한 요구, 지원 러너도 함께 비교한다. Node 24 지원 여부만 보고 바로 전체 워크플로에 적용하지 말고, 체크아웃과 캐시처럼 초반에 실행되는 작은 작업에서 먼저 검증한다.

액션 제작자는 action.yml만 바꾸면 끝나지 않는다

GitHub 메타데이터 문서는 JavaScript 액션의 runs.using에 node24를 지정하는 형식을 제공한다. 하지만 TypeScript나 여러 npm 의존성을 쓰는 액션은 보통 빌드 산출물을 저장소에 포함한다. 선언만 바꾸고 예전 번들을 그대로 두면 새 런타임에서 의존성 호환 문제가 뒤늦게 나타날 수 있다.

따라서 의존성을 Node 24에서 설치하고 테스트한 뒤 배포 번들을 다시 만들고, main·pre·post 진입점을 모두 실행한다. 태그가 움직이는 액션이라면 기존 사용자가 받는 릴리스 범위도 확인한다. 이것은 단순 문자열 교체가 아니라 실행물 재검증이다.

셀프 호스티드는 온라인 표시만으로 충분하지 않다

최종 공지는 Node 24가 macOS 13.4 이하와 호환되지 않고 ARM32를 공식 지원하지 않는다고 명시한다. 러너가 온라인이어도 이 운영체제·아키텍처 경계에 걸리면 JavaScript 액션 단계에서 실패할 수 있다. 호스트 버전과 러너 패키지, 컨테이너 이미지를 한 묶음으로 본다.

ARC나 컨테이너형 러너에서는 호스트 패키지와 실제 작업 컨테이너가 보는 externals가 다를 수 있다. 공개 이슈에는 actions-runner 2.336.0 컨테이너 이미지에 node24 디렉터리가 빠져 checkout@v6가 실패한 재현이 기록됐다. 릴리스 번호만 맞다고 가정하지 말고 실제 실행 경로를 확인해야 한다.

공개 이슈의 컨테이너 이미지 누락 사례는 특정 버전과 구성에서 재현된 보고이므로 모든 셀프 호스티드 러너에 일반화할 수 없다. 같은 오류 경로와 이미지 구성이 확인될 때만 참고하고, 최신 이미지의 수정 여부와 릴리스 노트를 다시 본다.

작은 검증 작업이 수정 범위를 지킨다

외부 액션 하나와 간단한 run 단계만 둔 검증 작업을 같은 러너 라벨에서 실행한다. 외부 액션에서만 실패하면 액션 버전이나 번들을, 작업 시작 전 경로 오류가 나면 러너 이미지를 우선 본다. 애플리케이션 테스트까지 들어가기 전에 층을 나누는 것이 핵심이다.

실패 로그의 실행 경로와 액션 메타데이터가 Node 24를 가리키고, 같은 러너의 작은 검증 작업이 통과하면 전환 확인이 끝난다. 그 다음에 원래 워크플로를 되돌려 입력·권한·캐시 차이를 확인한다.

Node 20 종료는 애플리케이션 Node를 한꺼번에 바꾸는 신호가 아니라, 액션 패키지와 러너 실행 환경의 경계를 다시 확인하라는 신호다.

함께 읽기

이어서 보면 좋은 글

  • GitHub Actions 러너 업데이트: 큐 대기 전에 확인할 5곳Node 24 런타임을 확인한 뒤 셀프 호스티드 러너 자체의 버전·연결·라벨 문제를 진단하는 기반 글로 이어진다.
  • GitHub Actions 권한 최소화: GITHUB_TOKEN과 pull_request_target을 분리해야 하는 이유액션 메이저 버전을 바꾼 뒤에도 워크플로 토큰과 신뢰 경계를 다시 확인하는 다음 단계로 이어진다.

Node 20 종료는 워크플로 안에서 node-version: 20을 전부 지우라는 뜻이 아니다. 바뀐 것은 JavaScript 액션을 구동하는 러너 내장 런타임이다. 액션 사용자는 uses: 버전을, 제작자는 action.yml과 배포 번들을, 셀프 호스티드 운영자는 러너·운영체제·내장 런타임을 확인해야 한다. 세 층을 구분하면 애플리케이션 테스트 버전까지 성급히 바꾸지 않고 실패 지점을 좁힐 수 있다. 실패한 작업 하나에서 uses: 목록과 첫 오류 경로를 대조해 액션 버전·액션 번들·러너 환경 중 어느 층의 문제인지 표시한다.
