함수 설명 한 줄을 부탁할 때도, 원인을 모르는 오류를 찾을 때도 같은 AI 모델을 쓰고 있나요? 매번 가장 강한 모델을 고르자니 비용이 신경 쓰이고, 가벼운 모델을 고르자니 다시 시킬 일이 걱정됩니다. 코딩을 돕는 AI 서비스, GitHub Copilot의 자동 모델 선택(Auto)에 선택지가 생겼습니다. 핵심은 모델 이름을 외우는 것이 아니라 이번 일에서 비용과 완성도 중 무엇을 우선할지 정하는 것입니다. 다만 높은 단계를 고른다고 항상 비싼 모델이 호출되는 것은 아닙니다.

선택 기준과 실제 결과의 차이

비싼 모델 고정과 품질 우선 설정을 구분하고 작은 작업의 완료 기준부터 확인합니다.

이번 업데이트에서 달라진 것

Copilot Auto의 세 단계는 비용·품질·응답 시간의 우선순위다. Intelligence에서도 간단한 일에는 작은 모델이 선택될 수 있으며 실제 선택된 모델에 따라 사용량이 계산된다.

GitHub는 2026년 9월 14일 Auto에 Efficiency, Balance, Intelligence 세 단계를 발표했습니다. 각각 비용 우선, 비용·품질·응답 시간의 균형, 복잡한 작업의 품질 우선입니다. VS Code, Copilot CLI, GitHub Copilot 앱에 순차 적용됩니다. 공식 변경 안내

여기서 헷갈리기 쉬운 부분이 있습니다. 세 단계는 서로 다른 모델 꾸러미가 아닙니다. 같은 후보 모델들을 두고 선택의 우선순위를 바꿉니다. Intelligence에서도 간단한 요청에는 작은 모델이 선택될 수 있고, 사용량은 실제 선택된 모델을 기준으로 계산됩니다.

따라서 “Intelligence를 켰으니 무조건 가장 비싼 모델”도, “Efficiency니까 결과는 확인하지 않아도 될 만큼 단순할 것”도 맞는 판단은 아닙니다.

오늘 맡길 일 하나로 고르면 쉽습니다

처음이라면 다음처럼 작업을 나누어 보세요. 아래 구분은 공식 성능 순위가 아니라, 실패했을 때 확인하고 고치기 쉬운지를 기준으로 만든 사용 제안입니다.

  • 가벼운 설명 수정 → Efficiency(비용 우선) — 이미 이해한 함수의 설명 문장을 다듬을 때 시작해 볼 수 있습니다. 결과를 받으면 실제 코드의 동작과 설명이 같은지 확인하세요.
  • 범위가 분명한 기능 수정 → Balance(균형) — 작은 기능을 수정하고 테스트를 추가하는 일입니다. 요청한 범위만 바뀌었는지, 기존 기능도 여전히 작동하는지 확인하세요.
  • 여러 곳이 얽힌 오류 조사 → Intelligence(품질 우선) — 여러 모듈이 관계된 오류의 원인 후보를 비교하는 일입니다. 그럴듯한 답 하나보다 근거와 반례가 제시됐는지 확인하세요.

지금 할 수 있는 확인은 간단합니다.

  • Copilot의 모델 선택 메뉴에서 Auto와 단계 선택이 보이는지 확인합니다. 순차 적용 중이므로 메뉴가 없다고 곧바로 오류로 보지는 마세요.
  • 삭제·배포가 없는 작은 작업 하나를 고릅니다. 예를 들면 기존 함수의 설명 개선입니다.
  • 결과를 원본과 비교합니다. 표현만 좋아졌는지, 존재하지 않는 기능까지 설명했는지 봅니다.

완료 기준은 “답이 왔다”가 아니라 설명이 실제 코드와 일치하고 요청하지 않은 수정이 없는 것입니다. 제품 선택과 별개로, 결과를 검증할 수 있는 작은 일부터 시작하면 판단이 쉬워집니다.

 

단계보다 먼저, 끝났다는 기준을 알려주세요

“이거 개선해 줘”라는 요청은 무엇을 바꿔도 개선이라고 주장할 여지를 줍니다. 모델 단계를 올리기 전에 작업의 끝을 좁혀 주는 편이 좋습니다.

예를 들어 함수 설명을 맡긴다면 이렇게 요청할 수 있습니다.

이 함수의 입력·출력·예외를 설명하는 주석만 다듬어 줘. 실행 코드는 바꾸지 말고, 코드에서 확인할 수 없는 동작은 추측하지 마. 수정한 설명을 실제 코드와 대조해 줘.

오류 조사라면 요청도 달라집니다.

아직 코드는 수정하지 말고 원인 후보를 세 개 이내로 정리해 줘. 각 후보의 근거, 반대 증거, 확인할 테스트를 함께 제시해 줘. 확인된 사실과 추측을 구분해 줘.

이 예시들은 직접 측정한 성능 실험 결과가 아닙니다. 일을 작게 나누고 결과 확인 기준을 붙이는 편집자의 사용 제안입니다. 어떤 단계를 쓰든 로그인 정보, 고객 자료, 공개하면 안 되는 코드를 무심코 포함하지 않는 것도 별도 확인 사항입니다.

Auto가 일을 나눠 맡기는 이유

모델 자동 선택은 식당에서 모든 주문을 가장 오래 걸리는 조리법으로 처리하지 않는 것과 비슷합니다. 중요한 것은 가장 큰 도구를 쓰는 일이 아니라, 요청을 제대로 끝낼 도구를 고르는 일입니다.

GitHub 설명에 따르면 Auto는 작업 복잡성과 모델의 가용 상태를 함께 고려합니다. 사용자가 정한 단계는 그 선택에 방향을 주는 설정이지, 특정 모델을 고정하는 이름표가 아닙니다. Auto 동작 설명

이런 선택 문제는 연구에서도 다룹니다. RouteLLM은 요청에 따라 강한 모델과 더 가벼운 모델을 나누어 사용하면서 비용과 품질의 균형을 찾는 연구입니다. 다만 Copilot이 이 논문의 구현을 사용한다는 뜻은 아니며, 논문의 실험 수치를 Copilot의 절감 효과로 옮겨 쓰면 안 됩니다. RouteLLM 논문

독자에게 필요한 요점은 하나입니다. Auto를 쓴 뒤에도 내가 맡긴 일의 결과가 맞는지는 확인해야 합니다. 자동 선택은 검수의 대체물이 아닙니다.

무엇을 기록하면 내게 맞는 선택인지 알 수 있을까

단계를 바꿀 때마다 막연히 “더 똑똑한 느낌”만 남기면 다시 같은 고민을 하게 됩니다. 다음 세 가지 정도만 기록해 보세요.

  • 처음 요청으로 쓸 만한 결과가 나왔는가.
  • 내가 다시 설명하거나 수정한 부분은 무엇인가.
  • 확인 가능한 사용량과 기다린 시간은 어느 정도였는가.

두 단계를 비교한다면 가능한 한 같은 작은 작업과 같은 완료 기준을 사용하세요. 요청 자체가 다르면 결과 차이가 모델 선택 때문인지 구분하기 어렵습니다. 한 번의 성공이나 실패로 모든 작업에 대한 우열을 정하지 않는 것도 중요합니다.

실무에서는 응답 하나의 비용뿐 아니라 다시 설명하고 고치는 노력도 부담입니다. 그래서 “항상 가장 가볍게”와 “항상 가장 강하게” 사이에 내 작업별 기준이 필요합니다.
