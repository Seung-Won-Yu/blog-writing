SDK를 넣는 선택과 서버를 넣는 선택을 나눈다

LiteLLM의 Ollama 제공자 문서는 Python completion 함수에 모델과 api_base를 전달하는 예를 보여 준다. 여기서는 앱 프로세스 안에서 라이브러리를 사용한다. 여러 제공자의 호출 코드를 정리하려는 목적과 팀의 공통 관문을 운영하려는 목적을 나눠야 한다.

같은 Python 앱이 여러 제공자를 호출하되 별도 서버를 늘리고 싶지 않다면 SDK가 검토 대상이다. 제공자별 기능 차이가 완전히 없어지는 것은 아니다. 실제 앱이 사용하는 매개변수와 응답 처리, 스트리밍 종료와 오류 처리를 확인할 책임은 남는다.

Proxy는 공통 운영 지점이 필요할 때 검토한다

LiteLLM Proxy의 공식 시작 문서는 별도 서버 실행과 호출 경로를 설명한다. 인증·사용량·예산과 모델 라우팅 같은 공통 관리 기능이 필요한 상황에서 검토할 수 있다. 기능을 제공한다는 사실만으로 현재 설정에서 정책이 적용됐다고 판단하지 않는다.

가상의 예로, 개인 문서 요약 앱 하나가 로컬 모델 하나만 사용한다면 별도 관문 없이 직접 연결을 먼저 검토할 수 있다. 반면 여러 앱이 같은 모델 연결 설정을 공유하고 변경 창구를 한곳에 모아야 한다면 Proxy가 해결하는 일이 생긴다. 이는 도입 판단 예시이며 실제 설치 결과나 비용 절감 사례가 아니다.

관문을 추가하면 모델 서버뿐 아니라 관문 프로세스의 상태도 확인해야 한다. 요청이 실패했을 때 앱에서 관문까지 도달했는지, 관문에서 Ollama까지 연결됐는지, 모델이 요청을 처리했는지를 나누어 보게 된다. 이 구조상의 판단은 공식 연결 경로를 엮은 작성자의 해석이다.

연결 오류는 어느 구간에서 났을까?

Proxy를 추가한 뒤 요청이 실패하면 확인할 연결도 두 구간이 된다. 앱에서 관문에 도달했는지와 관문에서 Ollama에 도달했는지를 나누면, 모델을 바꿔도 해결되지 않는 접속 오류를 먼저 구분할 수 있다.

localhost는 요청을 보내는 프로세스가 실행 중인 환경을 가리킨다. 앱과 관문, Ollama가 서로 다른 컴퓨터나 컨테이너에 있다면 같은 문자열을 복사해도 같은 대상이 아니다. 이 글의 선택표를 공용 서버 배포 설정이나 외부 공개 허가로 사용하지 않는다.

문서 비교가 확인한 것과 확인하지 않은 것

2026년 11월 6일 Ollama 호환 API·FAQ와 LiteLLM Ollama 제공자·Proxy 시작 문서 네 곳을 읽었다. 같은 모델을 호출하는 대상, 앱 내부 라이브러리와 별도 프로세스의 경계, 공통 운영 책임을 기준으로 비교했다.

이 글은 Ollama와 LiteLLM 공식 문서 네 곳을 대조한 구조 분석이다. 패키지 설치·모델 다운로드·서버 실행·속도와 비용 측정은 하지 않았다. 실제 요청의 호환성과 공유 배포의 보안 설정은 별도 검증이 필요하다.

기존 역할별 지도는 어떤 도구가 모델 실행·요청 관문·관측을 맡는지 설명한다. 여기서는 모델 실행 도구를 다시 고르지 않고, 이미 쓰는 모델에 연결하는 경로를 좁혔다. 실제 적용 시에는 선택한 경로와 버전을 적고 필요한 요청 기능을 하나씩 확인한다.
