API 응답에서 상태값 하나를 읽으려는데 JSON 라이브러리부터 골라야 하는 순간이 있다. 작은 진단 도구나 단일 파일 스크립트라면 Jackson의 데이터 바인딩까지 필요하지 않아도 의존성 설정은 피하기 어려웠다. OpenJDK는 8월 17일 JEP 540 ‘Simple JSON API’를 JDK 28 대상으로 지정했다. JDK 28에 Simple JSON API가 들어간다

OpenJDK가 외부 의존성 없이 JSON을 파싱하고 생성하는 JEP 540을 JDK 28 대상으로 지정했다.

내장됐지만 기본으로 바로 켜지는 API는 아니다

JEP 540은 상태가 ‘Targeted’, 대상 릴리스가 JDK 28로 바뀌었다. 최종 표준 API가 확정됐다는 뜻은 아니다. 이름 그대로 인큐베이터 모듈이며 사용하려면 컴파일과 실행 때 --add-modules jdk.incubator.json을 명시해야 한다. 실행 시에도 인큐베이터 모듈을 쓴다는 경고가 나온다. API 모양이 피드백에 따라 달라질 수 있으므로 장기 운영 서비스의 공개 계약에 바로 박아 넣기보다 실험과 작은 내부 도구부터 시작하는 편이 맞다.

# 단일 소스 파일 실행
java --add-modules jdk.incubator.json Weather.java

# 컴파일 뒤 실행
javac --add-modules jdk.incubator.json WeatherCheck.java
java --add-modules jdk.incubator.json WeatherCheck

이번 변화가 반가운 곳은 배포 스크립트, 진단 CLI, 테스트 보조 도구처럼 ‘응답에서 값 몇 개만 읽는’ 코드다. 지금은 간단한 작업에도 Maven이나 Gradle에 JSON 의존성을 넣고 버전을 관리해야 한다. JDK 28 환경만 통제할 수 있다면 그 준비가 줄어든다. 반대로 여러 JDK 버전을 지원해야 하는 라이브러리나 안정된 API가 중요한 제품 코드는 인큐베이터가 끝날 때까지 기다릴 이유가 충분하다.

Json.parse 뒤에는 여섯 종류의 값만 남는다

중심에는 JsonValue가 있다. JSON의 문자열·숫자·불리언·null·객체·배열을 각각 대응하는 여섯 하위 인터페이스로 표현한다. Json.parse가 문자열이나 char[]을 읽으면 이 값들로 이루어진 메모리 트리가 만들어진다. 객체에서 키를 찾을 때 get("name"), 배열에서 순서를 찾을 때 get(0), Java 값으로 꺼낼 때 asString()·asInt() 같은 변환 메서드를 사용한다.

import jdk.incubator.json.Json;

String body = """
    {"user": {"name": "Mina", "level": 3}}
    """;

var json = Json.parse(body);
String name = json.get("user").get("name").asString();
int level = json.get("user").get("level").asInt();

System.out.println(name + " / " + level);

경로가 없거나 예상한 형식과 다르면 조용히 null을 돌려주는 대신 JsonValueException이 발생한다. 파싱 자체가 실패하면 JsonParseException에 루트에서 문제 값까지의 경로와 문서 안 위치가 담긴다. 작은 스크립트를 빠르게 쓰되 잘못된 구조를 일찍 드러내려는 설계다. 입력 형식이 자주 바뀌는 API라면 예외를 한꺼번에 잡기보다 선택 값 처리와 타입 분기를 코드에 명시해야 한다.
