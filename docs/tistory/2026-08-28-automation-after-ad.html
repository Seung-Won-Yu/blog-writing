확장자만 믿은 첫 실행은 네 번째 파일에서 멈췄다

처음에는 모든 .pdf를 PdfReader에 넘겼다. 세 정상 파일을 읽은 뒤 네 번째에서 invalid pdf header와 EOF marker not found가 출력됐고, PdfStreamError: Stream has ended unexpectedly로 종료됐다.

종료 코드는 2였다. 예외 처리에서는 임시 파일이 있으면 지우고 최종 이름의 파일도 존재하지 않게 했다. 실패 직후 output_exists는 False였고, 네 입력 파일은 모두 원래 자리에 남았다.

fixture 생성 단계에서도 실패가 한 번 더 있었다. macOS의 AppleSDGothicNeo.ttc가 ReportLab에서 지원하지 않는 PostScript 윤곽으로 판정됐다. AppleGothic.ttf로 바꾸자 합성 PDF가 생성됐다.

글꼴 실패는 병합 도구의 결함이 아니라 테스트 데이터 생성 조건의 문제였다. 그래서 pypdf 실패와 섞어 설명하지 않고, fixture를 만드는 환경이 달라지면 한글 글꼴 경로부터 확인해야 한다는 제한으로 남겼다.

헤더 검사 뒤에는 3쪽과 책갈피 3개가 맞았다

안전 모드에서는 네 입력 중 세 개를 채택하고 04-깨진문서.pdf 한 개를 제외했다. 출력은 3쪽이었고, 다시 PdfReader로 열었을 때 최상위 책갈피도 세 개였다.

merged = PdfReader('업무문서-묶음.pdf')
actual = [
    (item.title, merged.get_destination_page_number(item) + 1)
    for item in merged.outline
    if not isinstance(item, list)
]
expected = [
    ('8월 견적서', 1),
    ('프로젝트 회의록', 2),
    ('출장 영수증', 3),
]
assert len(merged.pages) == 3
assert actual == expected

책갈피 제목은 PDF 메타데이터의 title을 우선하고, 없으면 파일명에서 확장자를 뺀 값을 썼다. 제목이 비어 있는 스캔 문서도 최소한 파일명으로 찾을 수 있게 하기 위한 조건이다.

최종 파일 크기는 58,329바이트였고 SHA-256은 d028710daa98d920cb6e7726c6edf2cf2c2c8a798f55c0995b24e5970e082833이었다. 이 값은 이번 합성 fixture의 결과를 식별하는 용도다.

수동 병합과 이번 자동화의 확인 지점
확인 지점수동 작업자동화 실험
순서파일을 열어 눈으로 확인01·02·03 파일명 정렬
잘못된 입력열리지 않을 때 발견%PDF- 헤더로 사전 제외
탐색페이지를 스크롤문서별 책갈피 생성
실패 복구중간 파일을 직접 정리임시 출력 제거·원본 보존

세 파일처럼 작은 묶음에서는 수동 방식이 더 빠를 수 있다. 자동화의 이점은 파일 수 자체보다 같은 규칙을 매달 반복하고, 제외 목록과 검증 결과를 남겨야 할 때 커진다.

헤더 통과가 안전한 PDF 전체를 보증하지는 않는다

%PDF- 헤더는 첫 번째 문턱일 뿐이다. 파일 끝의 구조가 손상됐거나 교차 참조가 깨졌다면 PdfReader에서 여전히 실패할 수 있다. 이번 코드는 그 실패도 예외로 처리해 최종 파일을 확정하지 않는다.

암호화 문서는 비밀번호가 필요하고, 동적 폼은 같은 필드명이 충돌할 수 있다. 공식 병합 문서도 폼을 합칠 때 top name으로 필드 그룹을 나누라고 안내한다. 전자서명은 병합 과정에서 유효성이 달라질 수 있다.

  • 원본 PDF는 읽기 전용 복사본 폴더에서 시험한다.
  • 파일명 앞 번호가 실제 병합 순서와 맞는지 먼저 확인한다.
  • 제외된 파일 목록을 조용히 버리지 않고 사용자에게 보여 준다.
  • 최종 이름은 페이지·책갈피 검사 뒤에만 확정한다.
  • 암호화·폼·전자서명 문서는 별도 샘플로 보존 여부를 검증한다.
  • 큰 문서는 메모리와 처리 시간을 별도로 측정한다.

공식 문서는 큰 PDF에서 Python 재귀 한도에 닿을 수 있다고 경고한다. 이번 3쪽 실험은 속도나 메모리 비교가 아니다. 수백 쪽 문서에 적용한다면 표본 크기와 실행 시간을 따로 기록해야 한다.

Real Python의 실전 예제도 비용 보고서처럼 여러 PDF를 합치는 장면을 다룬다. 다만 라이브러리 예제의 클래스 이름과 현재 6.16.2 API가 다를 수 있어 실제 구현은 최신 공식 문서를 기준으로 잡았다.

다시 실행할 때 바뀌어야 하는 조건

다음 실행에서는 입력 폴더만 바꾸지 않는다. pypdf 메이저 버전, 암호화 여부, 폼 필드, 전자서명, 문서 크기 중 하나가 달라지면 같은 fixture와 검사 코드를 먼저 다시 돌린다.

실제 업무 폴더에 붙일 때는 파일명을 자동으로 정하는 규칙과 사람이 승인할 지점을 분리한다. 제외 목록, 예상 순서, 최종 페이지 수를 보여 준 뒤 사용자가 확인해야 결과를 배포하는 흐름이 알맞다.

잘 합쳐진 PDF는 파일이 하나라는 뜻만이 아니다. 잘못된 입력을 설명하고, 원하는 문서로 곧바로 이동하며, 실패해도 원본과 최종 이름을 지키는 결과다.
