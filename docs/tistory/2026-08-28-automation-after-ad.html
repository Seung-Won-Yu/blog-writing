매달 반복할 때만 자동화를 쓴다

매달 증빙 열 개를 같은 순서로 묶는다면 화면에서 파일을 정렬하는 일도 반복 노동이 된다. 이때 자동화는 클릭을 줄이는 것보다 규칙을 고정하는 데 의미가 있다. 파일명 앞의 01·02·03을 순서로 사용하고, 열 수 없는 PDF는 제외 목록에 남기며, 정상 문서마다 첫 페이지로 이동하는 책갈피를 만든다.

화면 방식에서 자동화로 넘어갈 기준
확인 질문아니요예
같은 작업이 정기적으로 반복되는가미리보기·PDF24 사용자동화 검토
파일 순서 규칙이 매번 같은가화면에서 직접 정렬파일명으로 고정
잘못된 입력과 책갈피를 함께 확인해야 하는가완성 파일만 확인검증 코드가 유리

세 질문에서 모두 ‘예’일 때 아래 자동화를 고려하면 된다. 한 달에 한 번 파일 두세 개를 합치는 정도라면 화면 방식이 여전히 빠르다. 자동화는 무조건 고급인 방법이 아니라 반복 횟수와 오류 비용이 준비 시간을 넘어설 때 선택하는 도구다.

준비: 복사본과 파일 순서를 만든다

  • Python 3.9 이상이 설치된 Windows 또는 macOS 컴퓨터
  • 원본이 아닌 PDF 복사본 세 개 이상
  • 메모장이나 텍스트 편집기
  • 새로 만든 pdf-merge 작업 폴더

pdf-merge 안에 input-pdfs 폴더를 만들고 복사본을 넣는다. 프로그램은 파일명 순서대로 합치므로 01-견적서, 02-회의록, 03-영수증처럼 앞에 두 자리 번호를 붙인다. 이 이름은 합쳐진 PDF의 왼쪽 책갈피에도 사용된다.

pdf-merge/
├─ merge_pdfs.py
└─ input-pdfs/
   ├─ 01-견적서.pdf
   ├─ 02-회의록.pdf
   └─ 03-영수증.pdf

실행: 긴 코드는 필요할 때만 연다

처음 한 번만 pypdf를 설치하고, 아래 접힌 코드를 열어 전부 복사한 뒤 merge_pdfs.py로 저장한다. 평소 독자는 코드를 읽을 필요가 없다. 입력 폴더와 실행 명령, 결과 파일만 알면 된다. 기존 업무문서-묶음.pdf가 있으면 덮어쓰지 않고 멈추도록 만들었다.

매달 반복할 때 쓰는 전체 자동화 코드 보기
from pathlib import Path
from pypdf import PdfReader, PdfWriter

INPUT_DIR = Path('input-pdfs')
TEMP_FILE = Path('업무문서-묶음.tmp.pdf')
OUTPUT_FILE = Path('업무문서-묶음.pdf')

def has_pdf_header(path):
    with path.open('rb') as file:
        return file.read(5) == b'%PDF-'

valid = []
excluded = []
for path in sorted(INPUT_DIR.glob('*.pdf')):
    if not has_pdf_header(path):
        excluded.append(f'{path.name}: PDF 형식 아님')
        continue
    try:
        reader = PdfReader(str(path))
        valid.append((path, reader.metadata.title or path.stem, len(reader.pages)))
    except Exception as error:
        excluded.append(f'{path.name}: {type(error).__name__}')

if not valid:
    raise SystemExit('합칠 수 있는 PDF가 없습니다.')
if OUTPUT_FILE.exists():
    raise SystemExit('기존 업무문서-묶음.pdf를 다른 곳으로 옮긴 뒤 다시 실행하세요.')

writer = PdfWriter()
page_cursor = 0
for path, title, page_count in valid:
    writer.append(str(path))
    writer.add_outline_item(title=title, page_number=page_cursor)
    page_cursor += page_count

try:
    with TEMP_FILE.open('wb') as output:
        writer.write(output)
    merged = PdfReader(str(TEMP_FILE))
    bookmarks = [item for item in merged.outline if not isinstance(item, list)]
    if len(merged.pages) != page_cursor or len(bookmarks) != len(valid):
        raise RuntimeError('페이지 또는 책갈피 검증에 실패했습니다.')
    TEMP_FILE.replace(OUTPUT_FILE)
except Exception:
    TEMP_FILE.unlink(missing_ok=True)
    raise

print(f'완료: {OUTPUT_FILE} / {page_cursor}쪽 / 책갈피 {len(valid)}개')
if excluded:
    print('제외된 파일:')
    for reason in excluded:
        print(f'- {reason}')

Windows는 명령 프롬프트에서 py를, macOS는 터미널에서 python3를 사용한다. 먼저 pypdf를 설치한 다음 같은 창에서 스크립트를 실행한다. 성공하면 pdf-merge 폴더에 업무문서-묶음.pdf가 생기고 완료 문구에 전체 페이지와 책갈피 개수가 나온다.

# Windows
py -m pip install pypdf==6.16.2
py merge_pdfs.py

# macOS
python3 -m pip install pypdf==6.16.2
python3 merge_pdfs.py

완성 파일은 세 곳만 본다. 첫째, 페이지가 01·02·03 순서인지 확인한다. 둘째, 왼쪽 책갈피를 눌렀을 때 각 문서의 첫 쪽으로 이동하는지 본다. 셋째, 제외된 파일 목록이 나타났다면 그 파일을 직접 열어 실제로 문제가 있는지 확인한다.

결과가 이상하면 여기부터 확인한다

테스트에는 PDF 확장자만 붙인 일반 텍스트 파일을 하나 섞었다. 확장자만 믿고 합치면 네 번째 파일에서 작업이 멈췄지만, 자동화는 실제 PDF 헤더와 열기 가능 여부를 먼저 확인해 그 파일을 제외하고 정상 문서 세 개만 합쳤다. 오류가 나도 임시 결과를 지우고 입력 복사본은 그대로 남긴다.

  • 순서가 틀리면 파일명 앞의 01·02·03을 고치고 다시 실행한다.
  • 기존 업무문서-묶음.pdf가 있다는 메시지는 이전 결과를 다른 곳으로 옮긴 뒤 해결한다.
  • 제외 목록의 파일은 확장자만 바꾸지 말고 원본 프로그램에서 PDF로 다시 저장한다.
  • 암호·전자서명·입력 양식이 있는 문서는 복사본에서 보존 여부를 별도로 확인한다.

Mac 미리보기와 PDF24에서도 원칙은 같다. 원본이 아니라 복사본에서 시작하고, 결과를 새 이름으로 저장하며, 전달 전에 문서 경계를 확인한다. 자동화가 실패하면 원인을 고친 뒤 입력 복사본에서 다시 시작한다. 실패한 중간 파일을 정상 결과처럼 이어 쓰지 않는다.

개발 기록: 어디까지 직접 확인했나

Mac 미리보기의 순서와 원본 자동 저장 주의점은 Apple 공식 사용 설명서로 확인했다. PDF24 Creator가 Windows 10·11에서 오프라인으로 작동하고 파일을 PC에 유지한다는 내용도 PDF24 공식 안내를 기준으로 정리했다.

PDF24의 드래그 앤 드롭 병합과 페이지 정렬 역시 공식 기능 설명을 확인했다. 이 두 화면 방식은 이번 로컬 실험의 성능 비교 대상이 아니라, 독자가 가장 쉬운 선택지를 먼저 고르도록 설명하기 위한 공식 사용법이다.

자동화는 실제 업무 문서 대신 제목만 있는 1쪽짜리 견적서·회의록·영수증과 이름만 PDF인 잘못된 파일을 만들어 실행했다. Python 3.9.6과 pypdf 6.16.2에서 네 입력 중 정상 세 개가 3쪽으로 합쳐졌고 책갈피 세 개의 이동 위치도 일치했다.

파일 이름만 바꾼 일반 텍스트는 병합 전에 제외됐고, 오류 시 임시 결과가 제거되는 것도 확인했다. 암호화 PDF, 전자서명 문서, 입력 양식, 수백 쪽짜리 큰 파일은 시험하지 않았다. 이런 문서는 어떤 방법을 쓰든 원본 보존과 결과 검증을 별도로 해야 한다.

좋은 자동화 글은 코드가 긴 글이 아니라, 독자가 가장 쉬운 해결책을 먼저 고르고 반복이 생겼을 때만 한 단계 더 갈 수 있는 글이다.
