AI 에이전트에게 코드 리뷰 기준, 문서 형식, 배포 확인 순서를 매번 다시 설명하다 보면 프롬프트가 업무 매뉴얼처럼 길어진다. Agent Skills는 이 반복을 줄이기 위해 작업 지침과 참고자료, 필요하면 실행 스크립트까지 폴더 하나로 묶는 방식이다. 다만 프롬프트나 MCP를 대신하는 만능 기능은 아니다. 네 도구의 경계를 알아야 필요한 곳에만 스킬을 쓸 수 있다.

Agent Skills는 어디에 쓰일까: 프롬프트·MCP와의 차이

반복되는 전문 절차는 스킬로, 한 번성 요청은 프롬프트로, 외부 도구 연결은 MCP로 나누면 AI 에이전트의 작업 구조가 선명해진다.

프롬프트를 잘 써도 같은 설명이 반복되는 이유

코드 리뷰를 맡길 때는 보안·성능·테스트 기준을 붙이고, 보고서를 만들 때는 제목 구조와 표 형식을 다시 적는다. 한 번은 괜찮지만 같은 설명을 세 번째 붙여 넣는 순간부터 프롬프트는 질문이 아니라 복사해 쓰는 업무 매뉴얼이 된다.

Agent Skill은 바로 그 매뉴얼을 파일로 분리한다. 특정 업무가 들어왔을 때만 절차를 읽고, 필요한 참고자료와 스크립트를 함께 사용한다. 프롬프트를 없애는 기능이 아니라 프롬프트에 매번 붙이던 반복 절차를 재사용 가능하게 만드는 장치에 가깝다.

프롬프트·상시 지침·Agent Skill·MCP를 고르는 기준
방식가장 잘 맞는 일적용 범위예시
프롬프트지금 한 번의 요청현재 대화·작업이 함수 이름을 바꿔 줘
상시 지침늘 지킬 기본 원칙모든 관련 작업한국어로 답하고 기존 포맷 유지
Agent Skill반복되는 전문 절차관련 작업일 때만코드 리뷰·문서 제작·배포 점검
MCP외부 도구·데이터 연결연결된 시스템GitHub·DB·업무 도구 조회

GitHub 문서도 간단하고 늘 관련되는 규칙은 사용자 지정 지침에, 자세하고 특정 작업에서만 필요한 절차는 스킬에 두는 방향을 설명한다. MCP는 다른 축이다. 도구에 닿는 연결을 제공하고, 스킬은 그 도구를 어떤 순서와 기준으로 쓸지 가르칠 수 있다.

Agent Skill은 폴더 하나로 시작한다

공식 명세에서 스킬의 최소 단위는 디렉터리와 SKILL.md 파일 하나다. SKILL.md 앞부분에는 이름과 설명을 넣고, 본문에는 단계·예시·예외처럼 에이전트가 따라야 할 지침을 쓴다. 거대한 플러그인이나 별도 서버가 필수인 구조가 아니다.

scripts에는 반복 실행할 코드를, references에는 세부 문서나 도메인 지식을, assets에는 템플릿과 이미지·스키마를 둘 수 있다. 지침만으로 충분한 스킬은 SKILL.md 하나로 끝내도 된다. 파일이 많을수록 좋은 것이 아니라 작업에 필요한 근거가 제자리에 있는지가 중요하다.

 

모든 지침을 한꺼번에 읽지 않는 구조

설치한 스킬이 많아지면 매번 모든 문서를 읽느라 대화 공간을 낭비할 것 같지만, 공식 명세는 점진적 공개를 기본 원리로 둔다. 시작할 때는 각 스킬의 이름과 설명만 보고, 관련 작업이라고 판단한 뒤에야 SKILL.md 전체를 읽는다.

세 번째 단계에서 scripts·references·assets를 필요한 만큼만 연다. 그래서 좋은 description은 소개 문구가 아니라 호출 조건이다. 무엇을 하는지와 언제 써야 하는지가 구체적일수록 엉뚱한 작업에서 켜지거나 필요한 순간에 빠질 가능성을 줄일 수 있다.

공개 스킬은 개발 과정의 어디에 쓰일까

OpenAI는 Codex 스킬의 예로 디자인 구현, 프로젝트 관리, 클라우드 배포, 이미지 생성, API 개발, PDF·스프레드시트·문서 제작을 제시한다. 내부에서는 평가 실행, 학습 작업 점검, 문서 초안, 성장 실험 보고처럼 반복되지만 팀별 기준이 필요한 일에도 활용한다고 밝혔다.

개발 단계별로 스킬이 값을 만드는 자리
단계스킬에 담을 것얻는 효과
기획·조사출처 우선순위·비교 기준·산출물 형식조사 범위와 근거가 흔들리지 않는다
구현프로젝트 규칙·디자인 자료·완료 조건코드 생성보다 앞선 판단을 재사용한다
검토·테스트확인 순서·위험 기준·회귀 테스트리뷰마다 빠지는 항목을 줄인다
문서·보고독자 수준·문서 구조·렌더 검증팀이 원하는 형식을 반복해서 맞춘다
배포·운영사전 점검·승인 경계·실패 대응실행 전후의 확인 절차를 고정한다

GitHub Copilot은 클라우드 에이전트, 코드 리뷰, CLI, 앱, VS Code와 JetBrains의 에이전트 모드에서 스킬을 지원한다고 안내한다. 프로젝트 스킬은 저장소 안에 두어 팀과 함께 버전 관리하고, 개인 스킬은 여러 프로젝트에서 공통으로 사용할 수 있다.

  • 프로젝트 전용: .github/skills, .claude/skills, .agents/skills
  • 개인 공통: ~/.copilot/skills 또는 ~/.agents/skills
  • 재사용할 기준은 저장소에 넣어 변경 이유와 검토 이력을 남긴다.
  • 한 제품에서만 쓰는 선택 필드는 다른 에이전트에서도 같은 방식으로 동작한다고 가정하지 않는다.

좋은 스킬은 설명보다 경계가 분명하다

좋은 스킬은 지시를 많이 담은 스킬이 아니다. 언제 시작하고 무엇을 입력으로 받으며 어디까지 끝내는지가 분명하다. 실패하면 멈출 조건과 사용자의 확인이 필요한 지점을 써 두어야 에이전트가 스스로 범위를 키우는 일을 줄일 수 있다.

  • description에 무엇을 하고 언제 쓰는지 함께 적는다.
  • 입력·작업 순서·완료 조건·실패 시 중단 조건을 분리한다.
  • 긴 배경지식은 references로 옮기고 한 파일에는 한 주제만 둔다.
  • scripts의 의존성과 오류 메시지를 확인하고 작은 입력으로 먼저 검증한다.
  • assets의 템플릿과 예시는 실제 결과 형식과 맞는지 렌더링해 본다.
  • 명령 실행과 네트워크 접근은 작업에 필요한 최소 범위만 허용한다.

Anthropic은 대표 입력으로 먼저 평가해 부족한 부분을 찾은 뒤 스킬을 점진적으로 만들라고 권한다. 처음부터 모든 예외를 담으려 하면 긴 매뉴얼만 생긴다. 실제 작업에서 반복된 성공 방법과 자주 난 실수를 기록하고, 필요할 때 참고 파일을 나누는 편이 유지하기 쉽다.

남의 스킬을 바로 설치하면 안 되는 이유

공개 스킬은 읽을 수 있는 파일이라는 장점과 실행 가능한 지침이라는 위험을 함께 가진다. GitHub는 프롬프트 인젝션·숨은 지침·악성 스크립트를 경고한다. 327개 공개 스킬을 분석한 2026년 연구도 저장소 등록부터 실행·업데이트까지 여러 단계의 위험을 따로 점검해야 한다고 제안한다.

공개 Agent Skill 설치 전 다섯 가지 질문
확인 질문괜찮은 신호멈춰야 할 신호
출처와 라이선스가 보이는가공식 문서·공개 이력·명확한 라이선스작성자·버전·배포 경로가 불명확
SKILL.md를 먼저 읽었는가목적·범위·중단 조건이 구체적다른 지침을 무시하라는 문구
스크립트를 검토했는가의존성과 입출력이 작고 명확원격 코드 다운로드·광범위한 파일 접근
권한이 최소한인가필요할 때 사용자 확인shell·bash를 이유 없이 사전 승인
작은 입력으로 시험했는가복사본·샌드박스에서 결과 확인실제 저장소나 운영 데이터에 바로 실행

allowed-tools는 명세에서도 실험적 필드이며 구현마다 지원이 다를 수 있다. 특히 shell이나 bash를 미리 허용하면 확인 단계가 사라질 수 있다. 외부 스킬은 설치 파일 전체와 의존성, 네트워크 연결을 읽고 복사본 환경에서 시험한 뒤 범위를 넓히는 편이 안전하다.

프롬프트가 ‘이번에 무엇을 할까’를 묻는다면, 스킬은 ‘이 일을 우리 방식으로 어떻게 끝낼까’를 기록한다.

Agent Skills의 핵심은 에이전트를 갑자기 더 똑똑하게 만드는 데 있지 않다. 반복해서 설명하던 일의 순서와 판단 기준을 검토 가능한 파일로 남기고, 필요한 순간에만 불러오게 만드는 데 있다. 프롬프트는 지금의 요청, 상시 지침은 늘 지킬 원칙, MCP는 외부 도구와의 연결이다. 이 세 가지 사이에 반복되는 전문 절차가 생겼을 때 스킬이 가장 큰 값을 한다. 새 스킬을 찾기 전에 최근 한 달 동안 AI에게 세 번 이상 반복한 업무 하나를 고르고, 입력·작업 순서·성공 확인·실패 시 중단 조건을 네 줄로 먼저 적어 본다.
