콘솔에서 만든 S3 버킷을 인수했는데 팀 저장소에는 그 버킷을 설명하는 코드가 없다. IaC Generator는 AWS에서 읽은 설정으로 템플릿을 만든다. 이 파일로 기존 버킷을 관리하려면 가져오기 전에 실물 이름과 읽지 못한 값을 확인해야 한다. 첫 버킷을 기준으로 어디서 멈추고 무엇을 확인할지 잡아 보자.

IaC Generator에서 기존 버킷의 실물 매핑과 편입 뒤 검증

부분 스캔으로 생성한 템플릿을 검토하고 기존 실물 식별자를 스택에 연결하는 과정의 확인 기준을 정리한다.

버킷 하나부터 관리 주체를 확인한다

IaC Generator로 템플릿을 만든 뒤 실제 리소스와 대조한다. CloudFormation 관리로 옮기려면 검토한 IMPORT 변경 세트를 별도로 실행해야 한다.

콘솔에서 만든 버킷을 인수했다면 먼저 이름과 소유 계정을 기록한다. 다른 팀의 스택이나 Terraform 상태가 이미 이 버킷을 관리한다면 새 관리 주체를 추가하는 작업부터 멈춘다. 전환이 필요하면 담당자와 기존 관리 경계를 정리해야 한다.

  • 대상 리소스의 계정·리전·종류와 실물 식별자를 기록하고 기존 관리 도구가 있는지 확인한다.
  • 스캔 범위를 좁혀 템플릿을 만들고 읽지 못한 값과 관련 리소스 제안을 검토한다.
  • IMPORT 변경 세트에서 템플릿 이름과 실물 식별자가 일치하는지 대조한다.
  • 편입 뒤 같은 식별자를 확인하고, 지원되는 속성의 차이를 다음 배포 전에 검토한다.

연습 대상으로는 사용처와 담당자가 분명한 비운영 리소스 하나를 고른다. CloudFormation 콘솔의 IaC generator에서 Resource scans로 들어가 스캔을 시작한다. 부분 스캔에서는 리소스 종류를 좁힐 수 있다. 계정과 리전부터 맞추고, 조회 권한과 지원 유형도 확인한다.

스캔 목록과 템플릿 경고를 따로 읽는다

스캔에서 버킷을 선택한 뒤 관련 리소스 제안을 검토한다. 제안된 정책이나 연결 리소스의 관리 주체가 다르면, 같은 스택으로 편입할 이유부터 확인한다. 목록에 대상이 없으면 리전, 읽기 권한, 지원 유형을 먼저 점검한다.

템플릿에 경고가 있으면 논리 ID를 기준으로 대상을 찾는다. 예를 들어 Lambda 배포 코드처럼 서비스가 읽기 요청에 돌려주지 않는 값은 생성기가 채울 수 없다. 필요하면 승인된 배포 정의에서 값을 확인하고, 출처를 확인할 수 없으면 해당 리소스의 가져오기를 보류한다. 공식 화면의 Code/S3Bucket과 Code/S3Key는 함수 배포 파일이 저장된 위치를 다시 확인하라는 단서다.

생성된 템플릿을 검토할 때
확인한 상태다음 행동
스캔에 대상 없음계정·리전·조회 권한·지원 유형을 다시 확인한다.
읽을 수 없는 속성 경고승인된 구성에서 필요한 값을 확인하고 초안에 반영한다.
이미 다른 도구가 관리소유권 이전을 합의할 때까지 가져오기를 멈춘다.

논리 ID와 버킷 이름을 한 줄로 맞춘다

가상 예에서 템플릿의 논리 ID는 ArchiveBucket, 실물 버킷 이름은 archive-team-sandbox-example이다. 수동 가져오기에서 AWS::S3::Bucket의 식별자 속성으로 BucketName을 고르고, 그 값에 실물 버킷 이름을 넣는다. 이름이 비슷한 다른 버킷과 연결되지 않는지 확인한다.

가져올 리소스에는 DeletionPolicy가 필요하다. 예를 들어 Retain은 해당 삭제 정책이 적용되는 스택 삭제나 템플릿 제거 시 실물을 남긴다. 교체 시 정책과는 별개이므로 향후 업데이트의 교체 가능성도 따로 확인한다.

변경 세트의 실행 버튼 앞에서 멈춰 본다

기존 스택에 가져올 때는 현재 스택 정의를 포함한 전체 템플릿을 준비한다. 변경 세트 종류는 IMPORT로 고르고, 이번에 연결할 리소스만 목록에 있는지 검토한다. 기존 리소스의 속성 변경이나 새 리소스 생성은 별도 변경으로 분리한다.

CloudFormation은 실물 존재와 템플릿의 속성 형식 등을 검사하지만, 템플릿에 적은 구성이 실물 설정과 모두 같은지는 확인하지 않는다. 승인 전에 버킷 버전 관리처럼 팀이 유지해야 하는 값을 서비스 콘솔의 실제 설정과 대조한다.

Terraform이 관리하는 리소스라면 상태에 어떤 주소로 등록돼 있는지도 확인한다. HashiCorp 문서 역시 가져오기를 구성과 별도로 다룬다. 운영 중인 리소스를 두 도구가 동시에 변경할 수 있게 두면 다음 배포에서 어느 쪽의 설정이 적용될지 관리하기 어렵다.

편입 성공 뒤 같은 실물인지 확인한다

승인 후 IMPORT_COMPLETE가 나오면 스택의 리소스 탭에서 ArchiveBucket의 물리 ID를 찾는다. 기록한 버킷 이름과 같아야 한다. 그 뒤 드리프트 감지로 지원되는 속성을 비교하고, 감지 범위에 없는 속성은 서비스 화면이나 승인된 설정 기록에서 확인한다.

불일치가 나오면 다음 스택 업데이트를 보류한다. 지금 실물을 기준으로 템플릿을 고칠지, 별도 변경으로 실물을 수정할지 담당자와 결정한다. 가져오기 자체가 롤백된 경우에는 이벤트에서 실패 원인과 현재 관리 상태를 확인한 뒤 다시 시도한다.

다음 배포에 남길 기록

첫 편입 기록에는 실물 식별자, 연결할 스택, 검토한 변경 세트, 아직 비교하지 못한 속성을 함께 적는다. 다음 담당자는 이름이 같은 다른 버킷을 조회했거나 지원되지 않는 속성을 확인된 값으로 오해하지 않고 이어서 검토할 수 있다.

파일 생성, 실물 연결, 편입 후 구성 확인을 세 단계로 나누면 YAML을 받았다는 사실이나 IMPORT_COMPLETE만으로 작업을 닫는 실수를 줄일 수 있다.

공개 AWS 문서를 비교해 작성했다. 버킷 이름은 가상 예시이며 실제 AWS 계정에서 스캔이나 가져오기를 실행하지 않았다.

운영 중인 리소스를 코드로 관리하기 시작하는 날에는 기능 변경을 함께 넣지 않는 편이 추적하기 쉽다. 먼저 편입할 리소스의 이름과 관리 주체를 기록하고, 아직 확인하지 못한 설정이 있다면 다음 변경을 승인하기 전에 해소한다. 그래야 이후 스택 변경에서 예상 밖 차이가 생겼을 때 어디부터 확인할지 남는다. 스택에서 기존 버킷과 같은 물리 ID를 확인하고, 지원되는 속성의 드리프트와 확인할 수 없었던 값을 기록하면 첫 편입 검토가 끝난다.
