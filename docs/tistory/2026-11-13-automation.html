TypeScript 7 ESLint 전환: 방치한 Promise를 CI에서 확인하는 법

TypeScript 7을 CI에 추가할 때 기존 타입 기반 ESLint가 방치된 Promise를 검출하는지 정상·위반 입력으로 판단한다.

CI에서 타입 검사와 린트의 역할을 나눈다

TypeScript 7 타입 검사와 기존 ESLint를 별도 작업으로 실행한다. Promise를 처리한 입력과 처리하지 않은 입력을 같은 설정으로 비교해, 후자에만 지정한 규칙 ID가 나오는지 확인한다.

타입 검사는 코드의 타입 관계가 맞는지 확인한다. 타입 기반 린트는 타입 정보를 써서 팀이 금지한 패턴도 찾는다. 함수가 Promise를 반환할 때 그 결과를 쓰지 않는 호출은 타입상 유효할 수 있다. 방치한 호출을 찾아내려면 해당 린트 규칙이 활성화돼 있어야 한다.

  • CI가 실행하는 타입 검사 명령과 ESLint 명령을 각각 찾는다.
  • 정상 입력과 위반 입력을 같은 린트 설정과 TypeScript 프로젝트에 넣는다.
  • 위반 입력의 규칙 ID와 CI 종료 상태를 확인한 뒤 전환 범위를 정한다.
같은 커밋에서 남길 두 가지 합격 신호
CI 작업무엇을 확인할까
TypeScript 7 타입 검사선택한 tsconfig로 검사하고 기존에 기대한 타입 진단과 비교한다.
타입 기반 ESLint위반 입력에서 지정한 규칙 ID를 확인하고 정상 입력에서는 그 ID가 없어야 한다.

ESLint가 불러오는 TypeScript를 먼저 확인한다

Microsoft의 TypeScript 7.0 안내에는 7.0 CLI와 기존 API를 요구하는 도구를 병행하는 예가 있다. 예제는 npm 별칭으로 7.0 CLI 패키지와 기존 API 패키지의 설치 이름을 분리한다. 기존 도구가 typescript라는 이름으로 패키지를 찾는다는 점이 중요하다.

모노레포라면 루트 선언만 읽고 끝내지 말자. 린트 명령이 실행되는 워크스페이스의 의존성 선언과 lockfile을 확인한다. 7.0 발표에 나온 예제를 옮길 때도 정확한 버전과 린터 지원 범위를 먼저 확인한다.

이 글을 작성할 때 typescript-eslint의 지원 문서는 TypeScript 6.1 미만을 지원 범위로 명시했다. 7.1 베타의 새 API를 확인했다면, 사용하는 린터가 그 API를 지원하는지도 별도로 확인한다.

한 줄만 다른 Promise 입력을 고른다

기존 CI가 린트하는 테스트 경로에서, 호출 대상의 반환 타입이 Promise라고 알 수 있는 작은 입력을 고른다. 가상의 함수 sendReceipt가 Promise<void>를 반환하고 호출 지점은 async 함수 안이라고 가정한다. 아래 표는 팀의 실제 설정으로 대조할 예시다.

정상 입력과 위반 입력의 예상 차이
입력기대하는 린트 결과
await sendReceipt()이 호출에서 no-floating-promises가 나오지 않는다.
sendReceipt()이 호출에서 @typescript-eslint/no-floating-promises가 나온다.

함수와 파일 위치, 설정을 그대로 두고 await의 유무만 바꾼다. 처음부터 여러 규칙을 동시에 건드리면 린트가 실패했을 때 어느 규칙이 반응했는지 판단하기 어렵다. 두 입력의 결과와 실행한 커밋을 같이 기록한다.

린트가 실패한 이유까지 읽는다

파일이 ignore에 걸리거나 프로젝트에 포함되지 않으면, 원하는 규칙까지 도달하지 못할 수 있다. 파서 오류만 나왔다면 설정을 먼저 바로잡는다. projectService를 쓰는 구성에서는 대상 파일이 어느 tsconfig에 속하는지 확인한다.

CI에서 보이는 결과다음에 확인할 곳
둘 다 깨끗하게 통과파일 제외, 규칙 활성화, 호출의 실제 반환 타입을 확인한다.
둘 다 파서 오류린터가 읽은 TypeScript 버전과 tsconfig 포함 범위를 확인한다.
위반이 경고로만 기록팀이 차단 규칙으로 운영한다면 규칙 심각도와 CI의 경고 처리 조건을 확인한다.
위반 입력에서 해당 규칙 ID로 실패정상 입력도 확인한 뒤 기존 린트 게이트가 동작했다고 기록한다.

CI 작업별로 전환 결정을 남긴다

공식 문서를 대조한 이 글의 판단은, 타입 검사기와 린트의 합격 조건을 분리하면 어느 작업을 전환하고 어느 작업을 유지할지 커밋 단위로 결정할 수 있다는 것이다.

가령 TypeScript 7의 진단이 기대와 같고, 기존 ESLint가 정상 입력을 통과시키면서 위반 입력에 지정 규칙 ID를 남겼다면 컴파일러 작업부터 바꿀 근거가 생긴다. 린트에서 실패하면 의존성이나 파일 범위를 확인하고 기존 린트 설정을 유지한다.

위반 입력은 임시 브랜치나 별도 검증 단계에서만 확인한다. 마지막에는 입력을 원래 상태로 돌리고, 평소 CI가 사용하는 명령으로 타입 검사와 린트가 모두 통과하는지 확인한다.

근거와 한계

정상 입력에 지정 규칙 ID가 없고 위반 입력에는 해당 ID와 차단 상태가 남으며 TypeScript 7 타입 검사 결과가 별도로 기록된다.

2026년 11월 13일에 공식 문서 다섯 곳을 대조했다. 예제는 판정 기준을 설명하는 입력이며 실제 패키지 설치, 린트 실행, CI 시간 측정은 하지 않았다.

이 판정은 선택한 Promise 규칙과 파일에 한정된다. 프레임워크 플러그인이나 별도 tsconfig를 쓰는 워크스페이스는 해당 작업이 읽는 설정으로 각각 확인한다. 린터가 새 TypeScript API 지원을 발표하면 지원 버전과 규칙 결과를 다시 확인한다.
