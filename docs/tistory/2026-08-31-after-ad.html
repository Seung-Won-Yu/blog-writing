업데이트 대상은 설치 파일이 아니라 소유 경로다

일반 고정 서버에서 자동 업데이트가 켜져 있으면 러너는 작업을 받을 때 또는 릴리스 뒤 일정 기간 안에 자체 갱신한다. Runner_와 SelfUpdate 로그에서 성공 흔적을 확인한다. 서비스는 켜져 있지만 업데이트 서비스에 닿지 못하는 방화벽 구성도 함께 본다.

config.sh --disableupdate로 자동 업데이트를 끈 환경은 운영자가 릴리스 캘린더를 소유해야 한다. 고정 서버는 패키지를 교체하고 서비스를 다시 올리지만, 불변 컨테이너와 ARC는 실행 중인 컨테이너 안에서 고치지 않는다. 베이스 이미지의 러너 버전을 올려 새 이미지를 배포한다.

러너 패키지만 바꿔도 운영체제, Docker, 언어 런타임, 캐시는 자동으로 갱신되지 않는다. 러너 호환성 복구와 호스트 이미지 유지보수를 한 작업으로 뭉치면 실패 범위가 커진다. 두 변경을 분리하고 각자 검증·되돌림 기준을 둔다.

작은 검증 작업이 업데이트 완료를 결정한다

대규모 러너 풀을 한 번에 바꾸지 않는다. 같은 라벨을 가진 러너 중 하나를 교체하고, 체크아웃·캐시·아티팩트 업로드·컨테이너 실행처럼 실제 팀이 쓰는 경로를 포함한 짧은 검증 워크플로를 보낸다. 단순 echo 성공만으로는 부족하다.

완료 신호는 새 버전 표시, Idle 연결, 검증 작업 배정, 작업 로그, 결과 업로드까지 이어지는 것이다. 기존 러너를 바로 지우지 말고 새 경로가 한 번 이상 성공할 때까지 드레인 상태로 둔다. 실패하면 이전 패키지나 이미지 다이제스트로 돌아간다.

brownout 중 간헐적으로만 실패했다면 한 번의 성공을 정상 판정으로 삼지 않는다. 공지된 시간대와 이후에 같은 검증 작업을 반복해 등록과 실행 경로를 나눠 본다. GitHub 전체 장애 여부도 상태 페이지에서 확인해 로컬 러너 문제와 섞지 않는다.

30일 규칙을 자산 캘린더로 바꾼다

릴리스 알림만 구독하고 담당자가 없으면 30일은 금방 지난다. 러너 이름, 현재 버전, 자동 업데이트 여부, 패키지·이미지 저장소, 소유 팀, 마지막 검증 시각을 자산 목록에 남긴다. 새 릴리스가 나오면 목록과 실제 버전을 비교하는 정기 작업을 연다.

  • 저장소·조직·엔터프라이즈 범위의 러너를 모두 목록화한다.
  • 2.329.0 등록 하한과 새 릴리스 뒤 30일 실행 조건을 구분한다.
  • 자동 업데이트를 끈 서버와 컨테이너·ARC 이미지의 소유자를 지정한다.
  • Runner_·SelfUpdate 로그를 외부에 보존하고 실패 알림을 연결한다.
  • 새 패키지나 이미지는 한 러너에서 실제 검증 작업을 거친 뒤 넓힌다.
  • 이전 패키지·이미지 다이제스트·chart 조합을 되돌림 경로로 보존한다.

GitHub Enterprise Server는 github.com의 brownout 일정과 같은 기준으로 단정하면 안 된다. 사용하는 GHES 버전의 릴리스 문서가 요구하는 러너 버전을 따로 확인한다. Enterprise Cloud와 GHES를 함께 운영하면 자산 목록에서도 두 경계를 분리한다.

운영 목표는 모든 러너가 항상 최신이라는 문구가 아니다. 새 릴리스가 나온 뒤 누가 어디를 바꾸고, 무엇으로 정상 동작을 증명하며, 실패하면 어떤 패키지나 이미지로 돌아가는지가 30일 안에 실행되는 상태다.

러너의 온라인 상태는 현재 연결을 보여 주고, 업데이트 캘린더는 다음 작업도 받을 수 있게 만든다.

함께 읽기

이어서 보면 좋은 글

  • GitHub Actions 권한 최소화: GITHUB_TOKEN과 pull_request_target을 분리해야 하는 이유러너를 최신으로 유지한 뒤에도 워크플로와 토큰 권한을 분리해야 셀프 호스티드 실행 환경의 위험 범위를 줄일 수 있다.
  • Dependabot 3일 쿨다운: 일반 업데이트와 보안 업데이트 차이, 설정법까지새 릴리스를 놓치지 않되 검증 시간을 확보하는 업데이트 캘린더를 코드 의존성 관리에도 이어 적용할 수 있다.

셀프 호스티드 러너의 초록 상태등은 프로세스가 연결됐다는 뜻이지, 앞으로도 계속 작업을 받을 수 있다는 보증이 아니다. 등록 하한과 실행 유효 버전을 분리해 보고, 자동 업데이트 여부와 이미지 소유자를 자산 목록에 함께 적어야 한다. 릴리스 알림부터 작은 검증 작업, 교체와 되돌림까지 한 주기로 묶으면 큐 대기는 갑작스러운 장애가 아니라 미리 발견할 수 있는 운영 신호가 된다. 오늘 조직의 러너 목록에서 이름·상태·버전·자동 업데이트 여부·이미지 소유자를 한 번에 적고, 30일 안에 갱신되지 않는 경로를 업데이트 작업으로 등록한다.
