로컬에서는 설치되는데 클라우드 빌드에서만 의존성 설치가 막힌다. Workers Builds npm 버전은 10월 23일 변경 이후 packageManager에 정확한 버전을 적어 지정할 수 있다. 다만 engines.npm이나 잠금 파일 하나만 믿어서는 설치 환경이 맞았는지 알 수 없다. npm 프로젝트를 배포하는 개발자라면 설정을 바꾸기 전에 실패 단계와 실제 사용 버전부터 대조하자.

IT 트렌드 해설

30초 요약

  • Workers Builds npm은 packageManager로 정확한 버전을 고른다. engines.npm과 잠금 파일은 맡는 일이 다르다.
  • 실패 단계와 버전 로그를 보존하고 검증용 브랜치에서 한 가지 조건씩 바꾼다.
  • 버전 고정은 잠금 파일 불일치나 모든 설치·배포 오류를 해결하지 않는다.

Workers Builds에서 npm 버전을 지정할 때 나눠 확인할 세 경계

새 버전 선택 기능을 engines.npm·빌드 루트·잠금 파일·npm ci의 조건과 연결해, 설치 실패를 안전하게 좁히는 판단 기준을 제공한다.

설치 오류라면 실제 npm 버전부터 대조한다

Workers Builds npm 버전은 package.json의 packageManager에 정확한 버전을 적어 지정한다. engines.npm만으로는 선택되지 않으며, 설치 도구를 고르는 잠금 파일도 따로 확인해야 한다.

  • 실패한 빌드의 의존성 설치 단계와 실제 npm·Node 버전을 확인한다.
  • 프로젝트 루트의 packageManager와 저장소 최상위의 같은 필드가 일치하는지 읽는다.
  • 선택한 npm의 정확한 버전과 npm용 잠금 파일을 함께 검토한다.
  • 검증용 브랜치에서 설치 로그·테스트·변경 파일을 대조한 뒤 적용 범위를 정한다.

대상은 Cloudflare의 Git 연결 빌드인 Workers Builds에서 npm 설치를 관리하는 개발자다. GitHub Actions에서 직접 배포하거나 로컬에서 Wrangler만 실행한다면 그 환경의 설치 설정을 따로 확인한다. Worker 실행 중의 오류도 이번 변경과 다른 경계다.

10월 23일 공식 발표는 의존성을 설치하기 전에 지정한 npm 버전을 설치한다고 설명한다. 로컬에서 작성한 잠금 파일을 클라우드에서도 같은 도구로 읽도록 맞출 선택지가 생긴 것이다. 모든 기존 프로젝트의 설치 오류가 자동으로 사라진다는 발표는 아니다.

지금 실패하지 않고 실제 버전도 의도와 같다면 급히 숫자를 바꿀 이유는 없다. 반대로 설치가 끝난 뒤 소스 컴파일에서 실패했다면 npm 버전 차이는 여러 가설 중 하나다. 마지막 오류 한 줄보다 처음 실패한 단계와 그 앞의 환경 기록을 보존한다.

engines는 요구 조건이고 packageManager는 선택값이다

engines.npm은 이 프로젝트에 맞는 npm 범위를 표현한다. npm 문서에서도 기본적으로 요구 조건을 알리는 필드로 설명한다. Workers Builds는 이 값을 npm 선택에 쓰지 않는다. 경고가 보였다는 사실과 원하는 버전이 설치됐다는 사실을 구분하자.

설정 세 가지가 맡는 일이 다르다
항목맡는 일단독으로 보장하지 않는 것
engines.npm사용 가능한 npm 범위 표현클라우드의 npm 선택
packageManager설치 도구의 정확한 버전 지정잠금 파일·의존성의 일괄 변환
package-lock.jsonnpm 의존성 트리 기록Node·OS까지 같은 실행 환경

아래는 공식 발표에 나온 버전 형식 예시다. 기존 package.json을 이 예시로 덮어쓰지 말고 최상위 객체에 필드를 추가한다. 11.19.1은 예시이며 모든 프로젝트에 대한 권장 버전이나 이 글에서 설치를 검증한 버전이 아니다.

{
  "packageManager": "npm@11.19.1"
}

정확한 버전을 사용하고 npm@^11 같은 범위는 쓰지 않는다. Workers Builds 문서는 버전 표현을 해석하지 못하면 기본 버전을 쓴다고 설명한다. 설정 파일을 저장했다는 사실만으로 적용 성공을 판단할 수 없는 이유다.
