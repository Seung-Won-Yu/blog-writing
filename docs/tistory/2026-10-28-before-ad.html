같은 프로젝트가 로컬에서는 설치되는데 Workers Builds npm 설치 단계에서만 막힌다고 하자. engines.npm에 버전을 적었어도 빌드 로그에는 다른 숫자가 찍힌다면, 버전을 고르는 설정과 프로젝트의 요구 조건을 혼동했을 수 있다.

Workers Builds에서 npm 버전을 지정할 때 나눠 확인할 세 경계

새 버전 선택 기능을 engines.npm·빌드 루트·잠금 파일·npm ci의 조건과 연결해, 설치 실패를 안전하게 좁히는 판단 기준을 제공한다.

npm 버전을 고정하려면 packageManager부터 확인한다

Workers Builds npm 버전은 package.json의 packageManager에 정확한 버전을 적어 지정한다. engines.npm은 프로젝트의 요구 조건이며 실제 npm 선택 설정이 아니다.

기존 package.json의 최상위 객체에 아래 필드를 추가한다. 11.19.1은 10월 23일 공식 발표의 형식 예시다. 프로젝트가 검증한 버전으로 바꾸고, 파일 전체를 이 예시로 덮어쓰지 않는다.

{
  "packageManager": "npm@11.19.1"
}

npm@^11 같은 범위 대신 정확한 버전을 쓴다. 형식을 해석하지 못하면 기본 버전을 사용하므로, 저장 후 빌드 로그에서 실제 선택값을 확인한다.

대상은 GitHub 저장소를 연결해 의존성 설치를 맡기는 Workers Builds다. 로컬 Wrangler나 GitHub Actions로 직접 배포한다면 해당 환경의 설치 설정을 확인한다. 실행 중인 Worker의 오류도 이번 버전 선택 변경과는 별개다.

  • 실패한 빌드의 의존성 설치 단계와 실제 npm·Node 버전을 확인한다.
  • 프로젝트 루트의 packageManager와 저장소 최상위의 같은 필드가 일치하는지 읽는다.
  • 선택한 npm의 정확한 버전과 npm용 잠금 파일을 함께 검토한다.
  • 검증용 브랜치에서 설치 로그·테스트·변경 파일을 대조한 뒤 적용 범위를 정한다.

engines는 요구 조건이고 packageManager는 선택값이다

engines.npm은 이 프로젝트에 맞는 npm 범위를 표현한다. npm 문서에서도 기본적으로 요구 조건을 알리는 필드로 설명한다. Workers Builds는 이 값을 npm 선택에 쓰지 않는다. 경고가 보였다는 사실과 원하는 버전이 설치됐다는 사실을 구분하자.

설정 세 가지가 맡는 일이 다르다
항목맡는 일단독으로 보장하지 않는 것
engines.npm사용 가능한 npm 범위 표현클라우드의 npm 선택
packageManager설치 도구의 정확한 버전 지정잠금 파일·의존성의 일괄 변환
package-lock.jsonnpm 의존성 트리 기록Node·OS까지 같은 실행 환경

처음 실패한 단계부터 구분하자. 의존성 설치가 끝난 뒤 컴파일에서 실패했다면 빌드 명령과 소스를 먼저 본다. 현재 설치가 정상이고 npm 버전도 의도와 같다면 급히 숫자를 바꿀 필요는 없다.
