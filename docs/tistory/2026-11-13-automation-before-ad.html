TypeScript 7 ESLint 전환: 방치한 Promise를 CI에서 확인하는 법

TypeScript 7을 CI에 추가할 때 기존 타입 기반 ESLint가 방치된 Promise를 검출하는지 정상·위반 입력으로 판단한다.

CI에서 타입 검사와 린트의 역할을 나눈다

TypeScript 7 타입 검사와 기존 ESLint를 별도 작업으로 실행한다. Promise를 처리한 입력과 처리하지 않은 입력을 같은 설정으로 비교해, 후자에만 지정한 규칙 ID가 나오는지 확인한다.

타입 검사는 코드의 타입 관계가 맞는지 확인한다. 타입 기반 린트는 타입 정보를 써서 팀이 금지한 패턴도 찾는다. 함수가 Promise를 반환할 때 그 결과를 쓰지 않는 호출은 타입상 유효할 수 있다. 방치한 호출을 찾아내려면 해당 린트 규칙이 활성화돼 있어야 한다.

  • CI가 실행하는 타입 검사 명령과 ESLint 명령을 각각 찾는다.
  • 정상 입력과 위반 입력을 같은 린트 설정과 TypeScript 프로젝트에 넣는다.
  • 위반 입력의 규칙 ID와 CI 종료 상태를 확인한 뒤 전환 범위를 정한다.
같은 커밋에서 남길 두 가지 합격 신호
CI 작업무엇을 확인할까
TypeScript 7 타입 검사선택한 tsconfig로 검사하고 기존에 기대한 타입 진단과 비교한다.
타입 기반 ESLint위반 입력에서 지정한 규칙 ID를 확인하고 정상 입력에서는 그 ID가 없어야 한다.

ESLint가 불러오는 TypeScript를 먼저 확인한다

Microsoft의 TypeScript 7.0 안내에는 7.0 CLI와 기존 API를 요구하는 도구를 병행하는 예가 있다. 예제는 npm 별칭으로 7.0 CLI 패키지와 기존 API 패키지의 설치 이름을 분리한다. 기존 도구가 typescript라는 이름으로 패키지를 찾는다는 점이 중요하다.

모노레포라면 루트 선언만 읽고 끝내지 말자. 린트 명령이 실행되는 워크스페이스의 의존성 선언과 lockfile을 확인한다. 7.0 발표에 나온 예제를 옮길 때도 정확한 버전과 린터 지원 범위를 먼저 확인한다.

이 글을 작성할 때 typescript-eslint의 지원 문서는 TypeScript 6.1 미만을 지원 범위로 명시했다. 7.1 베타의 새 API를 확인했다면, 사용하는 린터가 그 API를 지원하는지도 별도로 확인한다.
