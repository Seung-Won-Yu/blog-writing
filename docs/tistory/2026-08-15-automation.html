AI 코딩 에이전트가 빨리 실패하는 장면은 대개 비슷하다. 취소 주문을 빼 달라는 한 줄을 보자마자 코드를 고치지만, 취소 상태가 어떤 문자열인지와 환불 주문을 어떻게 볼지는 확인하지 않는다. 인기 스킬 저장소가 실제로 이 성급함을 막는지 확인하려고 같은 작은 Python 저장소와 같은 모호한 요구사항을 Superpowers, mattpocock/skills, Karpathy Guidelines에 각각 넣었다. 세 실행 모두 코드를 한 줄도 바꾸지 않고 멈췄지만, 멈추는 방식은 확실히 달랐다.

AI 에이전트 스킬 저장소, 같은 코딩 과제로 비교해 보니

인기 에이전트 스킬 저장소의 설계 철학을 소개한 글을 바탕으로 세 저장소를 같은 읽기 전용 과제에 직접 적용했다.

별점 대신 같은 모호한 과제를 건넸다

요즘IT 글은 인기 스킬 저장소가 단순 프롬프트 모음이 아니라 에이전트에게 일하는 절차를 가르치는 온보딩 문서라고 설명한다. 순위는 발견에 도움이 되지만 내 작업에 맞는지는 알려 주지 않는다. 그래서 기능 목록을 다시 요약하는 대신 세 저장소의 핵심 규칙을 고정한 뒤 동일한 작은 Python 과제에 적용했다.

fixture에는 주문 목록의 합계를 계산하는 total_amount 함수와 테스트가 있다. 요구사항은 ‘취소 주문을 합계에서 제외하라’ 한 줄뿐이다. 어떤 문자열을 취소로 볼지, 환불된 주문까지 제외할지는 쓰지 않았다. 좋은 첫 행동은 그 빈칸을 확인하는 것이고, 나쁜 첫 행동은 임의의 문자열을 정해 바로 코드를 바꾸는 것이다.

과제: total_amount가 취소 주문을 제외하도록 수정한다.
제약: 첫 응답만 작성하고 파일은 변경하지 않는다.
일부러 비운 조건: 취소 상태 문자열, 환불 주문 처리

세 저장소는 규모보다 통제 방식이 달랐다

실험 커밋에서 Superpowers는 14개의 SKILL.md를 갖고 있었고, 브레인스토밍 스킬은 요구가 명확해 보이더라도 질문과 설계 승인 전에는 구현하지 않는 하드 게이트를 둔다. mattpocock/skills는 35개의 스킬로 더 잘게 나뉘며, grilling은 남은 결정을 번호로 한꺼번에 제시하고 각 항목에 추천안을 붙인다. Karpathy Guidelines는 하나의 짧은 스킬에 가정 확인, 최소 변경, 테스트 목표를 묶는다.

라이선스도 같지 않다. 확인 시점에 Superpowers와 mattpocock/skills는 MIT 라이선스를 표시했지만 Karpathy 파생 저장소는 GitHub 메타데이터에서 감지된 라이선스가 없었다. Karpathy가 직접 만들거나 보증한 저장소가 아니라는 안내도 읽어야 한다. 팀 공통 규칙으로 복사할 계획이라면 인기보다 출처와 라이선스를 먼저 확인해야 한다.

같은 첫 응답인데 질문의 폭이 달랐다

세 실행은 같은 gpt-5.6-terra medium, 읽기 전용 sandbox, 임시 세션에서 수행했다. 스킬 파일과 과제 파일만 읽게 했고 첫 응답 뒤 종료했다. 결과는 세 경우 모두 git diff가 비어 있었다. 스킬을 붙였다는 사실보다 ‘코드를 바꾸지 않았다’는 행동이 먼저 확인됐다.

Superpowers는 승인 전 구현 금지에 가장 강하다

Superpowers의 브레인스토밍 규칙은 먼저 작업 범위를 분류하고, 필요한 질문을 한 번에 하나씩 묻고, 설계를 제시한 뒤 명시적 승인을 기다린다. 이번 과제에서는 취소 상태 문자열 하나를 물어 첫 왕복을 작게 만들었다. 제품 동작과 데이터 계약을 바꾸는 작업처럼 잘못 시작했을 때 비용이 큰 팀에 어울린다.

반면 아주 작은 수정에서도 승인 절차가 반복되면 답답할 수 있다. 모든 문구 수정과 테스트 이름 변경까지 같은 게이트를 적용하기보다, 외부 동작·데이터·권한처럼 되돌리기 비싼 변경에 강한 게이트를 두고 내부 리팩터링에는 더 가벼운 경로를 두는 편이 현실적이다.

mattpocock은 결정의 지도를 먼저 펼친다

grilling 스킬은 해결책을 만들기 전에 남아 있는 의사결정을 번호로 제시하고 추천과 근거를 붙인다. 이번에는 취소 문자열을 CANCELLED로 둘지와 REFUNDED를 합계에 포함할지를 함께 물었다. 사용자는 번호별 답만 돌려주면 된다. 기획·API·데이터 모델처럼 선택이 서로 얽힌 작업에서 빠진 결정을 찾기 좋다.

질문을 많이 찾는 능력과 질문을 많이 던지는 것은 다르다. 사소한 선택까지 한꺼번에 꺼내면 사용자가 결정 피로를 느낀다. 추천안이 안전한 기본값인지, 지금 결정하지 않아도 되는 항목인지 구분해 주는 규칙이 함께 있어야 장점이 살아난다.

Karpathy 방식은 가볍지만 팀 규칙을 대신하지 않는다

Karpathy Guidelines는 여러 스킬을 호출하는 프레임워크보다 하나의 행동 규칙에 가깝다. 가정을 드러내고, 여러 해석이 있으면 질문하고, 요청한 범위만 수술하듯 고치고, 코드를 쓰기 전에 테스트 목표를 정한다. 이번 응답도 취소 문자열과 환불 처리 두 조건만 짧게 확인했다.

기존 에이전트 설정을 크게 바꾸지 않고 붙이기 쉽다는 장점이 있다. 대신 설계 문서, 승인 주체, 커밋 단위, 실패 시 되돌림 같은 팀 절차는 자동으로 생기지 않는다. 규칙이 가벼울수록 저장소의 테스트 명령과 변경 금지 영역을 별도 AGENTS.md나 작업 계약에 적어야 한다.

내 팀에는 질문의 양보다 멈추는 지점이 중요하다

선택은 저장소 규모가 아니라 실패 비용으로 하면 된다. 외부 API와 데이터 계약처럼 잘못 만들면 되돌리기 비싼 작업은 승인 게이트가 유리하다. 이해관계자가 많고 결정이 얽힌 기능은 질문 묶음이 빠진 선택을 줄인다. 테스트가 잘 갖춰진 작은 유지보수 작업은 최소 변경 규칙이 흐름을 덜 방해한다.

  • 첫 응답에서 요구사항의 빈칸을 실제 질문으로 바꾸는가?
  • 답을 받기 전 코드와 파일을 수정하지 않는가?
  • 추천 기본값과 사용자가 결정해야 할 항목을 구분하는가?
  • 요청 밖 리팩터링과 새 의존성을 막는가?
  • 테스트 목표와 실패 시 되돌릴 범위를 남기는가?
  • 저장소 출처·커밋·라이선스를 재현 기록에 남길 수 있는가?

새 스킬을 팀 전체에 설치하기 전에 읽기 전용 첫 응답 시험을 먼저 하면 부작용이 없다. 실제로 자주 실패하는 모호한 과제 세 개를 고르고, 질문 수보다 빠진 가정, 첫 파일 변경 시점, 제안 범위, 검증 계획을 비교한다. 그 뒤 가장 잘 맞는 규칙만 작게 가져오는 편이 수십 개 스킬을 통째로 설치하는 것보다 관리하기 쉽다.

실험 범위와 다시 확인할 조건

이번 비교는 한 개의 작은 Python fixture와 첫 응답만 측정했다. 완성 코드의 정확도, 긴 작업의 토큰 비용, 여러 차례 대화 뒤의 일관성, 실제 팀 협업 속도는 비교하지 않았다. 첫 응답에서 멈추는 능력은 중요한 안전 신호지만 전체 개발 품질의 순위는 아니다.

재현하려면 과제 파일과 비워 둔 결정 두 개, 모델·권한·스킬 커밋을 함께 고정한다. 이후 스킬이 업데이트되면 같은 읽기 전용 명령으로 첫 응답과 git diff를 다시 확인한다. 질문 없이 코드가 바뀌거나 범위 밖 파일을 건드리면 결과를 채택하지 않고 스킬 규칙 또는 작업 계약을 좁힌다.

에이전트 스킬의 가치는 더 많은 코드를 쓰는 데 있지 않았다. 틀린 가정으로 첫 줄을 쓰기 전에 멈추게 하는 데 있었다.
