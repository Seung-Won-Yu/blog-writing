빈칸을 허용해야 없는 사실을 채우지 않는다

모든 필드를 필수로 만들고 빈값을 허용하지 않으면, 정보가 없는 문서에도 무언가를 넣으라고 요구하는 셈이 된다. 모양의 안정성이 정보 부족을 없애지는 않는다. 추출 앱이라면 누락 상태를 어떻게 표현할지 데이터 계약에서 먼저 정해야 한다.

Outlines README에는 행사 정보를 추출하되 정보가 부족하면 다른 응답을 허용하는 예가 있다. 여기서 가져갈 것은 특정 문자열이 정답이라는 주장이 아니다. 정상 결과만 정의하지 말고 답을 만들 수 없는 상태도 출력 공간에 포함하라는 설계 질문이다.

가상의 공고 정리 앱에서 “연봉 미공개”를 숫자 0으로 저장하면 이후 집계가 왜곡될 수 있다. 숫자를 강제하기보다 값 없음과 실제 0을 구분한다. 앱이 값을 소비할 때도 누락을 검토 대기 상태로 처리해야 한다. 빈칸을 허용하는 스키마만 만들고 저장 경로는 그대로 두면 부족하다.

  • 원문에 없는 값: 값 없음 또는 추출 불가 상태로 분리한다.
  • 원문과 충돌하는 값: 원문·후보 값·실패 이유를 함께 보존한다.
  • 응답이 중간에 끊김: 완성된 정상 객체와 구분하고 저장을 보류한다.

이 목록은 문헌을 바탕으로 만든 앱 설계 제안이다. 누락 상태의 이름이나 타입은 서비스 계약에 맞춰 정한다. 결과에 근거 문장을 함께 받더라도 모델이 그 문장을 잘못 골랐을 수 있으므로, 근거 필드가 있다는 사실만으로 정확성 통과를 선언하지 않는다.

제공자가 이미 필요한 제약을 지원하고 앱 검증도 있다면 새 라이브러리를 하나 더 붙일 이유가 약하다. 반대로 로컬 모델의 출력을 통제하려는 앱은 Outlines의 백엔드 호환성과 배포 조건을 볼 이유가 있다. 이 선택표는 도구의 성능 순위가 아니라 실패 위치를 기준으로 만든 해석이다.

엄격 모드를 켜도 모든 입력의 동작이 똑같아지는 것은 아니다. 공식 문서는 JSON 입력의 날짜·시간처럼 더 느슨한 규칙이 적용되는 경우를 설명한다. Python 객체 검증과 JSON 검증을 같은 조건으로 취급하지 말고 실제 입력 경로를 확인한다.

검증을 도입할 때의 질문은 “더 엄격하면 더 좋을까”보다 “어떤 변환이 의미를 보존하나”다. URL의 문자열 숫자를 받는 기존 앱과 원문 추출 결과를 보존하는 앱은 목적이 다르다. 기존 호출자가 기대하던 변환을 갑자기 거절하면 호환성 문제도 생긴다.

일회성 수동 정리라면 사람이 JSON을 보고 원문과 대조하는 것으로 충분할 수 있다. 같은 추출을 계속 저장·집계하는 서비스에서는 실패를 자동으로 분리할 계약이 더 중요하다. 도입 비용을 판단할 때는 실행 시간 외에 검증 규칙 유지와 오류 기록을 누가 맡는지도 포함한다.

  • 스키마 변경 때는 생성기·검증기·저장 계약이 함께 맞는지 확인한다.
  • 새 필수 필드를 못 채우는 기존 결과는 정상 저장과 분리한다.

여러 문서를 연결한 이 글의 해석은, 도구 이름보다 실패가 드러나는 위치를 먼저 정하면 불필요한 도입을 줄일 수 있다는 것이다.

재시도는 원인이 바뀔 때만 의미가 있다

괄호가 잘렸다면 완료 조건이나 출력 길이를 확인하고, 필드 관계가 틀렸다면 어떤 조건을 위반했는지 구체적으로 돌려준다. 원문에 날짜 자체가 없다면 같은 요청을 반복해도 새로운 근거는 생기지 않는다. 형식 실패와 정보 부족을 같은 재시도 큐에 넣지 않는다.

오류를 되돌릴 때는 실패 이유와 해당 필드를 좁혀야 한다. “다시 제대로 해”라는 지시보다 날짜 순서가 계약에 맞지 않는다는 정보가 유용하다. 다만 이 글은 재시도 효과를 실험한 결과가 아니며, 어떤 피드백이 정확도를 높이는지는 앱의 실제 사례로 평가해야 한다.

횟수나 시간 예산을 다 쓰면 보류 상태로 끝낼 수 있어야 한다. 실패 결과가 성공 데이터와 같은 위치에 저장되지 않게 하고, 원문과 후보 결과는 검토할 수 있게 남긴다. 재시도 횟수는 제품의 비용·지연 요구에 맞춰 정하며 무제한 반복을 기본값으로 두지 않는다.

  • 형식 오류: 생성 완료·지원 제약을 확인한 뒤 제한 재시도한다.
  • 관계 오류: 위반한 규칙을 좁혀 피드백하거나 앱에서 거절한다.
  • 정보 부족: 새로운 근거가 없으면 추출 불가로 보류한다.

근거와 한계: 문법 보장이 사실 보장은 아니다

2023년 Grammar-Constrained Decoding 원 논문은 문법으로 출력 공간을 통제하고 정보 추출·개체 구분·구문 분석 과제에서 평가했다. 특정 연구 조건의 결과는 제약 생성의 가능성을 보여 준다. 현재 내 모델과 데이터에서 같은 정확도가 나온다는 근거로 일반화하지 않는다.

Simon Willison의 2025년 LLM schemas 구현 기록은 여러 모델에 스키마를 전달하고 비정형 자료를 구조화해 다루는 흐름을 보여 준다. 여기서는 개발자가 스키마를 재사용하고 결과를 소비하는 실전 사례로 참고했다. 그의 예시를 이 글의 실행 성과처럼 옮기지 않았다.

조사 범위는 TGI의 생성 과정, Outlines의 공개 사용 예, Pydantic의 검증·변환 정책, 원 논문과 독립 구현 기록이다. 제공자별 현재 기능 전체나 JSON Schema 전체의 지원 차이를 비교한 글은 아니다. 호출할 모델·백엔드·입력 종류가 바뀌면 관련 공식 문서를 다시 확인해야 한다.

이 글은 공식 문서와 구현 기록을 대조한 선택 가이드다. 모델 호출·설치·성능 실험을 하지 않았으며 특정 조합의 정확도나 처리 속도를 보장하지 않는다.

  • 실제 원문의 정답 사례와 정보 부족 사례를 나누어 확인한다.
  • 파싱 성공·앱 규칙 통과·원문 일치를 별개 결과로 기록한다.
