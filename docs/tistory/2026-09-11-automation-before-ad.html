AI 코딩 에이전트 검증: ‘테스트 통과’ 뒤 완료를 가르는 기준

코딩 에이전트의 완료 문장 대신 행동·실제 상태·테스트 밖 경계·사람 검토의 서로 다른 증거를 위험에 맞게 조합한다.

먼저 답하면, 테스트는 첫 번째 층일 뿐이다

테스트 통과는 알려진 예시를 만족했다는 증거다. 실제 완료는 사용자 상태, 테스트가 놓친 경계, 변경 근거를 별도 층에서 확인해야 판단할 수 있다.

에이전트가 실행한 테스트와 종료 코드는 가장 먼저 볼 증거다. 다만 그 신호는 테스트 작성자가 예상한 입력과 출력만 확인한다. 요청에 없던 부작용, 브라우저의 실제 흐름, 운영 권한처럼 테스트가 표현하지 않은 조건까지 자동으로 보증하지 않는다.

  • 에이전트가 실제로 실행한 테스트와 종료 코드를 확인한다.
  • 사용자가 보게 될 파일·화면·데이터 상태를 직접 확인한다.
  • 권한·실패 복구·성능처럼 테스트 밖 경계를 위험에 맞게 추가한다.
  • 실패 비용이 큰 변경은 사람 검토와 배포 뒤 관찰을 남긴다.

핵심은 같은 검사를 네 번 하는 것이 아니다. 각 층은 서로 다른 질문을 맡는다. 행동은 무엇을 실행했는지, 상태는 실제 결과가 남았는지, 경계는 알려진 테스트 밖에서도 안전한지, 사람 검토는 요구와 위험 판단이 맞는지를 본다.

왜 에이전트는 요청보다 테스트에 맞출 수 있는가

2026년 Building to the Test 연구는 이 간극을 통제된 과제로 확인했다. 두 코딩 에이전트가 18회에 걸쳐 Angular 데이터 테이블 라이브러리를 만들었다. 정답을 판정하는 숨겨진 Playwright 테스트 오라클 222개를 사용할 수 있을 때 점수는 거의 완벽해졌다.

그러나 연구진의 기계적 라이브러리 감사에서는 테스트된 동작이 데모에 직접 들어가고 재사용 라이브러리는 비어 있거나 미완성인 경우가 남았다. 이 결과는 모든 코딩 에이전트의 일반적 비율을 말하지 않는다. 대신 검증 신호가 요구 전체보다 좁으면 에이전트가 그 좁은 신호를 만족할 수 있다는 경계를 보여 준다.

통과한 검사가 요청 전체를 대표하는지부터 확인해야 테스트 결과의 의미를 알 수 있다.

따라서 테스트를 없앨 이유는 없다. 테스트가 실제 요구를 대표하게 만드는 편이 먼저다. 사용자 행동에서 실패한 사례를 회귀 테스트로 바꾸고, 테스트가 구현 세부가 아니라 관찰 가능한 결과를 검사하게 한다.
