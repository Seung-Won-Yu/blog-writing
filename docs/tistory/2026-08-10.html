‘간단한 내부 도구 하나 만들어 줘’라고 부탁했는데, 잠시 뒤에는 프레임워크와 패키지 수십 개, 컨테이너 이미지, 배포 설정까지 생겨 있다. 화면이 잘 뜬다는 사실만 보면 성공이다. 하지만 누가 어떤 패키지를 골랐는지, 외부 어디와 통신했는지, 어떤 비밀값을 읽었는지 답하지 못한다면 프로토타입은 이미 관리하기 어려운 운영 시스템이 됐다. AI 코딩 에이전트가 빠르게 만든 결과를 버리지 않으면서도 통제권을 놓치지 않으려면 코드 줄보다 변경의 출처와 권한 경계를 먼저 확인해야 한다.

오늘의 핵심뉴스

심층 분석 · ITWorld Korea · 2026. 8. 7

AI 코딩 에이전트가 만든 앱, 의존성과 권한을 추적하지 못하면 프로덕션 위험으로 이어진다

ITWorld Korea는 AI 에이전트가 개발 속도를 높이는 동안 조직이 선택하지 않은 패키지와 컨테이너, 느슨한 인증, 넓은 인프라 접근이 검토 없이 운영 환경으로 넘어가는 문제를 짚었다. GitHub와 OpenAI의 공식 보안 문서를 함께 대조해 패키지 출처, 네트워크, 권한, 사람 승인으로 나눠 실제 적용 기준을 정리했다.

프로토타입이 배포되는 순간 위험도 바뀐다

AI 코딩 에이전트에게 내부 대시보드를 부탁하면 단순한 소스 파일만 생기지 않는다. 문제를 빨리 풀기 위해 웹 프레임워크와 라이브러리를 고르고, 데이터 저장소와 컨테이너 구성을 붙이고, 실행 명령까지 만든다. 처음에는 개인 실험이었어도 동료가 쓰기 시작하고 실제 데이터가 들어오면 어느 순간 운영 서비스가 된다. 그런데 보안 검토는 여전히 ‘나중에 할 일’로 남기 쉽다.

ITWorld Korea가 지적한 핵심도 속도 자체가 아니다. 사람이 명시적으로 선택하지 않은 구성요소가 늘고, 에이전트가 만든 인증과 네트워크 구성이 자연스럽게 기본값이 되는 동안 그 결정을 누가 소유하는지 흐려진다는 점이다. 화면이 뜨고 테스트가 통과했다는 신호는 기능이 움직인다는 뜻이지, 패키지 출처와 데이터 경계까지 안전하다는 증거는 아니다.

그래서 실험과 운영을 가르는 기준은 사용자 수보다 영향 범위가 더 적절하다. 실제 계정으로 로그인하는가, 사내 문서나 고객 데이터를 읽는가, 비용이 드는 외부 API를 호출하는가, 인터넷에 공개되는가, 자동 배포가 가능한가 중 하나라도 해당하면 운영 수준의 검토를 시작할 때다. 나중에 유명해지면 점검하겠다는 접근은 이미 사용자가 생긴 뒤 구조를 뜯어고치는 비용을 키운다.

에이전트가 고른 패키지는 내 선택으로 남는다

package.json이나 requirements.txt에 새 이름이 추가됐다고 끝이 아니다. 잠금파일은 실제로 설치될 버전과 무결성 정보를 고정하고, 컨테이너의 베이스 이미지와 전이 의존성은 선언 파일 밖에서 더 많은 코드를 끌어온다. 에이전트가 ‘문제를 해결하는 패키지’를 찾았더라도 유지관리 상태, 배포 주체, 최근 변경, 알려진 취약점, 라이선스와 대체 가능성은 사람이 확인해야 한다. 이름이 비슷한 패키지나 최근 만들어진 패키지를 자동으로 받아들이면 타이포스쿼팅과 공급망 공격의 문이 열린다.

변경 흔적확인할 질문멈춰야 할 신호

잠금파일버전과 무결성 값이 예상 범위에서 바뀌었는가설명할 수 없는 대규모 전이 의존성 변경

GitHub의 Copilot 코딩 에이전트는 생성된 변경에 CodeQL과 의존성 검사를 적용하고, GitHub Advisory Database에서 악성 패키지와 높은 심각도의 취약점을 확인한다고 설명한다. 유용한 안전망이지만 모든 위험을 대신 판단하지는 않는다. 아직 신고되지 않은 문제, 과도한 기능, 유지보수 중단, 조직 정책과 맞지 않는 라이선스는 별도의 검토가 필요하다. 자동 검사는 승인 여부를 결정할 증거 중 하나로 보는 편이 안전하다.

네트워크는 켜짐보다 목적지와 방법을 적는다

에이전트가 인터넷을 쓸 수 있으면 문서와 패키지를 찾는 속도는 빨라진다. 동시에 외부 페이지에 숨은 지시를 읽거나, 민감한 내용을 외부 요청에 섞거나, 신뢰하지 않은 바이너리를 내려받을 가능성도 생긴다. ‘인터넷 허용’이라는 스위치 하나보다 어떤 도메인에 어떤 HTTP 방식으로 접근할 수 있는지, 그 접속이 설정 단계와 실제 작업 단계 중 어디에서 일어나는지를 분리해야 한다.

GitHub는 Copilot 코딩 에이전트의 인터넷을 기본 방화벽으로 제한하고, 필요한 운영체제·패키지·컨테이너 레지스트리를 허용 목록에 넣는 방식을 안내한다. 방화벽을 끄면 데이터 유출 위험이 커진다고 경고하며, Bash 명령 밖의 MCP 서버나 초기 설정 단계처럼 방화벽이 완전히 덮지 못하는 경계도 함께 적어 둔다. 제한 기능이 있다는 사실보다 어디까지 제한되는지 읽어야 하는 이유다.

  • 새 의존성과 잠금파일 변경 이유를 커밋 설명에서 확인한다.
  • 외부 통신은 필요한 도메인과 요청 방식만 허용하고 나머지는 닫는다.
  • 비밀값은 작업별 단기 자격증명으로 나누고 로그와 결과물에 남지 않았는지 검사한다.
  • 저장소 쓰기, CI 실행, 아티팩트 업로드, 운영 배포 권한을 서로 분리한다.
  • 테스트와 보안 검사가 통과해도 최종 병합과 운영 배포는 사람이 변경 내용을 읽은 뒤 승인한다.

권한은 작업 단위로 나누고 로그를 남긴다

에이전트가 저장소를 읽고 파일을 고쳐야 한다고 해서 조직의 모든 저장소, 장기 클라우드 키, 운영 데이터베이스까지 볼 이유는 없다. 읽기와 쓰기, 테스트 실행과 배포, 개발 환경과 운영 환경을 분리하면 잘못된 제안 하나가 미치는 범위를 줄일 수 있다. 가능하면 짧게 만료되는 자격증명을 쓰고, 작업이 끝나면 폐기하며, 에이전트가 접근한 도구와 명령 결과를 감사 가능한 로그로 남긴다.

GitHub의 공식 위험 안내도 에이전트가 전용 브랜치 하나에서 작업하고, 사람이 병합 전 변경을 검토하며, 워크플로 실행을 승인하는 경계를 강조한다. 이것은 AI만의 특별한 규칙이라기보다 기존 소프트웨어 공급망 원칙을 더 빠른 작업 속도에 맞춰 다시 적용한 것이다. 에이전트를 신뢰할 수 있는 동료처럼 대하는 것과 모든 권한을 한 번에 건네는 것은 전혀 다른 선택이다.

자동화해도 되는 범위와 사람 승인을 남길 범위
작업자동화 가능한 범위사람 확인이 필요한 순간

패키지 설치승인된 레지스트리와 고정된 버전새 배포자·새 설치 스크립트가 들어올 때

운영 배포검증된 산출물의 준비 단계실제 트래픽과 데이터에 반영하기 직전

보안 도구를 하나 더 붙이는 것만으로는 부족하다

보안 스캐너는 알려진 취약점과 위험 패턴을 찾는 데 강하지만 ‘이 서비스가 왜 인터넷에 공개돼야 하는가’나 ‘이 데이터 저장소에 인증이 빠져도 되는가’까지 제품 맥락으로 결정하지 못한다. 에이전트가 만든 구조를 다른 에이전트에게 검토시킬 수도 있지만, 같은 잘못된 전제와 누락된 요구사항을 공유할 수 있다. 자동 검토는 사람의 질문을 줄이는 도구이지 책임을 넘기는 장치가 아니다.

OpenAI의 에이전트 인터넷 접근 안내도 네트워크를 기본적으로 닫고 환경별 허용 목록을 쓰도록 설명하면서, 프롬프트 인젝션·데이터 유출·악성코드·라이선스 문제를 함께 경고한다. 중요한 점은 특정 제품이 더 안전하다는 비교가 아니다. 어떤 에이전트를 쓰든 외부 콘텐츠를 읽고 코드를 실행하며 비밀값에 접근하는 순간 같은 종류의 경계가 필요하다는 사실이다.

배포 전 네 번 멈추면 사고 범위가 줄어든다

첫 번째 멈춤은 새 패키지가 들어올 때다. 출처와 버전, 설치 스크립트, 대체 가능성을 확인한다. 두 번째는 외부 통신이 필요할 때다. 도메인과 요청 방법, 전송되는 데이터를 적는다. 세 번째는 권한이 늘어날 때다. 비밀값과 저장소 쓰기, CI, 클라우드 권한을 작업 단위로 좁힌다. 네 번째는 실제 배포 직전이다. 변경 목록과 검사 결과를 사람이 읽고 승인한 산출물만 운영 환경으로 보낸다.

이 네 지점은 개발을 느리게 만드는 장벽이 아니라 되돌릴 위치를 남기는 장치다. 에이전트가 수정과 테스트를 빠르게 반복하더라도 승인 조건이 고정돼 있으면 실패 원인을 패키지, 네트워크, 권한, 배포 중 하나로 좁힐 수 있다. 반대로 모든 권한을 한 작업에 몰아주면 문제가 생겼을 때 무엇이 어디까지 영향을 줬는지 확인하는 시간부터 길어진다.

ITWorld Korea의 문제 제기를 출발점으로 GitHub Copilot 코딩 에이전트의 방화벽·검사·브랜치·승인 경계와 OpenAI 에이전트의 네트워크 허용 목록 안내를 대조했다. 제품마다 구현은 달라도 승인된 출처, 제한된 통신, 최소 권한, 사람 검토라는 네 축은 공통으로 남는다.

AI 코딩 에이전트의 위험은 코드를 많이 만든다는 데 있지 않다. 선택한 적 없는 의존성과 넓은 권한이 검토 없이 운영 환경으로 넘어갈 때 문제가 커진다. 에이전트가 제안하는 속도는 그대로 활용하되, 새 패키지·외부 통신·비밀값·배포 변경에는 사람이 멈출 수 있는 문을 둬야 한다. 잘 작동하는 결과와 안전하게 운영할 수 있는 결과 사이에는 짧지만 반드시 거쳐야 할 승인 단계가 있다. 다음 에이전트 작업에서는 커밋 전에 의존성 파일, 외부 통신 목적지, 권한 변경, 배포 승인자를 한 번에 확인해 보자.
