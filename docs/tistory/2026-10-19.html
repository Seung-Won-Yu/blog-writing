Hive를 바꾼 뒤 Spark 잡만 실패한다. 관리 도구에서는 테이블이 보이는데 같은 이름을 조회하는 배치가 멈추면 무엇부터 고쳐야 할까? Spark Hive 연결 오류는 메타스토어 주소, 실제 클라이언트, 실패 요청을 나눠 확인해야 한다. 서버가 살아 있다는 사실과 Spark의 조회가 호환된다는 사실은 다르다. 오류가 난 지점을 좁히면 재설치나 공용 서버 변경에 앞서 작은 검증을 설계할 수 있다.

Spark와 Hive의 연결 실패를 요청·클라이언트·대상으로 나누는 기준

공식 지원표와 실제 운영 사례를 비교해 업그레이드 뒤 Spark만 실패하는 상황의 수집 근거와 검증 경계를 정리한다.

서버를 바꾸기 전에 실패한 요청을 보존한다

Spark Hive 연결 오류는 서버 버전 하나로 판단하지 않는다. 연결한 메타스토어 주소, Spark가 로드한 Hive 클라이언트, 오류가 발생한 요청을 함께 확인한 뒤 수정할 곳을 정한다.

  • 실패한 Spark 애플리케이션의 오류 전문·실행 시각·배포 버전을 보존한다.
  • 실제로 연결한 메타스토어 주소와 로드한 Hive 클라이언트 설정을 확인한다.
  • 통신 실패·메서드 불일치·테이블 조회 실패 중 어디에서 멈췄는지 나눈다.
  • 지원 범위 안의 변경 하나를 검증 환경에 적용하고 메타데이터와 대표 조회를 따로 확인한다.

대상은 기존 Hive 테이블을 읽던 Spark 배치를 관리하는 개발자다. 새 데이터 플랫폼을 고르거나 Hive 서버를 직접 패치하는 절차는 다루지 않는다. 우선 실패한 애플리케이션 하나와 이전에 성공한 배포본 하나를 비교 단위로 잡는다.

주소·클라이언트·실패 요청을 한 묶음으로 기록하면 연결 대상을 잘못 고른 문제와 서버가 요청을 지원하지 않는 문제를 분리할 수 있다.

원격 서버의 주소는 내부 운영 기록에 남기고 공개 문의에는 가린다. 오류 전문에서도 토큰·접속 문자열·테이블의 민감한 이름을 제거한다. 필요한 것은 접속 비밀이 아니라 어느 실행이 어느 대상에 어떤 요청을 보냈는지 확인할 단서다.

연결 성공과 테이블 조회 성공은 다른 확인이다

메타스토어는 데이터 파일 자체를 보내는 곳이 아니다. Spark는 먼저 테이블의 구조와 저장 위치를 확인하고, 그 정보를 바탕으로 데이터를 읽는다. 그래서 메타데이터 요청이 성공해도 파일 접근 단계에서 다른 오류가 날 수 있다.

다음 표는 원인을 확정하는 오류 사전이 아니라 조사 방향을 정하는 편집자의 분류다. 가장 바깥쪽 예외 이름만 보지 말고 안쪽 원인과 실패 시각을 함께 읽는다. 여러 계층의 오류가 겹치면 앞에서 막힌 것부터 확인한다.

Spark Hive 연결 오류를 처음 나눌 때의 판단표
남은 단서먼저 볼 곳아직 단정할 수 없는 것
timeout·connection refused접속 대상·경로·서버 상태클라이언트 버전 불일치
Invalid method name요청 이름·서버 인터페이스테이블 삭제 또는 데이터 손상
테이블 없음·접근 거절카탈로그·이름·실행 계정서버 전체 장애
메타데이터 조회 뒤 파일 오류저장 위치·파일 접근·형식메타스토어 연결 실패

관리 도구와 배치가 같은 주소·계정·카탈로그를 사용하는지부터 맞춘다. 다른 환경의 동명 테이블을 본 성공은 비교 근거가 되지 않는다. 특히 도구에 표시된 서버 이름만 같고 실제 접속 경로가 다르면 담당자에게 연결 대상을 확인한다.

공식 Spark 문서는 Hive 설정이 없을 때 로컬 metastore_db와 spark-warehouse를 만들 수 있다고 설명한다. 기대하던 테이블이 보이지 않는다면 새 로컬 환경을 원격 Hive로 착각했는지 확인한다. 이때 빈 목록은 테이블 삭제의 증거가 아니다.

버전 설정과 라이브러리 공급 방식은 한 쌍이다. spark.sql.hive.metastore.version은 통신에 쓸 Hive 클라이언트를 선택하는 데 관여하며 원격 서버를 업그레이드하지 않는다. spark.sql.hive.metastore.jars가 어디서 어떤 파일을 가져오는지도 함께 확인한다.

지원 버전과 실제로 로드한 라이브러리를 같이 본다

Spark 3.5.7 문서에서 기본 Hive 클라이언트는 2.3.9이고 지원 목록은 3.1.3까지다. Spark 4.0.1 문서는 기본값 2.3.10과 Hive 4.0.0~4.0.1 지원을 별도로 적는다. 두 문서의 숫자는 해당 Spark 버전의 기준이며 모든 배포본에 적용할 공통 정답이 아니다.

builtin을 쓰면서 임의의 다른 버전 숫자만 지정하면 라이브러리가 자동으로 그 버전으로 교체된다고 생각하기 쉽다. 공식 문서에서 builtin은 함께 묶인 Hive 버전과 맞아야 한다. path를 쓸 때도 지정 파일과 version의 일치를 확인해야 한다.

Maven 다운로드로 빠르게 시험할 수 있다는 사실과 운영 공급 방식으로 적절하다는 판단은 다르다. 공식 문서는 이 방식을 운영에 일반적으로 권장하지 않는다. 플랫폼에서 고정한 의존성 묶음이 있다면 임의 JAR 추가 전에 배포 담당자와 그 묶음을 확인한다.

실행 기록은 Spark UI의 Environment 탭과 제출 설정을 대조한다. 이 탭에는 명시적으로 지정한 Spark 속성이 표시되므로 항목이 없다는 것만으로 기능이 꺼졌다고 단정하지 않는다. 기본값은 실행한 버전의 문서에서 따로 확인한다.

get_table이 없다는 응답이면 요청 계약을 확인한다

NAVER D2가 2026년 9월 21일 공개한 운영 사례에서는 Hive 4.2 기반 사내 포크 전환 뒤 Spark 3.5.5의 구형 클라이언트가 get_table을 호출해 실패했다. 당시 서버 전체가 멈춘 것이 아니라 특정 클라이언트의 요청 경로가 끊긴 상황이었다.

그 사례에서 서버는 신형 조회 경로를 지원했지만 구형 요청 이름은 받지 못했다. 관리 도구가 성공해도 Spark의 다른 클라이언트가 성공한다는 보장이 없었던 이유다. Apache의 HIVE-26537도 메타스토어 구형 API 정리를 다루며 수정 버전에 4.0.1과 4.1.0을 기록한다.

RPC 요청 계약은 같은 기능을 한다는 설명보다 구체적이다. 클라이언트가 보내는 이름과 인자, 서버가 돌려주는 구조가 맞아야 한다. get_table과 get_table_req를 단순 문자열 치환으로 바꿔도 된다고 읽으면 안 된다. 입력·반환 형태가 다른 요청일 수 있기 때문이다.

이 사례를 근거로 모든 Hive 4 계열 연결 실패를 같은 원인으로 확정하지 않는다. 사내 포크·제품 배포판에는 수정이 들어갔을 수 있다. 설치한 서버가 실제로 받는 인터페이스와 실패한 실행이 보낸 요청을 운영 담당자와 대조해야 한다.

  • 스택에 기록된 요청 이름과 클라이언트 배포본을 함께 남긴다.
  • 서버 담당자에게 해당 배포본의 지원 인터페이스와 호환 조합을 확인한다.
  • 애플리케이션 교체와 공용 서버 변경 중 영향을 더 작게 제한할 수 있는 경로부터 검증한다.

검증은 메타데이터에서 시작해 대표 조회로 넓힌다

다음은 독자가 자기 검증 환경에 맞춰 사용하는 SQL 예시다. analytics와 sample_table은 설명용 이름으로, 허가된 테스트 테이블로 바꾼다. 실행 결과를 제시하는 예제가 아니며 운영 데이터를 생성·삭제하는 명령도 포함하지 않는다.

DESCRIBE TABLE EXTENDED analytics.sample_table;
-- 메타데이터 확인 뒤, 허가된 테스트 테이블에서 실행
SELECT * FROM analytics.sample_table LIMIT 1;

DESCRIBE TABLE은 열 이름·형식 같은 메타데이터를 반환하며 EXTENDED는 추가 정보를 보여 준다. 먼저 예상한 열 구조와 저장 위치가 맞는지 기존 정상 기록과 비교한다. 출력이 나왔다는 사실만으로 올바른 환경에 연결했다고 결론내리지 않는다.

뒤의 SELECT는 파일을 읽는 대표 경로를 확인하기 위한 작은 시작점이다. LIMIT 1은 비용 상한이나 전체 파일·파티션 검사의 보장이 아니다. 민감한 행이 출력될 수 있으므로 공개 자료가 들어 있는 테스트 테이블에서만 확인하고 출력 공유도 제한한다.

실무 검증에는 실제 사용하는 형식과 파티션, 권한 조건이 포함돼야 한다. 한 테이블 한 행의 성공으로 모든 배치를 검증했다고 보고하지 않는다. 변경한 클라이언트가 다른 작업에 미치는 영향을 확인할 목록은 운영 범위에 맞춰 추가한다.

조회가 달라지면 확대를 멈추고 이전 조합을 보존한다

새 애플리케이션에서 같은 호출을 해도 다른 예외가 나거나 열·저장 위치가 달라졌다면 배포 확대를 멈춘다. 오류 이름이 바뀐 것을 해결로 세지 말고 다음 실패 계층의 근거로 기록한다. 기존 배포본과 설정 묶음은 비교할 수 있게 보존한다.

변경 범위와 중단 조건을 기록하는 예시
선택먼저 갖출 근거확대를 멈출 조건
클라이언트 설정 수정지원 범위와 실제 로드 파일 일치같은 설정인데 로드 파일이 다름
지원 조합으로 전환대표 테이블·조회·권한 검증스키마나 조회 결과가 달라짐
서버 호환 경로 검토플랫폼 소유자의 지원·테스트 계획기존 사용자의 회귀 범위 불명확

공용 서버를 이전 버전으로 되돌리는 것은 애플리케이션 롤백보다 범위가 크다. 서버 스키마나 다른 사용자의 변경까지 얽힐 수 있으므로 이 표를 서버 다운그레이드 명령으로 해석하지 않는다. 애플리케이션 복구와 플랫폼 복구의 담당·절차를 분리한다.

이 글은 공개 문서와 운영 사례를 비교한 진단 가이드다. 실제 Spark·Hive 클러스터에서 오류를 재현하거나 특정 조합의 호환성을 검증하지 않았다.
