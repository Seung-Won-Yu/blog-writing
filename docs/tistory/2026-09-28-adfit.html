업무용 SaaS 상태 페이지가 초록색으로 바뀌고 로그인도 다시 된다. 그런데 장애 중 접수된 주문 하나는 사라졌고, 다른 요청은 두 번 처리됐다. 화면이 열린 시점과 업무가 복구된 시점은 같지 않다. 장애 시간대를 고정하고 접수 기록·비동기 큐·처리 결과·다운스트림을 같은 작업 식별자로 맞춰야 복구 완료를 말할 수 있다.

30초 요약

  • SaaS 장애 복구는 로그인 확인으로 끝나지 않으며 접수 기록·비동기 큐·처리 결과·다운스트림을 같은 작업 식별자로 맞춰야 한다.
  • 재시도는 오류 종류에 따라 제한하고 실패가 이어지면 회로를 열어 작업을 대기열에 보존한 뒤 소수 시험 요청으로 재개한다.
  • 작업 식별자가 없거나 중복·순서 역전의 업무 영향이 불명확하면 자동 재실행하지 말고 사람이 승인한 조정 절차로 전환한다.

SaaS 장애 복구 체크리스트: 로그인 정상 뒤 큐·중복 처리 확인법

Salesforce의 전 리전 장애에서 내부 로그인 서비스 대기가 서버 자원을 소모하고 복구가 리전별 배포와 수동 재시작까지 이어진 사례를 출발점으로, 외부 SaaS 정상화 뒤 우리 쪽 큐·예약 작업·중복·다운스트림 정합성을 확인하는 순서를 정리했다.

로그인 복구 뒤 네 흔적부터 맞춘다

SaaS 복구 알림만 믿지 말고 장애 시간대를 고정한 뒤 접수 기록, 비동기 큐, 처리 결과, 다운스트림 상태를 같은 작업 식별자로 맞춘다. 네 흔적이 일치해야 업무 복구를 선언할 수 있다. 화면이 열리는지 확인하는 일은 시작일 뿐이다.

  • 상태 페이지·내부 알림·오류 로그로 장애 시작과 복구 후보 시각을 고정한다.
  • 장애 시간대의 요청 ID·멱등성 키·업무 키를 모아 기대 작업 목록을 만든다.
  • 비동기 큐와 예약 작업에서 대기·실패·재시도·완료 상태를 대조한다.
  • 다운스트림 레코드의 누락·중복·순서 역전을 조정한 뒤 새 요청을 단계적으로 재개한다.

작업 식별자는 기술 ID 하나로 고정할 필요가 없다. 요청 ID가 없으면 주문 번호·고객 번호·예약 시각처럼 업무가 이미 가진 키를 조합한다. 다만 사람 이름이나 금액만으로 다시 실행하면 다른 요청을 중복 처리할 수 있으므로, 자동 조정과 수동 승인의 경계를 먼저 나눈다.

정상 화면과 완료된 업무는 같은 상태가 아니다

Salesforce의 2026년 9월 16일 공식 사고 기록은 내부 로그인 서비스의 응답을 기다리는 요청이 사용 가능한 서버 자원을 소모했다고 설명한다. 일부 고객은 심한 지연과 간헐적 오류뿐 아니라 지원 케이스 생성 불가도 겪었다. 복구는 시험 인스턴스 검증, 전 리전 배포, 추가 모니터링으로 이어졌다.

ITWorld의 후속 분석은 로그인 이후를 더 구체적으로 짚었다. 장애 중의 API 호출, 통합, 예약 작업, 큐와 워크플로는 늦게 실행되거나 실패하거나 순서가 바뀔 수 있다. 기저 데이터가 남아 있어도 직원이 최신 고객 이력과 처리 상태를 보지 못하면 업무 기준으로는 복구가 끝난 것이 아니다.

그래서 복구 후보 시각을 한 점으로 믿지 않고 구간으로 다룬다. 제공자가 정상화를 알린 시각, 우리 오류율이 평소 범위로 돌아온 시각, 큐 적체가 줄기 시작한 시각을 따로 기록한다. 조정 대상은 이 구간 앞뒤에 여유를 둔 작업 목록에서 찾는다.

작업은 네 가지 실패 상태로 나눠야 보인다

장애 중 작업을 성공과 실패 두 칸으로만 나누면 재시도 결과가 숨는다. 접수 자체가 안 된 작업, 접수됐지만 대기 중인 작업, 한 번 완료된 작업, 두 번 이상 완료된 작업을 분리한다. 이벤트 순서가 중요한 업무라면 완료 시각과 원래 발생 시각도 함께 비교한다.

SaaS 장애 시간대 작업을 조정하는 최소 상태표
상태찾을 흔적조치자동 재실행
미접수원본 요청은 있으나 SaaS 접수 ID 없음업무 유효성 확인 뒤 새 요청조건부
대기·실패큐·예약 작업에 미완료 상태원인 제거 뒤 제한 재시도가능
완료SaaS와 다운스트림 결과 일치재실행하지 않고 기록금지
중복·순서 역전같은 업무 키의 복수 결과·시간 불일치취소·병합·수동 조정금지

멱등성 키가 있으면 같은 요청의 재처리를 구분하기 쉬워진다. 그렇다고 키만 있으면 안전한 것은 아니다. 공급자가 키를 얼마 동안 보존하는지, 응답을 받기 전에 연결이 끊겼을 때 처리 여부를 다시 조회할 수 있는지, 다운스트림도 같은 키를 이어받는지 확인해야 한다.

 

무제한 재시도는 복구 중인 서비스를 다시 누른다

Google SRE는 여러 계층이 각각 재시도하면 한 번의 사용자 동작이 아래 계층에서 기하급수적으로 늘어날 수 있다고 경고한다. 각 계층이 최초 요청 뒤 세 번씩 더 시도하는 구조라면 세 계층만 거쳐도 최하단에는 최대 64번의 시도가 생긴다. 실패한 SaaS가 회복 중일 때 이런 증폭은 큐 적체와 타임아웃을 더 키운다.

일시적인 네트워크 오류와 5xx에는 무작위 지연을 섞은 지수 백오프와 횟수 제한을 쓴다. 잘못된 요청을 뜻하는 일반 4xx는 같은 내용으로 반복하지 않는다. 429는 공급자가 보낸 Retry-After나 레이트리밋 재설정 시각을 따른다. 재시도를 한 계층에 모으면 전체 시도량을 계산하기도 쉬워진다.

Salesforce의 신뢰성 지침은 외부 통합 실패가 이어질 때 서킷 브레이커를 열어 느린 타임아웃이 자원을 계속 잡지 않게 하고, 회복 확인에는 소수 요청만 보내라고 설명한다. 실패 중인 기능이 핵심 경로가 아니라면 추천·분석 같은 부가 기능을 끄고 핵심 업무만 유지하는 점진적 성능 저하도 준비한다.

복구 경로가 장애 난 제어면을 다시 요구하면 늦어진다

AWS가 설명하는 정적 안정성의 핵심은 장애가 난 뒤 새 자원을 만들거나 설정을 바꾸는 제어 작업에 복구를 의존하지 않는 것이다. 외부 SaaS 통합에도 같은 질문을 적용할 수 있다. SaaS가 멈췄을 때 작업을 잃지 않고 보관할 대기열, 마지막으로 확인된 읽기 데이터, 수동 처리 경로가 이미 준비돼 있는지 본다.

예를 들어 주소 검증 서비스가 멈췄다고 주문 접수 전체를 막을 필요는 없다. 검증 대기 상태로 주문을 보존하고 수동 확인으로 넘길 수 있다면 하드 의존성을 소프트 의존성으로 바꾼다. 반대로 결제 승인처럼 추측한 기본값을 쓸 수 없는 기능은 명확히 멈추고 사용자에게 처리 보류 상태를 보여 줘야 한다.

이 분류는 장애 중에 즉석에서 만들기 어렵다. 기능을 핵심·중요·지원·선택으로 나누고, 각 기능에 중단·대기열 보존·읽기 전용·수동 처리 중 한 경로를 미리 정한다. 복구 시에는 경로를 새로 설계하지 않고 준비된 모드가 실제로 작동했는지 확인한다.

업무 재개는 작은 시험과 조정 완료로 나눈다

복구 후보가 보이면 새 요청을 한꺼번에 풀지 않는다. 읽기, 단건 쓰기, 비동기 작업, 대량 작업 순으로 작은 시험을 보내고 오류·지연·큐 깊이를 평소 기준과 비교한다. 시험 요청은 실제 업무 키로 추적할 수 있어야 하며, 끝난 뒤 다운스트림까지 같은 결과가 남았는지 확인한다.

그와 별개로 장애 시간대의 기존 작업을 조정한다. 기대 작업 목록과 최종 결과 수를 맞추고, 중복 처리는 취소나 병합 기록을 남기며, 순서 역전은 후속 계산과 알림에 미친 영향을 확인한다. 새 요청이 정상이라고 과거 적체를 완료 처리하지 않는다.

작업 식별자가 끊긴 구간은 자동화 범위 밖이다. 금액·고객·시간대가 비슷한 후보를 사람이 검토하고, 재실행 전에 이미 처리됐을 가능성을 확인한다. 완벽한 자동 복구보다 중복 결제나 중복 통지를 막는 보수적인 정지가 더 나은 업무도 있다.

복구 완료는 상태 페이지가 아니라 증거 묶음으로 남긴다

완료 기록에는 장애 시간대, 기대 작업 수, 상태별 작업 수, 수동 조정 목록, 재시도 정책, 시험 요청 결과, 재개 승인자를 남긴다. 숫자는 공급자 상태 페이지의 전체 영향이 아니라 우리 시스템에서 관찰한 범위임을 구분한다. 나중에 공급자의 근본 원인 분석이 나오면 원인 문장과 재발 방지 항목을 보강한다.

장애 시간대의 기대 작업 수와 최종 처리 결과가 일치하고, 중복·순서 역전 조정과 제한된 재개 시험이 기록되면 복구 확인이 끝난 것이다. 이 기록을 다음 훈련의 입력으로 쓰면 상태 페이지와 로그인만 보는 습관에서 벗어날 수 있다.

SaaS 제공자의 상태 페이지는 외부 서비스가 응답한다는 신호이지, 우리 업무가 모두 처리됐다는 증명은 아니다. 복구의 끝은 장애 시간대에 기대했던 작업을 목록으로 만들고, 누락·중복·순서 역전·다운스트림 불일치를 조정한 뒤 새 요청이 정상 경로로 흐르는지 확인하는 지점이다. 평소에 작업 식별자와 대기열 보존, 제한 재시도, 수동 처리 경로를 준비해 두면 다음 장애에서 ‘로그인은 된다’와 ‘업무가 끝났다’를 구분할 수 있다. 최근 사용하는 SaaS 통합 하나를 골라 장애 시간대·작업 식별자·큐 위치·다운스트림 대조 기준·재개 승인자를 한 줄씩 적는다.
