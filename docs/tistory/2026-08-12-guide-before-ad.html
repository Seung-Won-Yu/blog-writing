모바일 앱이나 SPA에서 소셜 로그인을 붙인 뒤 콜백 URL에 code가 보이면, 그 값만 가로채도 토큰을 바꿀 수 있는지 불안해진다. PKCE는 인가 요청을 시작한 클라이언트만 그 코드를 토큰으로 교환하도록 묶는 장치다. 이 글은 code_verifier와 S256 challenge가 언제 만들어지고, 리디렉션 URI·state·토큰 정책을 어디까지 함께 점검해야 하는지 실제 HTTP 요청 모양으로 정리한다.

OAuth 2.0 PKCE로 인가 코드 탈취를 막는 구현 점검

PKCE는 인가 요청의 code_challenge와 토큰 요청의 code_verifier를 연결해, 탈취한 인가 코드만으로 토큰을 교환하지 못하게 한다.

콜백 URL의 code만 복사해도 토큰이 나오는지부터 확인한다

로그인 뒤 브라우저가 앱의 callback으로 돌아오면 URL에는 짧은 인가 코드가 붙는다. 이 코드는 access token이 아니지만, 토큰 엔드포인트가 코드만 보고 교환한다면 복사본을 얻은 쪽도 토큰을 받을 수 있다. PKCE(Proof Key for Code Exchange)는 인가 요청을 시작한 클라이언트가 따로 가진 verifier를 나중에 제출하게 해 이 교환을 묶는다.

OAuth 2.0의 역할을 먼저 나누면 구현이 덜 헷갈린다. authorization server는 사용자 인증과 동의를 처리하고 code를 발급한다. client는 앱이며, resource server는 access token을 검증해 API를 연다. OpenID Connect를 함께 쓴다면 ID token은 로그인한 사용자의 신원 정보이고, API 호출 권한을 나타내는 access token과 같은 용도가 아니다.

PKCE는 공개된 challenge와 숨겨 둔 verifier를 한 거래로 묶는다

클라이언트는 로그인 시작 직전에 예측하기 어려운 code_verifier를 만들고, SHA-256을 거쳐 base64url로 인코딩한 code_challenge를 만든다. authorize 요청에는 challenge와 code_challenge_method=S256만 넣는다. redirect에서 받은 code를 token 엔드포인트로 보낼 때 원 verifier를 함께 보낸다. 인가 서버는 처음 저장한 challenge와 verifier로 다시 계산한 값을 비교한다.

const bytes = crypto.getRandomValues(new Uint8Array(32));
const verifier = btoa(String.fromCharCode(...bytes))
  .replace(/\+/g, '-').replace(/\//g, '_').replace(/=+$/, '');
const digest = await crypto.subtle.digest('SHA-256', new TextEncoder().encode(verifier));
const challenge = btoa(String.fromCharCode(...new Uint8Array(digest)))
  .replace(/\+/g, '-').replace(/\//g, '_').replace(/=+$/, '');

// verifier는 현재 로그인 거래와 연결해 잠시만 보관한다.
sessionStorage.setItem('pkce_verifier', verifier);

verifier는 URL query, analytics 이벤트, 오류 메시지에 들어가면 안 된다. 브라우저 앱이라면 같은 탭의 짧은 로그인 거래에만 연결하고, callback 처리 성공·실패 어느 경우에도 지운다. 모바일 앱도 OS의 안전한 저장소를 장기 보관소로 오해하지 말고 거래 수명만큼만 다룬다.

인가 서버를 직접 운영한다면 challenge가 있던 거래에는 verifier 없는 token 요청을 절대 허용하지 않는다. 반대로 verifier가 왔는데 처음 요청에 challenge가 없었다면 PKCE 다운그레이드 시도로 보고 거절해야 한다. 이 짝 검증은 client_id와 인가 코드의 발급 이력에도 함께 묶여야 한다.
