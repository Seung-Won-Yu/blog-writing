한 줄만 다른 Promise 입력을 고른다

기존 CI가 린트하는 테스트 경로에서, 호출 대상의 반환 타입이 Promise라고 알 수 있는 작은 입력을 고른다. 가상의 함수 sendReceipt가 Promise<void>를 반환하고 호출 지점은 async 함수 안이라고 가정한다. 아래 표는 팀의 실제 설정으로 대조할 예시다.

정상 입력과 위반 입력의 예상 차이
입력기대하는 린트 결과
await sendReceipt()이 호출에서 no-floating-promises가 나오지 않는다.
sendReceipt()이 호출에서 @typescript-eslint/no-floating-promises가 나온다.

함수와 파일 위치, 설정을 그대로 두고 await의 유무만 바꾼다. 처음부터 여러 규칙을 동시에 건드리면 린트가 실패했을 때 어느 규칙이 반응했는지 판단하기 어렵다. 두 입력의 결과와 실행한 커밋을 같이 기록한다.

린트가 실패한 이유까지 읽는다

파일이 ignore에 걸리거나 프로젝트에 포함되지 않으면, 원하는 규칙까지 도달하지 못할 수 있다. 파서 오류만 나왔다면 설정을 먼저 바로잡는다. projectService를 쓰는 구성에서는 대상 파일이 어느 tsconfig에 속하는지 확인한다.

위반 입력에서 해당 규칙 ID로 실패정상 입력도 확인한 뒤 기존 린트 게이트가 동작했다고 기록한다.

CI 작업별로 전환 결정을 남긴다

공식 문서를 대조한 이 글의 판단은, 타입 검사기와 린트의 합격 조건을 분리하면 어느 작업을 전환하고 어느 작업을 유지할지 커밋 단위로 결정할 수 있다는 것이다.

가령 TypeScript 7의 진단이 기대와 같고, 기존 ESLint가 정상 입력을 통과시키면서 위반 입력에 지정 규칙 ID를 남겼다면 컴파일러 작업부터 바꿀 근거가 생긴다. 린트에서 실패하면 의존성이나 파일 범위를 확인하고 기존 린트 설정을 유지한다.

위반 입력은 임시 브랜치나 별도 검증 단계에서만 확인한다. 마지막에는 입력을 원래 상태로 돌리고, 평소 CI가 사용하는 명령으로 타입 검사와 린트가 모두 통과하는지 확인한다.

근거와 한계

정상 입력에 지정 규칙 ID가 없고 위반 입력에는 해당 ID와 차단 상태가 남으며 TypeScript 7 타입 검사 결과가 별도로 기록된다.

2026년 11월 13일에 공식 문서 다섯 곳을 대조했다. 예제는 판정 기준을 설명하는 입력이며 실제 패키지 설치, 린트 실행, CI 시간 측정은 하지 않았다.

이 판정은 선택한 Promise 규칙과 파일에 한정된다. 프레임워크 플러그인이나 별도 tsconfig를 쓰는 워크스페이스는 해당 작업이 읽는 설정으로 각각 확인한다. 린터가 새 TypeScript API 지원을 발표하면 지원 버전과 규칙 결과를 다시 확인한다.
