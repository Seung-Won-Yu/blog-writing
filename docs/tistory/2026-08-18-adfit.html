API 응답에서 상태값 하나를 읽으려는데 JSON 라이브러리부터 골라야 하는 순간이 있다. 작은 진단 도구나 단일 파일 스크립트라면 Jackson의 데이터 바인딩까지 필요하지 않아도 의존성 설정은 피하기 어려웠다. OpenJDK는 8월 17일 JEP 540 ‘Simple JSON API’를 JDK 28 대상으로 지정했다. JDK 안에서 JSON을 바로 파싱하고 생성할 수 있게 하되, 기존 라이브러리를 대체하지 않는 작은 도구로 경계를 분명히 그었다. 이 경계를 알아야 새 API를 편해서 쓰고, 큰 서비스에서 무리하게 끌고 가지 않을 수 있다.

JDK 28에 Simple JSON API가 들어간다

OpenJDK가 외부 의존성 없이 JSON을 파싱하고 생성하는 JEP 540을 JDK 28 대상으로 지정했다.

내장됐지만 기본으로 바로 켜지는 API는 아니다

JEP 540은 상태가 ‘Targeted’, 대상 릴리스가 JDK 28로 바뀌었다. 최종 표준 API가 확정됐다는 뜻은 아니다. 이름 그대로 인큐베이터 모듈이며 사용하려면 컴파일과 실행 때 --add-modules jdk.incubator.json을 명시해야 한다. 실행 시에도 인큐베이터 모듈을 쓴다는 경고가 나온다. API 모양이 피드백에 따라 달라질 수 있으므로 장기 운영 서비스의 공개 계약에 바로 박아 넣기보다 실험과 작은 내부 도구부터 시작하는 편이 맞다.

# 단일 소스 파일 실행
java --add-modules jdk.incubator.json Weather.java

# 컴파일 뒤 실행
javac --add-modules jdk.incubator.json WeatherCheck.java
java --add-modules jdk.incubator.json WeatherCheck

이번 변화가 반가운 곳은 배포 스크립트, 진단 CLI, 테스트 보조 도구처럼 ‘응답에서 값 몇 개만 읽는’ 코드다. 지금은 간단한 작업에도 Maven이나 Gradle에 JSON 의존성을 넣고 버전을 관리해야 한다. JDK 28 환경만 통제할 수 있다면 그 준비가 줄어든다. 반대로 여러 JDK 버전을 지원해야 하는 라이브러리나 안정된 API가 중요한 제품 코드는 인큐베이터가 끝날 때까지 기다릴 이유가 충분하다.

Json.parse 뒤에는 여섯 종류의 값만 남는다

중심에는 JsonValue가 있다. JSON의 문자열·숫자·불리언·null·객체·배열을 각각 대응하는 여섯 하위 인터페이스로 표현한다. Json.parse가 문자열이나 char[]을 읽으면 이 값들로 이루어진 메모리 트리가 만들어진다. 객체에서 키를 찾을 때 get("name"), 배열에서 순서를 찾을 때 get(0), Java 값으로 꺼낼 때 asString()·asInt() 같은 변환 메서드를 사용한다.

import jdk.incubator.json.Json;

String body = """
    {"user": {"name": "Mina", "level": 3}}
    """;

var json = Json.parse(body);
String name = json.get("user").get("name").asString();
int level = json.get("user").get("level").asInt();

System.out.println(name + " / " + level);

경로가 없거나 예상한 형식과 다르면 조용히 null을 돌려주는 대신 JsonValueException이 발생한다. 파싱 자체가 실패하면 JsonParseException에 루트에서 문제 값까지의 경로와 문서 안 위치가 담긴다. 작은 스크립트를 빠르게 쓰되 잘못된 구조를 일찍 드러내려는 설계다. 입력 형식이 자주 바뀌는 API라면 예외를 한꺼번에 잡기보다 선택 값 처리와 타입 분기를 코드에 명시해야 한다.

 

Jackson을 지우는 기능이 아니라 빈틈을 메우는 기능이다

OpenJDK 문서는 기존 JSON 라이브러리를 대체하지 않는다고 분명히 적었다. Simple JSON API에는 Java 객체와 JSON을 자동으로 오가는 데이터 바인딩이 없고, 큰 문서를 조금씩 읽는 스트리밍 API도 없다. 문서 전체와 파싱 결과가 메모리에 들어간다는 전제를 둔다. Jackson의 ObjectMapper로 요청 DTO를 변환하거나, 수백 MB 로그를 스트리밍하는 코드를 내장 API로 옮길 이유가 없다.

기능 수가 아니라 지금 처리할 JSON의 크기와 변환 방식으로 선택한다.
요구사항JDK 내장 API외부 라이브러리
작은 응답에서 값 몇 개 추출잘 맞음가능하지만 의존성 관리가 추가됨
JSON 생성기본 객체·배열 생성 가능복잡한 직렬화 규칙까지 지원
Java 객체 자동 매핑지원하지 않음Jackson·Gson·JSON-B가 적합
대용량 스트리밍지원하지 않음스트리밍 API가 적합
주석·후행 쉼표·JSON5지원하지 않음필요한 확장 문법을 지원하는 도구 선택
장기 호환성현재 인큐베이터라 변경 가능성숙한 버전 정책과 생태계

‘의존성이 하나 줄어든다’는 이유만으로 이미 안정적으로 쓰는 Jackson을 걷어내는 것도 이득이 적다. 변환 설정, 날짜 형식, 알 수 없는 필드 처리, 커스텀 직렬화가 축적된 서비스라면 교체 비용이 새 API의 단순함보다 크다. 새 도구에서 정말 필요한 기능이 트리 탐색뿐일 때 내장 API를 선택하고, 요구가 자라면 외부 라이브러리로 이동하는 순서가 자연스럽다.

엄격한 파서는 편의보다 모호함 제거를 먼저 택했다

파서는 RFC 8259에 맞는 JSON만 받는다. 사람이 편집한 설정 파일에서 자주 보이는 주석과 후행 쉼표는 허용하지 않는다. 같은 객체 안에 동일한 키가 두 번 등장해도 오류다. 일부 파서는 마지막 값을 남기고 일부는 첫 값을 남기는 중복 키를 허용하지만, JEP 540은 시스템마다 결과가 달라질 수 있는 모호함을 처음부터 차단한다. 기계 사이에 오가는 API 응답에는 장점이지만 JSONC나 JSON5 설정 파일을 그대로 읽으려는 경우에는 맞지 않는다.

숫자도 경계를 알아야 한다. asInt()와 asLong()은 범위를 벗어나면 거부하고, asDouble()은 지나치게 정밀한 값을 반올림할 수 있다. 금액처럼 정밀도를 잃으면 안 되는 값은 JSON 숫자의 문자열 표현으로 BigDecimal을 만들어야 한다. API가 짧아졌다고 입력 검증과 도메인 변환까지 사라지는 것은 아니다.

첫 적용 대상은 서비스 본체보다 작은 도구가 낫다

가장 안전한 시험대는 CI에서 API 응답 한 필드를 확인하는 스크립트, JDK 진단 결과를 읽는 도구, 테스트 픽스처를 검사하는 단일 파일 프로그램이다. 입력 크기가 작고 JDK 버전을 통제할 수 있으며, 실패하면 서비스 요청이 아니라 작업 하나만 멈춘다. 여기서 모듈 옵션, 예외 경로, 숫자 변환을 확인하면 운영 코드에 넣기 전 실제 마찰을 알 수 있다.

  • 문서 전체와 파싱 트리가 메모리에 들어가는 크기인지 확인한다.
  • 주석·후행 쉼표·중복 키가 포함된 기존 샘플을 실패 테스트로 둔다.
  • 객체 매핑이나 스트리밍이 필요해질 조건을 미리 적어 둔다.
  • 컴파일과 실행 환경 모두에 인큐베이터 모듈 옵션을 적용한다.
  • JDK 28 정식 출시 전 API 이름과 동작 변경을 다시 확인한다.

작은 도구에서 코드가 실제로 줄고 오류가 더 잘 보인다면 다음 내부 도구로 넓힐 수 있다. 반대로 예외 처리와 수동 매핑이 길어지기 시작하면 이미 외부 라이브러리가 해결한 문제를 다시 만들고 있다는 신호다. 내장 여부보다 요구사항을 가장 짧고 명확하게 표현하는 쪽을 고르는 것이 결국 유지보수 비용을 줄인다.

지금은 교체보다 경계 확인이 먼저다

JEP가 JDK 28 대상으로 지정됐어도 정식 출시와 표준화까지 설계는 바뀔 수 있다. 기존 서비스의 JSON 계층을 통째로 교체할 단계는 아니다. 대신 작은 입력과 실패 샘플을 준비해 내장 API가 어느 정도의 코드를 줄이는지, 엄격한 파싱이 기존 데이터에서 무엇을 거부하는지 확인할 시점이다. 그 결과가 쌓이면 JDK 28 도입 때 ‘내장이라서’가 아니라 ‘우리 요구에 맞아서’ 선택할 수 있다.

JEP 540의 의미는 Java가 갑자기 완전한 JSON 프레임워크를 품는다는 데 있지 않다. 짧은 스크립트와 진단 코드에서 의존성 없이 엄격한 JSON을 다룰 작은 출발점이 생긴다는 데 있다. 객체 매핑이나 대용량 스트리밍이 필요해지는 순간에는 Jackson·Gson·Jakarta JSON으로 넘어가면 된다. API가 인큐베이터인 동안에는 운영 코드의 기본 선택으로 고정하기보다, 작은 도구에서 경계와 오류 메시지를 확인하는 방식이 가장 현실적이다. JDK 28 Early-Access 환경이 준비되면 같은 작은 JSON 예제를 내장 API와 기존 라이브러리로 각각 작성해 필요한 기능의 경계를 비교한다.
