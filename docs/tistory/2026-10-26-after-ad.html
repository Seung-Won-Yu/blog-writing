서울의 저장 오류와 LA의 표시 오류를 따로 재현한다

2026년 10월 26일 macOS·Node v20.20.2에서 같은 입력을 실제 실행했다. 아래는 그 출력의 핵심 값이다. 두 환경 모두 날짜 전용 파싱의 ISO 값은 2026-10-26T00:00:00.000Z로 같았고, 원본 문자열의 JSON 왕복도 2026-10-26이었다.

실제 Node 출력: 입력은 모두 2026-10-26
실행 TZgetDate 결과현지 자정의 ISO
Asia/Seoul262026-10-25T15:00:00.000Z
America/Los_Angeles252026-10-26T07:00:00.000Z

서울 실행에서 현지 자정을 toISOString().slice(0, 10)으로 자른 결과는 2026-10-25였다. LA 실행에서는 new Date(raw).getDate()가 25였다. 둘 다 하루 전 증상이지만 전자는 직렬화 뒤 잘라 낸 날짜, 후자는 같은 순간을 현지 날짜로 읽은 결과다.

브라우저 개발자 도구에서는 process.env.TZ 명령이 동작하지 않는다. 이 예제의 실행 환경은 Node다. 실제 화면은 지원 브라우저와 서비스의 시간대 조건으로 따로 검증해야 하며, 여기서 시스템 시계를 바꾸거나 운영 서버 설정을 수정할 필요는 없다.

생일·마감일은 문자열 경로부터 지킨다

HTML의 날짜 입력은 표시 언어와 별개로 value를 YYYY-MM-DD 문자열로 준다. 날짜만 저장하는 계약이라면 그 값을 Date로 바꾸지 않고 요청 본문에 담는 경로가 단순하다. 다음은 입력이 이미 검증된 날짜 문자열이라는 전제의 전송 형태 예시이며 실제 서버 요청은 실행하지 않았다.

// dateInput은 type="date"인 입력 요소라고 가정
const dateOnly = dateInput.value;
const payload = { dueDate: dateOnly };
// JSON.stringify(payload)를 전송하는 기존 경로에 사용
// new Date(dateOnly).toISOString()으로 바꾸지 않는다.

빈 문자열·존재하지 않는 날짜·허용 범위는 별도로 검사해야 한다. 브라우저의 입력 제한만으로 서버 검증을 대신하지 않는다. API와 DB도 날짜 전용 필드를 시각으로 자동 변환하지 않는지 확인해야 하므로 프런트엔드 한 줄 수정만으로 전체 왕복이 고쳐졌다고 판단하지 않는다.

달력 계산이 필요하면 Temporal.PlainDate처럼 시각과 시간대가 없는 날짜 타입이 의미에 맞는다. 도입 전에는 대상 런타임의 지원과 직렬화 경로를 확인한다. 이 실행의 Node20에서 Temporal을 실행한 결과나 전 브라우저 지원을 주장하는 것은 아니다.

예약 시각에 일괄 9시간을 더하면 다른 값을 망친다

실제로 시작 시간이 있는 회의·예약이라면 순간을 보존해야 한다. 이미 올바르게 저장한 UTC 타임스탬프에 9시간을 더하는 수정은 순간 자체를 바꾼다. 의도한 표시 시간대를 선택하는 작업과 잘못 파싱한 값을 고치는 작업을 분리한다.

필드 의미에 따라 수정 범위를 정한다
필드 의미보존할 것확대를 멈출 조건
생일·날짜만 정한 마감연월일 문자열API나 DB가 자정을 다시 붙임
이미 발생한 로그·결제 시각같은 순간표시 수정 뒤 타임스탬프가 바뀜
장소와 시간이 있는 예약현지 시각·시간대 규칙장소·시간대가 원본에 없음

장소가 있는 미래 일정은 고정 +09:00 문자열 하나로 모든 지역의 시간대 정책을 표현할 수 없다. 필요한 시간대 식별자와 애매하거나 없는 현지 시각의 처리 기준을 서비스 계약으로 정해야 한다. 날짜 전용 값 보존만으로 예약 시스템 전체의 시간 문제가 풀리지는 않는다.

저장 뒤 다시 열기까지 같아야 수정이 끝난다

테스트 입력을 저장하고 응답을 받아 화면에서 다시 연다. 날짜 전용 필드는 고른 연월일이 그대로인지, 시각 필드는 같은 순간을 의도한 지역으로 보여 주는지 다른 기준으로 확인한다. 월말·연말·윤일·빈 입력도 서비스가 허용하는 범위에서 포함한다.

  • 원본 2026-10-26이 요청·저장·응답·재표시에서 같은 날짜로 남는지 확인한다.
  • 서울과 LA 조건을 각각 검증하고 테스트 환경·브라우저·실제 결과를 기록한다.
  • 기존 정상 시각 필드의 타임스탬프와 표시가 바뀌지 않았는지 회귀를 확인한다.
  • 다른 날짜가 나오면 운영 데이터 일괄 변경을 멈추고 처음 달라진 경계로 돌아간다.

이미 저장된 값에 날짜 전용 입력과 실제 시각이 섞였다면 일괄 하루 더하기를 하지 않는다. 원본 날짜·요청 로그·필드 정의로 의미를 복원할 수 있는지 먼저 확인한다. 원본이 없으면 어떤 값이 틀렸는지 확정할 수 없는 기록도 남는다.

실제 WebKit 오류 보고 205652에는 시간대 없는 날짜·시각 문자열의 해석 차이가 기록돼 있다. 이는 2019년의 과거 사례이며 현재 Safari의 같은 결함이 남았다는 근거는 아니다. 오래된 실행 환경을 지원한다면 현행 명세를 읽는 것과 실제 기기 확인을 구분해야 한다.

재현은 macOS의 Node v20.20.2에서 두 TZ 환경으로 수행했다. 실제 브라우저 입력창·서버·DB 왕복이나 모든 브라우저의 호환성을 검증한 결과는 아니다.
