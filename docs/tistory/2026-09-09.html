비공개 패키지 업데이트가 갑자기 401로 멈추면 만료된 PAT부터 의심하게 된다. GitHub는 9월 8일 Dependabot이 비공개 GitHub Packages와 GHCR을 읽을 때 작업별 GITHUB_TOKEN으로 packages: read를 요청하도록 바꿨다. 패키지 설정에서 업데이트 저장소에 Read 접근을 줬다면 PAT 없이도 동작한다. 다만 외부 레지스트리와 명시한 인증 설정까지 사라진 것은 아니다.

IT 트렌드 해설

30초 요약

  • 비공개 GitHub Packages가 저장소에 Read 접근을 주면 Dependabot은 PAT 대신 작업별 자동 토큰으로 패키지를 읽는다.
  • 기존 PAT를 먼저 지우지 말고 패키지 접근 권한과 실제 업데이트 성공을 확인한 뒤 GitHub-hosted registry 항목만 제거한다.
  • 외부 레지스트리, 사설망, 명시한 registry 경로와 자격 증명은 이번 변경의 대체 대상이 아니다.

핵심 해설 · GitHub Changelog · 2026. 9. 8

Dependabot, 비공개 GitHub Packages에 자동 읽기 권한 지원

GitHub는 Dependabot이 *.pkg.github.com과 ghcr.io에서 비공개 패키지를 가져올 때 작업별 GITHUB_TOKEN으로 packages: read를 요청하도록 바꿨다. 6월 초기 배포에서 발견된 npm 라우팅 충돌을 보완해 자동 자격 증명은 명시적 설정 뒤의 fallback으로만 동작한다.

PAT 만료가 막던 구간을 패키지 권한이 대신한다

비공개 GitHub Packages가 소비 저장소에 Read 접근을 허용하면 Dependabot은 GITHUB_TOKEN에 packages: read를 받아 패키지를 내려받는다. 이전에는 read:packages 권한을 가진 PAT를 Dependabot secret과 dependabot.yml에 연결했고, 토큰이 만료되거나 소유자가 조직을 떠나면 업데이트가 다운로드 전에 멈췄다.

이제 패키지 설정에서 소비 저장소를 Manage Actions access에 추가하고 Read를 주면, Dependabot 작업이 자동 GITHUB_TOKEN으로 packages: read를 요청한다. 토큰은 쓰기나 삭제 권한을 뜻하지 않는다. 패키지를 다운로드하고 메타데이터를 읽는 범위다.

  • Dependabot이 읽는 주소가 *.pkg.github.com 또는 ghcr.io인지 확인한다.
  • 패키지 Settings의 Manage Actions access에서 소비 저장소에 Read를 부여한다.
  • 기존 PAT 항목을 남긴 채 Dependabot 업데이트를 한 번 재실행한다.
  • 패키지 다운로드와 registry 선택이 모두 맞으면 GitHub Packages용 PAT만 제거한다.

영향받는 저장소는 주소와 권한으로 먼저 가른다

새 경로는 GitHub가 호스팅하는 모든 GitHub Packages 생태계와 Container registry인 GHCR에 적용된다. npm, Maven, NuGet처럼 패키지 형식이 무엇인지보다 실제 registry 호스트가 GitHub인지가 첫 기준이다. 회사의 Artifactory, Cloudsmith, 사설 npm registry에는 같은 자동 토큰이 전달되지 않는다.

Dependabot 비공개 패키지 인증 경로 선택표
패키지 위치필요한 접근PAT 제거 판단

사설망 registry인증과 runner 네트워크 접근둘 다 별도 유지

패키지와 저장소가 같은 조직에 있다는 사실만으로 접근이 생기지는 않는다. granular permission을 쓰는 패키지는 설정 페이지에서 어느 저장소가 Read·Write·Admin 중 어떤 역할을 갖는지 따로 정한다. Dependabot에는 패키지 다운로드에 필요한 Read만 주는 것이 경계를 가장 분명하게 남긴다.

자동 자격 증명은 명시한 설정 뒤에서만 움직인다

GitHub는 6월 23일 이 기능을 처음 내놓았다가 일부 npm 업데이트가 공개 패키지를 GitHub Packages에서 찾는 충돌을 발견해 되돌렸다. 9월 재활성화에서는 자동 GitHub Packages 자격 증명을 fallback으로 제한했다. dependabot.yml에 명시한 registry 자격 증명과 정상적인 패키지 라우팅이 먼저다.

따라서 이번 변경은 모든 registry 설정을 지우라는 신호가 아니다. 같은 업데이트 블록이 npmjs.org와 npm.pkg.github.com을 함께 쓰거나 scope·replaces-base로 경로를 고정했다면, 인증 성공뿐 아니라 어느 registry에서 패키지를 해석했는지 로그를 함께 봐야 한다.

PAT는 한 번 성공한 뒤 한 항목씩 걷어낸다

가장 안전한 전환은 새 권한과 옛 PAT가 잠시 겹치는 방식이다. 먼저 패키지에 소비 저장소 Read를 주고 Dependabot의 수동 업데이트나 다음 예약 작업을 실행한다. 로그에서 비공개 패키지 다운로드와 버전 해석이 성공했는지 확인한 뒤 GitHub Packages를 위한 registry 항목과 secret만 제거한다.

삭제 뒤에는 같은 업데이트를 다시 실행해 PAT가 없어도 성공하는지 확인한다. 여러 생태계나 디렉터리를 한 파일에서 관리한다면 한 번에 모든 secret을 지우지 않는다. 어떤 업데이트 블록이 어느 registry를 쓰는지 표시해 두면 외부 자격 증명을 잘못 제거하는 일을 피할 수 있다.

401이 남으면 토큰보다 패키지 쪽 접근 목록을 본다

새 경로에서 가장 먼저 확인할 곳은 저장소의 Actions 권한이 아니라 패키지의 Settings다. Manage Actions access 목록에 Dependabot을 실행하는 소비 저장소가 있고 역할이 Read인지 본다. 패키지를 배포한 저장소와 실제로 가져다 쓰는 저장소가 다르면 이 목록을 빠뜨리기 쉽다.

  • 패키지 주소가 GitHub-hosted인지와 실제 package scope를 확인한다.
  • 업데이트를 실행하는 소비 저장소가 패키지 접근 목록에 있는지 본다.
  • 명시한 registry URL·scope·replaces-base가 기대한 경로를 가리키는지 비교한다.
  • 사설망이면 self-hosted runner의 DNS·방화벽·허용 IP를 별도 점검한다.

짧은 토큰이 업데이트 검토를 대신하지는 않는다

오랫동안 요청된 개선은 PAT의 수명과 회전 부담을 줄이는 것이었다. 2023년 공개 기능 요청도 짧은 작업 토큰이 없어서 긴 수명과 잦은 교체 사이를 선택해야 한다고 지적했다. 이번 변경은 그 인증 부담을 줄이지만 Dependabot이 만든 버전 변경의 호환성이나 공급망 위험까지 판정하지는 않는다.

Dependabot 연구에서도 자동 업데이트 도입 뒤 기술적 지연은 줄었지만 알림 피로와 업데이트 불신은 남았다. 인증이 편해져 더 많은 비공개 의존성이 업데이트 대상에 들어오면 PR 그룹·검토 담당자·테스트 기준은 오히려 더 분명해야 한다. 자동 토큰은 패키지를 가져오는 문을 고칠 뿐, 들어온 변경을 병합할지 결정하지 않는다.

장기 PAT 없이 Dependabot 업데이트가 같은 비공개 패키지를 내려받고 외부 registry 설정은 그대로 동작하면 전환이 끝났다.
