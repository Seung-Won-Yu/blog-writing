Ollama LiteLLM 연결: 직접 호출·SDK·Proxy 선택 기준

같은 Ollama 모델 앞에 직접 호환 API·앱 내부 SDK·별도 Proxy 중 어떤 연결 층을 둘지 고른다. 문헌 비교이며 실행 후기가 아니다.

세 연결 경로에서 새로 생기는 것은 무엇인가

앱 하나가 필요한 기능을 Ollama의 호환 API로 호출할 수 있으면 직접 연결부터 본다. Python 코드에서 여러 제공자를 같은 함수로 다루려면 SDK를, 여러 앱이 공통 접속점과 운영 정책을 공유해야 하면 별도 Proxy를 검토한다.

이 구분은 세 제품의 속도 순위가 아니다. 같은 Ollama 모델 앞에 어떤 연결 층을 둘지 정하는 표다. SDK를 쓴다고 Proxy 프로세스가 자동으로 생기는 것도 아니고, 관문을 둔다고 모델 실행 서버가 없어지는 것도 아니다.

  • 앱이 쓰는 요청 기능을 일반 대화·스트리밍·도구 호출 등으로 구분한다.
  • 호출할 앱과 모델 제공자가 각각 하나인지 여러 개인지 확인한다.
  • 제공자 전환을 앱 코드에서 다룰지 공통 서버의 설정에서 다룰지 정한다.
  • 선택 이유와 실제 요청 확인 결과, 아직 확인하지 않은 기능을 기록한다.

직접 연결은 호환 범위부터 읽는다

Ollama 공식 문서는 호환 클라이언트를 로컬 서버의 /v1/ 주소로 연결하는 예를 제공한다. 다만 전체 API가 아니라 일부 기능의 호환이다. 기존 클라이언트가 설치되어 있다는 사실과 앱이 쓰는 모든 기능이 지원된다는 사실은 다르다.

먼저 앱의 실제 요청과 공식 지원 항목을 맞춘다. 간단한 대화 요청이 된다는 이유로 상태를 이어가는 요청, 도구 호출, 이미지 입력까지 같다고 가정하지 않는다. 이 글은 해당 기능을 실행한 호환성 시험이 아니다. 공식 문서로 연결 구조를 비교한다.

여러 공식 문서를 엮은 이 글의 해석은, 모델 이름보다 호출 주체·코드 안의 변환·공통 접속점의 필요를 먼저 나누면 불필요한 관문 서버를 줄일 수 있다는 것이다.
