외부 기여자의 열린 PR 수를 제한했는데 Draft가 계속 쌓인다. GitHub PR 제한은 10월 8일부터 Draft도 포함하도록 선택할 수 있다. 공개 저장소 관리자는 상한 숫자뿐 아니라 포함 옵션과 예외 명단을 함께 확인해야 한다. Draft는 검토 준비 상태를 나타낼 뿐, 자동 검사 비용까지 막아 주는 표시는 아니다.

GitHub, 동시 PR 한도에 Draft를 포함하는 선택 설정 추가

기존 Draft 예외를 선택적으로 닫을 수 있게 됐다. 공개 저장소의 외부 기여자별 접수 한도와 예외, 검토 준비·CI 경계를 문서 비교로 정리한다.

Draft가 계속 쌓였다면 포함 옵션부터 확인한다

GitHub PR 제한은 이제 선택 설정으로 Draft까지 셀 수 있다. 공개 저장소의 쓰기 권한 없는 기여자가 대상이며, Draft 표시만 바꿔서는 대기 중인 작업 수를 줄일 수 없다.

변경 발표는 기존 예외를 닫을 수 있는 선택지를 추가했다는 뜻이다. 모든 저장소에서 자동으로 같은 설정이 켜졌다고 읽지 말고 자기 저장소의 현재 값을 확인한다. 관리 대상은 저장소 전체 PR 수가 아니라 한 외부 기여자가 동시에 열어 둔 PR 수다.

  • 공개 저장소의 외부 기여자별 열린 PR과 Draft를 구분해 현재 대기열을 확인한다.
  • 관리 화면에서 동시 PR 상한과 Draft 포함 옵션, 기존 예외 명단을 읽는다.
  • 정상 기여자의 작업 분할·검증 증거·응답 책임을 기준으로 한도와 예외를 결정한다.
  • 설정 저장 뒤 값을 재확인하고 기여 안내와 실제 접수 결과, CI 실행 기록을 대조한다.

이 순서는 실제 계정에서 시행한 결과가 아닌 문서 기반 점검안이다. 공개 저장소 관리자라는 전제를 먼저 확인한다. 쓰기 권한이 있는 내부 개발자의 PR이 많아지는 문제는 이 외부 기여자 상한만으로 해결되지 않는다.

같은 상한에서도 Draft 포함 여부에 따라 계산이 달라진다

10월 14일 확인한 한국어 공식 문서에는 여전히 Draft가 한도에서 제외된다는 설명이 남아 있었다. 같은 페이지의 영문판에는 포함 선택이 있다. 번역본만 보고 기존 예외를 현재 규칙으로 판단하지 말고 최신 변경 기록과 영문 설정 설명을 함께 대조한다.

다음 표는 동시 상한을 2로 정했다고 가정한 설명용 예시다. 추천 상한이나 실제 저장소의 측정값이 아니다. 쓰기 권한이 없고 예외 명단에도 없는 같은 기여자의 열린 PR만 비교한다.

가상 상한 2에서 Draft 포함 전후의 계산
현재 열린 작업Draft 제외Draft 포함
일반 PR 1개·Draft 1개1개로 계산2개로 계산
Draft 2개0개로 계산2개로 계산
일반 PR 2개2개로 계산2개로 계산

이 예시에서 포함 옵션을 켜면 일반 PR 하나와 Draft 하나가 같은 접수 공간을 사용한다. 다음 작업을 열기 전 기존 작업을 정리하는 판단이 필요해진다. 한도는 저장소별·사용자별이므로 서로 다른 사람의 PR을 합쳐 개인 상한 초과로 계산하지 않는다.

상한에 이미 도달했다면 기여자는 불필요한 열린 작업을 닫거나, 검토를 거쳐 병합되는 것을 기다릴 수 있다. 한도 공간을 만들려고 미검증 변경을 서둘러 병합하는 정책은 접수 부담을 배포 위험으로 옮긴다.

설정값과 기여 안내를 함께 맞춘다

공식 경로는 저장소 Settings에서 Moderation options, Interaction limits로 들어가 Pull request limits를 보는 것이다. 동시 상한을 고르고 Draft 포함 옵션을 확인한다. 관리 권한이나 해당 항목이 보이지 않으면 저장소 관리자에게 확인하고 다른 계정의 권한으로 우회하지 않는다.

영문 문서의 두 번째 설정 항목이 Draft 포함 선택이다. 이 선택 여부와 상한, 예외 명단을 함께 기록한다. 이 글에서는 독자의 저장소 설정을 대신 바꾸지 않았다. 실제 정책 변경은 해당 저장소의 관리자와 기여 규칙에 따라 결정한다.

기여 안내에는 Draft도 접수 공간을 쓰는지, 작업을 나누기 전에 무엇을 논의할지, 예외를 문의할 곳을 짧게 남긴다. 기여자가 제한에 걸린 뒤 처음 규칙을 알게 되면 열린 작업을 급히 닫거나 불필요한 권한 요청으로 이어질 수 있다.

예를 들어 의존 관계가 있는 세 변경을 순차 제출할지, 첫 변경을 먼저 검토한 뒤 다음 것을 받을지 정할 수 있다. 이는 편집자가 제안하는 운영 선택이다. GitHub가 모든 프로젝트에 같은 PR 개수나 제출 순서를 요구한다는 뜻은 아니다.

정상 기여자의 예외는 기여 결과와 책임으로 판단한다

공식 문서의 예외 명단은 신뢰할 수 있는 외부 기여자가 PR 한도를 넘을 수 있게 한다. 다른 권한을 늘리는 기능은 아니다. 그래서 여러 변경을 꾸준히 제출하는 사람에게 쓰기 권한을 주기 전에 접수 예외만 필요한지 구분할 수 있다.

예외 판단의 가상 사례를 보자. 반복 기여자가 서로 연결된 작은 변경을 올리고, 각 변경의 이유와 재현 결과를 설명하며, 리뷰 질문에도 응답한다면 병렬 작업을 허용할 근거가 생긴다. 계정 나이 또는 제출량만으로 검토 책임을 확인했다고 보지는 않는다.

10월 8일 공개된 독립 연구는 코드 리뷰 경험이 있는 31개국 실무자 239명의 설문을 분석했다. 응답자들은 AI 사용 여부 하나보다 범위·프로젝트 맥락·CI 밖의 검증·질문에 대한 응답·병합 후 책임을 함께 봤다. 이 결과는 실제 한도 설정의 절감률을 측정한 실험이 아니다.

이 연구를 바탕으로 한 운영 제안은 예외 요청에 “왜 여러 PR이 필요한가, 무엇을 확인했는가, 누가 응답하고 유지하는가”를 적게 하는 것이다. 작은 상한을 자동 품질 판정처럼 쓰지 않고, 예외도 검토 부담을 설명할 수 있을 때 선택한다.

예외와 작업 분할을 정할 때 남길 근거
상황먼저 확인할 근거운영 선택

리뷰 질문에 응답 없음담당자·후속 유지 계획새 접수 확대를 보류

Draft를 포함해도 CI와 검토 준비 상태는 별도다

Draft는 아직 검토 준비가 끝나지 않았다는 표시다. 검토 준비로 바꾸면 코드 소유자에게 리뷰가 요청되며, Draft인 동안은 병합할 수 없다. 이미 알림을 구독한 사람은 Draft로 바꿔도 구독이 해제되지 않는다. 따라서 Draft를 “아무 부담도 없는 메모”로 읽으면 안 된다.

GitHub Actions의 pull_request 이벤트는 기본적으로 opened·synchronize·reopened에 반응한다. 워크플로의 이벤트와 작업 조건에 따라 Draft에도 검사가 실행될 수 있다. Draft 표시 자체가 모든 빌드와 테스트를 멈추는 계약은 아니다.

PR 상한은 사람별 접수량을, Draft 상태는 검토 준비 여부를, CI 설정은 자동 검사 실행을 다룬다. 세 항목을 따로 확인해야 접수량을 줄인 뒤에도 남는 리뷰와 실행 비용을 설명할 수 있다.

실제 CI 부담을 볼 때는 자기 워크플로의 on, types, 작업 조건과 실행 기록을 읽는다. 접수 한도만 바꾼 뒤 빌드 시간 감소를 단정하지 않는다. 기존 PR의 업데이트와 재실행, 다른 이벤트가 남아 있으면 실행량은 다른 방향으로 움직일 수 있다.

  • 검토 준비 전 어떤 가벼운 검증을 할지 프로젝트에서 정한다.
  • 준비 완료 뒤 무거운 검사 결과가 모두 남았는지 실제 실행 기록으로 확인한다.

저장된 값과 실제 접수 결과가 다르면 멈춰 확인한다

정책 변경 뒤에는 저장된 상한·포함 옵션·예외 명단을 다시 읽고, 정상 기여자의 실제 접수 결과와 대조한다. 검토 목적으로 운영 저장소에 시험 PR을 대량 생성하지 않는다. 시험이 필요하면 관리자가 승인한 별도 검증 저장소와 안전한 기여 계정을 사용한다.

  • 기여자가 한도 이하인데 막힌다고 보고하면 먼저 같은 저장소의 같은 사용자에게 열린 일반 PR과 Draft를 확인한다. 다른 상호작용 제한도 별도로 존재하므로 메시지와 적용 정책을 함께 본다. PR 수만으로 원인을 확정하지 않는다.
  • 반대로 예상보다 많은 PR이 열렸다면 쓰기 권한·예외 대상·Draft 포함 값을 먼저 확인한다. 공지에는 기존 초과 PR의 자동 정리와 모든 상태 전환 시점의 세부 동작이 명시되지 않았다. 이미 열린 PR을 자동 폐쇄한다고 가정하지 않는다.

이 글은 공개 문서 비교다. 실제 저장소의 제한 설정을 바꾸거나 차단·CI 절감 효과를 측정하지 않았으며, 기존 초과 PR의 처리와 상태 전환 시점의 세부 동작은 공지로 확정하지 않는다.

정상 기여가 막히면 기존 설정 기록을 보존하고 한도 또는 포함 선택을 재검토한다. 곧바로 모든 사람에게 예외나 쓰기 권한을 주지 않는다. 예외의 대상과 이유, 문의 처리 경로를 남겨야 다음 관리자가 같은 상황을 다시 판단할 수 있다.
