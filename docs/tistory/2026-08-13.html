원격 MCP 서버를 여러 대로 늘렸는데도 특정 인스턴스가 죽을 때마다 일부 에이전트가 멈춘다면, 서버 수보다 세션이 먼저 문제일 수 있다. 2026-07-28 MCP 명세는 이 연결 고리를 프로토콜 기본값에서 없앴다. 이제 도구 호출은 이전 연결을 기억하는 서버가 아니라, 요청 하나만으로 처리할 수 있는 HTTP 엔드포인트를 목표로 한다. 다만 세션 헤더가 사라졌다고 애플리케이션의 상태까지 저절로 사라지는 것은 아니다. 주문 번호, 승인 단계, 장기 작업처럼 다음 호출로 이어져야 할 값은 요청마다 명시적으로 넘겨야 한다.

MCP는 Stateless가 되고, 개발자는 이것이 다시 API가 되는지 묻는다

MCP 2026-07-28 명세의 stateless 전환이 세션 기반 원격 도구 서버의 라우팅과 운영을 어떻게 바꾸는지 다룬다.

세션이 사라지면 요청은 어느 서버로 가도 된다

이전 Streamable HTTP 방식에서는 먼저 initialize를 호출하고 서버가 준 Mcp-Session-Id를 이후 요청마다 들고 다녀야 했다. 2026-07-28에서는 이 초기 연결과 프로토콜 세션이 제거됐다. 도구 호출 하나가 필요한 버전과 기능 정보를 스스로 포함하므로, 로드밸런서는 그 요청을 특정 인스턴스에 고정하지 않아도 된다.

이 변화가 곧바로 ‘MCP는 평범한 API다’라는 뜻은 아니다. JSON-RPC 도구 호출, 클라이언트 기능 협상, 다중 왕복 요청 같은 MCP 고유의 규칙은 남는다. 바뀐 것은 이 규칙을 연결을 열 때 한 번 교환하느냐, 각 요청에서 선언하느냐이다.

초기 연결 대신 _meta가 맡는 정보

새 명세에서 프로토콜 버전과 클라이언트 기능은 요청의 _meta에 포함된다. 서버는 선언되지 않은 기능을 가정하면 안 되며, 필요한 기능이 없으면 오류로 돌려줘야 한다. 따라서 서버 코드에서 세션 객체에 숨겨 둔 기능 협상 결과가 있다면, 요청 검증 단계로 옮길 대상인지 먼저 점검해야 한다.

프로토콜 세션과 애플리케이션 상태를 분리해 전환 범위를 확인한다.
기존 세션 중심stateless 중심운영에서 확인할 것
initialize 후 세션 ID 유지요청마다 버전·기능 선언SDK가 새 메타데이터를 보낼 수 있는가
특정 인스턴스에 고정어느 인스턴스나 처리공유 세션 저장소 의존을 제거했는가
연결 상태에 기능 보관필요한 상태는 명시적 참조업무 상태 핸들을 어디에 저장할 것인가

업무 상태까지 없애면 안 되는 이유

프로토콜 세션과 애플리케이션 상태는 다르다. 예를 들어 장바구니 ID, 승인 대기 단계, 비동기 작업의 진행 번호는 다음 호출에서 계속 필요하다. 이 값들을 서버 메모리에만 두면 stateless 라우팅에서 사라진다. 새 명세의 방향은 상태를 금지하는 것이 아니라, 필요한 상태를 요청 인자나 명시적 핸들로 전달해 어떤 인스턴스도 같은 저장소를 통해 해석할 수 있게 만드는 것이다.

이 구분은 장애 대응에서도 차이를 만든다. 프로세스 메모리에만 남은 값은 인스턴스 교체와 함께 사라지지만, 요청에 포함된 안전한 참조 값과 내구성 있는 저장소의 레코드는 다른 인스턴스에서도 다시 조회할 수 있다. 참조 값 자체에 사용자 정보나 권한을 담아 두기보다, 서버가 매 요청의 인증 정보와 함께 검증할 수 있는 식별자로 제한하는 편이 안전하다.

게이트웨이는 두 버전을 함께 열어 두는 편이 안전하다

새 버전은 호환성 단절을 포함한다. AWS AgentCore Gateway는 지원 버전 목록에 2025-11-25와 2026-07-28을 함께 두고, 클라이언트가 요청 헤더로 버전을 고르게 하는 방식을 제시한다. GitHub도 새 명세 지원 과정에서 Redis 세션과 요청별 깊은 패킷 검사를 줄였다고 밝혔다. 하지만 모든 클라이언트가 새 SDK를 쓴다는 보장은 없으므로, 서버와 클라이언트를 같은 날 한꺼번에 바꾸기보다 병행 지원이 먼저다.

병행 운영 중에는 실패를 하나의 ‘연결 오류’로 뭉뚱그리지 않는 것이 좋다. 지원하지 않는 버전, 누락된 클라이언트 기능, 애플리케이션 상태 참조의 만료를 서로 다른 관측 항목으로 남기면 어느 층에서 되돌려야 하는지 분명해진다. 새 버전의 호출 비율과 오류 비율이 안정된 뒤에만 구버전의 광고를 중단해야, 이전 SDK를 쓴 자동화 작업을 예고 없이 끊지 않는다.

전환 전에는 이 네 가지를 순서대로 확인한다

  • 클라이언트와 서버 SDK가 2026-07-28을 실제로 지원하는지 확인한다.
  • 세션 ID나 프로세스 메모리에 숨겨 둔 업무 상태와 권한 맥락을 목록으로 만든다.
  • 기존 버전과 새 버전을 동시에 광고하고, 새 헤더의 tools/list와 tools/call을 작은 트래픽에서 검증한다.
  • 새 버전 요청이 실패할 때의 응답과 롤백 기준을 정하고, 구버전 지원을 제거하기 전 관측치를 남긴다.

단순해진 라우팅이 인증을 대신하지는 않는다

세션이 없어진다고 인증과 권한 확인이 자동으로 단순해지는 것은 아니다. 명세는 OAuth와 OpenID Connect에 더 가까운 방향으로 권한 처리를 강화했지만, 서버는 매 요청의 토큰과 요청 범위를 계속 검증해야 한다. 특히 clientInfo는 표시·로그·디버깅용 자기 신고 값이라 보안 판단 근거로 삼으면 안 된다. stateless는 장애와 확장의 복잡도를 줄이는 설계이고, 권한 검증을 생략하는 설계가 아니다.

다음 배포에서 바뀌는 것은 서버 수가 아니라 경계다

MCP 서버가 세션을 잃어도 도구의 의미와 사용자의 권한은 남는다. 요청이 어느 인스턴스에 도착해도 같은 결과를 내도록 만들려면, 프로토콜 정보는 매 요청에 넣고 업무 상태는 명시적 저장소로 옮기며 클라이언트 버전은 병행 관리해야 한다. 이 세 경계가 분명해지면 로드밸런서는 더 단순해지고, 장애가 나도 특정 서버에 붙잡힌 연결을 복구하느라 멈추는 일은 줄어든다.

Stateless MCP의 핵심은 서버를 잊게 만드는 일이 아니라, 서버가 기억해야 할 것과 도구 호출이 함께 들고 가야 할 것을 분리하는 데 있다. 세션 저장소와 고정 라우팅을 없애기 전에 프로토콜 버전, 요청 메타데이터, 상태 핸들, 클라이언트 호환성을 각각 확인하면 장애 지점을 줄이면서도 필요한 작업 맥락은 유지할 수 있다. 운영 게이트웨이에 새 버전을 바로 기본값으로 바꾸기보다, 기존 버전과 함께 광고한 뒤 한 클라이언트의 `tools/list` 호출부터 새 헤더로 확인해 보자.
