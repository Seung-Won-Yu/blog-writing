로컬에서는 설치되는데 클라우드 빌드에서만 의존성 설치가 막힌다. Workers Builds npm 버전은 10월 23일 변경 이후 packageManager에 정확한 버전을 적어 지정할 수 있다. 다만 engines.npm이나 잠금 파일 하나만 믿어서는 설치 환경이 맞았는지 알 수 없다. npm 프로젝트를 배포하는 개발자라면 설정을 바꾸기 전에 실패 단계와 실제 사용 버전부터 대조하자.

IT 트렌드 해설

30초 요약

  • Workers Builds npm은 packageManager로 정확한 버전을 고른다. engines.npm과 잠금 파일은 맡는 일이 다르다.
  • 실패 단계와 버전 로그를 보존하고 검증용 브랜치에서 한 가지 조건씩 바꾼다.
  • 버전 고정은 잠금 파일 불일치나 모든 설치·배포 오류를 해결하지 않는다.

Workers Builds에서 npm 버전을 지정할 때 나눠 확인할 세 경계

새 버전 선택 기능을 engines.npm·빌드 루트·잠금 파일·npm ci의 조건과 연결해, 설치 실패를 안전하게 좁히는 판단 기준을 제공한다.

설치 오류라면 실제 npm 버전부터 대조한다

Workers Builds npm 버전은 package.json의 packageManager에 정확한 버전을 적어 지정한다. engines.npm만으로는 선택되지 않으며, 설치 도구를 고르는 잠금 파일도 따로 확인해야 한다.

  • 실패한 빌드의 의존성 설치 단계와 실제 npm·Node 버전을 확인한다.
  • 프로젝트 루트의 packageManager와 저장소 최상위의 같은 필드가 일치하는지 읽는다.
  • 선택한 npm의 정확한 버전과 npm용 잠금 파일을 함께 검토한다.
  • 검증용 브랜치에서 설치 로그·테스트·변경 파일을 대조한 뒤 적용 범위를 정한다.

대상은 Cloudflare의 Git 연결 빌드인 Workers Builds에서 npm 설치를 관리하는 개발자다. GitHub Actions에서 직접 배포하거나 로컬에서 Wrangler만 실행한다면 그 환경의 설치 설정을 따로 확인한다. Worker 실행 중의 오류도 이번 변경과 다른 경계다.

10월 23일 공식 발표는 의존성을 설치하기 전에 지정한 npm 버전을 설치한다고 설명한다. 로컬에서 작성한 잠금 파일을 클라우드에서도 같은 도구로 읽도록 맞출 선택지가 생긴 것이다. 모든 기존 프로젝트의 설치 오류가 자동으로 사라진다는 발표는 아니다.

지금 실패하지 않고 실제 버전도 의도와 같다면 급히 숫자를 바꿀 이유는 없다. 반대로 설치가 끝난 뒤 소스 컴파일에서 실패했다면 npm 버전 차이는 여러 가설 중 하나다. 마지막 오류 한 줄보다 처음 실패한 단계와 그 앞의 환경 기록을 보존한다.

engines는 요구 조건이고 packageManager는 선택값이다

engines.npm은 이 프로젝트에 맞는 npm 범위를 표현한다. npm 문서에서도 기본적으로 요구 조건을 알리는 필드로 설명한다. Workers Builds는 이 값을 npm 선택에 쓰지 않는다. 경고가 보였다는 사실과 원하는 버전이 설치됐다는 사실을 구분하자.

설정 세 가지가 맡는 일이 다르다
항목맡는 일단독으로 보장하지 않는 것
engines.npm사용 가능한 npm 범위 표현클라우드의 npm 선택
packageManager설치 도구의 정확한 버전 지정잠금 파일·의존성의 일괄 변환
package-lock.jsonnpm 의존성 트리 기록Node·OS까지 같은 실행 환경

아래는 공식 발표에 나온 버전 형식 예시다. 기존 package.json을 이 예시로 덮어쓰지 말고 최상위 객체에 필드를 추가한다. 11.19.1은 예시이며 모든 프로젝트에 대한 권장 버전이나 이 글에서 설치를 검증한 버전이 아니다.

{
  "packageManager": "npm@11.19.1"
}

정확한 버전을 사용하고 npm@^11 같은 범위는 쓰지 않는다. Workers Builds 문서는 버전 표현을 해석하지 못하면 기본 버전을 쓴다고 설명한다. 설정 파일을 저장했다는 사실만으로 적용 성공을 판단할 수 없는 이유다.

모노레포에서는 두 package.json의 값을 맞춘다

빌드 루트가 저장소 최상위가 아니라면 두 위치의 package.json을 읽을 수 있다. 두 파일에 packageManager가 있으면 같은 값으로 맞추라는 것이 공식 문서의 안내다. 충돌할 때 어느 쪽이 이긴다고 추측하지 말고 서로 다른 값을 없앤다.

가상의 모노레포에서 저장소 최상위는 npm@11.19.1, apps/web은 npm@10.9.2라고 하자. 먼저 대시보드의 빌드 루트와 두 파일을 읽어 충돌을 찾는다. 팀이 선택한 동일한 정확 버전으로 맞춘 뒤 검증용 브랜치의 로그에서 실제 선택을 확인하는 순서다.

버전 지정이 잠금 파일의 역할을 대신하지 않는다

Cloudflare 문서에서 packageManager는 도구의 버전을 정하고, 저장소 잠금 파일은 의존성을 설치할 도구를 정한다. pnpm용 잠금 파일을 남긴 채 npm 버전만 적었다면 npm 프로젝트로 전환됐다고 판단하지 않는다. 도구 전환은 별도의 변경으로 검토한다.

npm의 package-lock.json은 설치된 의존성 트리를 기록한다. package.json의 범위만 보고 매번 새로 해석하는 것과 달리 팀·배포가 같은 구체적인 의존성 상태를 공유할 기준이 된다. 설치 실패를 없애려고 이 파일을 먼저 지우면 비교할 정상 기준도 잃기 쉽다.

버전 선택, 설치 도구 선택, 의존성 재현을 서로 다른 확인 항목으로 나누면 packageManager 한 줄에 모든 실패 원인을 맡기지 않게 된다.

가상 상황에서 다음 확인 대상을 고른다
관찰한 상태다음에 볼 것
지정한 npm과 로그가 다름정확 버전 형식·읽힌 루트·해당 커밋
npm은 같은데 npm ci 실패package.json과 잠금 파일·설치 옵션
설치는 성공, 컴파일 실패빌드 명령·소스·환경 변수
네트워크 단계에서 실패접속 오류와 서비스 상태

같은 npm이어도 Node 버전·운영체제·네이티브 의존성·환경 변수까지 같아지는 것은 아니다. 버전 차이를 제거했다면 그 다음 실패 경계로 이동한다. 환경을 한꺼번에 바꾸면 통과해도 무엇이 해결했는지 알기 어려워진다.

npm ci를 쓴다면 오류를 감추기보다 불일치를 고친다

npm ci는 기존 잠금 파일을 요구하며 package.json과 맞지 않으면 잠금 파일을 고쳐 계속하지 않고 실패한다. package.json이나 잠금 파일을 쓰지 않는 설치 방식이라는 점이 배포 재현의 기준이 된다. 다만 기존 node_modules는 지우고 설치하므로 작업 중인 폴더에서 가볍게 실행할 읽기 명령은 아니다.

npm 문서는 잠금 파일을 만들 때 의존성 트리 모양에 영향을 주는 옵션을 썼다면 npm ci에도 같은 옵션이 필요하다고 설명한다. 버전을 맞췄는데도 실패하면 기존 .npmrc와 설치 명령을 함께 비교한다. 오류를 없애려고 새 옵션을 임의로 켜지 않는다.

node --version
npm --version

위 두 명령은 현재 셸이 쓰는 버전을 출력한다. 로컬 프로젝트 폴더에서 얻은 값과 클라우드 설치 단계의 로그를 비교한다. 빌드 명령에 출력 줄을 추가하면 자동 의존성 설치 뒤에 실행될 수도 있으므로, 설치 전에 실패했다면 그 줄의 출력은 남지 않을 수 있다.

잠금 파일이 실제로 오래됐다는 근거가 있으면 별도 검증 환경에서 의도한 npm과 옵션으로 갱신한다. diff에서 의존성이 예상 밖으로 넓게 바뀌면 적용을 멈추고 이유를 확인한다. 버전 고정 변경에 대규모 의존성 갱신을 무심코 섞지 않는 것이 비교를 쉽게 한다.

성공 로그와 되돌릴 기준을 같은 커밋으로 남긴다

검증용 브랜치에서 같은 커밋의 설치 로그, 실제 npm·Node 값, 테스트 결과를 기록한다. 설치 성공과 애플리케이션 테스트 성공을 구분하고, 둘 다 필요한 확인으로 남긴다. 정상 배포본과 설정 diff도 보존해야 문제가 생겼을 때 원인을 좁힐 수 있다.

새 실패가 나타나면 적용 확대를 중단하고 변경한 설정을 이전의 검토된 상태로 되돌리는 방안을 검토한다. 기본 버전을 다시 쓰는 것도 시간이 지나면 달라질 수 있으므로, 이전 성공 로그에 남은 실제 버전과 비교한다. 되돌린 사실만으로 복구 성공을 단정하지 않는다.

이 글은 공식 문서를 비교한 점검안이다. 실제 Workers Builds 프로젝트를 연결하거나 클라우드 설치를 실행하지 않았으며, 특정 저장소의 오류 해결을 보장하지 않는다.
