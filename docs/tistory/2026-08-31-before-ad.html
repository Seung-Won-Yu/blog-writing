자동 테스트·배포 작업(워크플로)이 Queued, 즉 대기 중인데 일을 맡는 전용 컴퓨터(셀프 호스티드 러너)는 Online으로 보일 때가 있다. 화면만 보면 멀쩡하지만, 등록 가능한 최저 버전과 실제 작업을 받을 수 있는 최신 범위는 다르다. 어디가 막혔는지 다섯 곳만 차례로 확인하면 원인을 빨리 좁힐 수 있다.

개발 가이드

30초 요약

  • 러너가 온라인이어도 버전·라벨·연결 조건이 맞지 않으면 작업은 대기 줄에 남을 수 있다.
  • 상태, 버전, 진단 로그, 네트워크, 작은 검증 작업의 다섯 곳을 순서대로 확인하면 원인을 좁힐 수 있다.
  • 클라우드용 일정과 사내 서버용 기준은 다를 수 있으므로 사용하는 GitHub 제품의 문서를 따로 확인해야 한다.

먼저 알아둘 말

워크플로
코드 검사·테스트·배포처럼 정해 둔 순서대로 자동 실행되는 작업 묶음이다.
러너
워크플로가 요청한 명령을 실제로 실행하는 컴퓨터나 컨테이너다.
대기 줄
실행할 작업이 적합한 러너를 만나기 전까지 순서를 기다리는 대기열이다.
라벨
GPU·운영체제처럼 작업에 맞는 러너를 찾기 위해 붙이는 구분 이름이다.
온라인
러너 프로그램이 GitHub에 연결돼 현재 작업을 기다리고 있다는 상태 표시다.

실전 가이드 · actions/runner · 2026. 8. 26

GitHub Actions Runner v2.337.0 공개, 30일 업데이트 기준 다시 시작

GitHub가 셀프 호스티드 Actions Runner v2.337.0을 공개했다. Enterprise Cloud는 8월 31일 구버전 등록 brownout 일정에 들어가며, 실행 러너는 각 새 릴리스 뒤 30일 안에 갱신해야 한다.

큐가 멈췄는데 러너는 온라인으로 보이는 이유

워크플로 작업은 runs-on 라벨에 맞는 러너가 연결되면 바로 배정될 것처럼 보인다. 하지만 실제로는 러너 서비스 연결, 라벨 일치, 사용 가능 상태, 서비스가 허용하는 버전 조건을 모두 통과해야 한다. 한 단계라도 맞지 않으면 작업은 Queued에 남는다.

설정 화면의 Idle은 러너가 연결돼 작업을 기다린다는 상태다. 그 표시만으로 버전 유효성이나 다음 재등록 성공까지 보장하지 않는다. GitHub도 오래된 러너는 새 등록에 실패하거나 기존 작업을 받지 못해 워크플로가 큐에 머물 수 있다고 안내한다.

2.329.0은 등록선이고 실행선은 계속 움직인다

GitHub Enterprise Cloud의 새 아키텍처에 러너를 등록하거나 재등록하려면 2.329.0 이상이어야 한다. 이 숫자는 영구 지원 버전이 아니다. 이미 등록된 러너가 계속 작업을 받으려면 새 러너 릴리스가 나온 뒤 30일 안에 갱신해야 한다.

셀프 호스티드 러너의 두 가지 버전 조건
구분기준놓쳤을 때확인할 곳
등록·재등록2.329.0 이상config 등록이 차단될 수 있음러너 버전과 brownout 일정
작업 실행각 새 릴리스 뒤 30일 이내새 작업이 큐에 배정되지 않음릴리스 날짜와 현재 버전
중요 보안 업데이트공지된 즉시 기준패치 전까지 큐 배정 중단 가능보안 공지와 릴리스 노트

메이저·마이너뿐 아니라 패치 릴리스도 30일 계산의 새 기준이 된다. 8월 26일 공개된 v2.337.0처럼 최신 릴리스가 보이더라도 점진 배포 때문에 조직 설정의 다운로드 안내에는 다른 버전이 제시될 수 있다. 조직에 실제 제공된 버전을 기준으로 확인한다.

상태·버전·로그를 한 번에 모아 원인을 좁힌다

먼저 저장소·조직·엔터프라이즈 설정의 Actions → Runners에서 이름, 라벨, 상태, 버전을 본다. 여러 러너를 운영한다면 API로 목록을 내려받아야 누락을 줄일 수 있다. 이 작업에는 러너 조회 권한이 있는 인증이 필요하다.

# 조직 러너의 이름·상태·버전·라벨 목록
gh api --paginate /orgs/ORG/actions/runners \
  --jq '.runners[] | [
    .name,
    .status,
    .version,
    (.labels | map(.name) | join(","))
  ] | @tsv'

# 고정 Linux 러너 서비스와 최근 자체 업데이트 흔적
cd /opt/actions-runner
./svc.sh status
grep -h 'SelfUpdater' _diag/Runner_*.log | tail -20

러너 디렉터리의 _diag/Runner_*.log에는 연결과 자체 업데이트 기록이, Worker_*.log에는 개별 작업 실행 기록이 남는다. 일회성 러너는 종료와 함께 로그가 사라질 수 있으므로 외부 로그 저장소로 전달해야 원인을 재구성할 수 있다.

버전이 최신인데도 큐가 멈추면 라벨, 서비스 프로세스, 포트 443 통신을 차례로 본다. config.sh --check는 필요한 GitHub 서비스 연결을 검사하고 실패 항목의 로그 경로를 알려 준다. TLS 검증 해제는 상시 해결책이 아니라 진단용 마지막 수단이다.
