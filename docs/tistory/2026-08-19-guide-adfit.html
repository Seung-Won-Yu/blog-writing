주문 저장은 실패했는데 감사 로그만 남았거나, 예외를 잡아 처리했는데 마지막 commit에서 UnexpectedRollbackException을 만난 적이 있다. Spring의 @Transactional은 메서드 이름표가 아니라 이미 열린 물리 트랜잭션에 참여할지, 새 거래를 열지 정하는 규칙이다. 이 글은 REQUIRED와 REQUIRES_NEW가 데이터베이스 커넥션·롤백 표식·재시도와 어떻게 연결되는지 코드와 점검 순서로 풀어낸다.

Spring @Transactional 전파와 롤백 규칙을 서비스 경계에서 점검하는 법

기본 REQUIRED는 기존 물리 트랜잭션에 참여한다. 독립 기록이 필요할 때만 REQUIRES_NEW를 쓰고 커넥션 풀과 재시도 규칙을 함께 점검한다.

예외를 잡았는데 왜 마지막 commit에서 실패할까

주문 처리 중 재고 부족 예외를 내부 서비스가 잡고 감사 로그만 남긴 뒤 정상 반환했다. 그런데 외부 메서드가 commit할 때 UnexpectedRollbackException이 터지면, 원인은 마지막 줄이 아니라 이미 같은 물리 트랜잭션에 찍힌 rollback-only 표식일 수 있다. Spring 기본 전파 REQUIRED는 현재 거래가 있으면 새 거래를 만들지 않고 그 거래에 참여한다.

트랜잭션은 데이터베이스에 보낼 SQL 묶음이며, Spring의 프록시는 메서드 경계에서 시작·참여·종료를 정한다. PostgreSQL은 명시적 BEGIN 없이도 문장 하나를 거래로 처리하지만, 서비스 작업이 여러 변경을 묶어야 한다면 어느 호출이 같은 커넥션과 commit 결과를 공유하는지 먼저 그려야 한다.

REQUIRED는 논리적 경계가 여러 개여도 같은 물리 거래를 쓴다

외부 주문 서비스와 내부 재고 서비스가 모두 REQUIRED라면 둘은 하나의 데이터베이스 거래에 참여한다. 내부에서 RuntimeException이 밖으로 전파되면 기본 롤백 규칙이 적용된다. 내부가 예외를 잡더라도 명시적으로 rollback-only가 되었다면 외부 호출자가 성공을 가정한 commit은 허용되지 않는다.

@Transactional
public void place(OrderCommand command) {
  inventory.reserve(command.sku());   // REQUIRED: 외부 거래 참여
  audit.writeAccepted(command.id());  // REQUIRES_NEW: 독립 기록
}

@Transactional(propagation = Propagation.REQUIRES_NEW)
public void writeAccepted(UUID orderId) {
  auditRepository.save(new AuditLog(orderId));
}

이 코드에서 감사 로그를 독립시키는 이유는 주문 성공 여부와 다른 보존 정책이 있기 때문이어야 한다. 단지 예외가 보기 싫다는 이유로 분리하면 호출자는 어느 데이터가 실제로 commit됐는지 알기 어려워진다.

REQUIRES_NEW는 실패를 격리하지만 결과까지 자동으로 일관되게 만들지는 않는다

REQUIRES_NEW는 외부 거래를 중단하고 독립 물리 거래를 연다. 따라서 감사 로그·실패 알림처럼 주문 본문이 취소되어도 남아야 하는 기록에는 맞을 수 있다. 반대로 주문 상태와 결제 상태처럼 함께 성공하거나 함께 취소되어야 하는 데이터를 분리하면, 외부 실패 뒤 내부 기록만 남는 부분 성공을 설계로 받아들여야 한다.

독립 기록을 선택했다면 그 기록도 실패할 수 있음을 호출자에게 숨기지 않는다. 주문 성공 이벤트를 감사 테이블에 먼저 독립 저장하고 메시지 발행을 뒤에 붙이면 발행 실패, 재시도, 중복 기록의 기준이 필요하다. 외부 거래의 성공 여부를 사실로 기록해야 한다면 아직 commit되지 않은 상태를 성공으로 남기지 않도록 after-commit 이벤트나 outbox 패턴처럼 전달 시점을 분리해 비교한다.

독립 거래는 추가 데이터베이스 커넥션을 얻는다. 여러 요청이 외부 거래를 잡은 채 내부 REQUIRES_NEW를 기다리면 풀 크기가 동시 작업 수보다 충분하지 않을 때 대기와 교착 상태가 생길 수 있다. Spring 문서는 이러한 경우 풀에 동시 스레드 수보다 최소 하나 더 여유가 필요하다고 설명한다. 실제 값은 외부 거래 시간·동시성·다른 소비자까지 포함해 부하 시험으로 정한다.

검사 예외는 기본으로 rollback되지 않는다

@Transactional의 기본 규칙은 RuntimeException과 Error에서 rollback하고, checked exception에서는 commit한다. 비즈니스 예외를 검사 예외로 표현했다면 의도를 코드에 남겨야 한다. catch한 뒤 예외를 다른 타입으로 바꾸는 경로도 같은 기준으로 리뷰한다. 패턴 문자열보다 클래스 기반 rollbackFor가 의도하지 않은 매칭을 피하기 쉽다.

프록시 방식이라는 점도 함께 확인한다. 같은 클래스의 메서드가 this로 서로를 호출하면 일반적인 프록시 경계를 통과하지 않아 annotation의 전파 설정이 적용되지 않을 수 있다. 전파가 필요한 작업은 별도 Spring 빈으로 분리하거나 설계를 바꿔 실제 호출 경계를 테스트한다. 테스트에서는 최종 데이터만 보지 말고 예외 뒤 어떤 SQL이 commit됐는지와 활성 커넥션 수를 함께 남긴다.

@Transactional(rollbackFor = StockUnavailableException.class)
public void reserve(String sku) throws StockUnavailableException {
  if (!stock.hasEnough(sku)) {
    throw new StockUnavailableException(sku);
  }
  stock.decrease(sku);
}

PostgreSQL의 직렬화 실패는 애플리케이션 재시도가 필요하다

격리 수준은 전파와 다른 축이다. Spring에서 isolation은 새 거래를 시작하는 REQUIRED 또는 REQUIRES_NEW에만 적용된다. PostgreSQL Serializable은 직렬화할 수 없는 동시 실행을 감지하면 SQLSTATE 40001로 실패시킬 수 있으므로, 사용자는 실패한 거래 전체를 안전하게 재시도할 수 있게 만들어야 한다. 내부 일부 SQL만 다시 실행하면 읽기·쓰기 전제가 달라질 수 있다.

배포 전에는 경계·예외·풀을 한 번에 확인한다

  • 서비스 호출 그래프에서 REQUIRED, REQUIRES_NEW, 비동기 경계를 표시하고 각 데이터가 외부 실패 뒤 남아도 되는지 합의한다.
  • 각 예외 타입의 rollback 규칙과 catch 후 변환 경로를 통합 테스트로 확인한다.
  • REQUIRES_NEW 경로가 있다면 HikariCP 대기 시간·활성 커넥션·타임아웃을 부하 조건에서 관측한다.
  • Serializable 또는 명시 잠금을 쓴다면 SQLSTATE 40001 재시도 범위와 멱등성 키를 거래 전체 기준으로 검증한다.

같은 작업은 함께 취소하고, 독립 기록은 의도적으로 따로 commit한다는 기준이 먼저다. 그 다음에 전파 옵션, 예외 규칙, PostgreSQL 재시도, 커넥션 풀 용량을 한 흐름으로 테스트하면 annotation 한 줄로 생기는 뜻밖의 부분 성공을 줄일 수 있다.
