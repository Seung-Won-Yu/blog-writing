단계보다 먼저, 끝났다는 기준을 알려주세요

“이거 개선해 줘”라는 요청은 무엇을 바꿔도 개선이라고 주장할 여지를 줍니다. 모델 단계를 올리기 전에 작업의 끝을 좁혀 주는 편이 좋습니다.

예를 들어 함수 설명을 맡긴다면 이렇게 요청할 수 있습니다.

이 함수의 입력·출력·예외를 설명하는 주석만 다듬어 줘. 실행 코드는 바꾸지 말고, 코드에서 확인할 수 없는 동작은 추측하지 마. 수정한 설명을 실제 코드와 대조해 줘.

오류 조사라면 요청도 달라집니다.

아직 코드는 수정하지 말고 원인 후보를 세 개 이내로 정리해 줘. 각 후보의 근거, 반대 증거, 확인할 테스트를 함께 제시해 줘. 확인된 사실과 추측을 구분해 줘.

이 예시들은 직접 측정한 성능 실험 결과가 아닙니다. 일을 작게 나누고 결과 확인 기준을 붙이는 편집자의 사용 제안입니다. 어떤 단계를 쓰든 로그인 정보, 고객 자료, 공개하면 안 되는 코드를 무심코 포함하지 않는 것도 별도 확인 사항입니다.

Auto가 일을 나눠 맡기는 이유

모델 자동 선택은 식당에서 모든 주문을 가장 오래 걸리는 조리법으로 처리하지 않는 것과 비슷합니다. 중요한 것은 가장 큰 도구를 쓰는 일이 아니라, 요청을 제대로 끝낼 도구를 고르는 일입니다.

GitHub 설명에 따르면 Auto는 작업 복잡성과 모델의 가용 상태를 함께 고려합니다. 사용자가 정한 단계는 그 선택에 방향을 주는 설정이지, 특정 모델을 고정하는 이름표가 아닙니다. Auto 동작 설명

이런 선택 문제는 연구에서도 다룹니다. RouteLLM은 요청에 따라 강한 모델과 더 가벼운 모델을 나누어 사용하면서 비용과 품질의 균형을 찾는 연구입니다. 다만 Copilot이 이 논문의 구현을 사용한다는 뜻은 아니며, 논문의 실험 수치를 Copilot의 절감 효과로 옮겨 쓰면 안 됩니다. RouteLLM 논문

독자에게 필요한 요점은 하나입니다. Auto를 쓴 뒤에도 내가 맡긴 일의 결과가 맞는지는 확인해야 합니다. 자동 선택은 검수의 대체물이 아닙니다.

무엇을 기록하면 내게 맞는 선택인지 알 수 있을까

단계를 바꿀 때마다 막연히 “더 똑똑한 느낌”만 남기면 다시 같은 고민을 하게 됩니다. 다음 세 가지 정도만 기록해 보세요.

  • 처음 요청으로 쓸 만한 결과가 나왔는가.
  • 내가 다시 설명하거나 수정한 부분은 무엇인가.
  • 확인 가능한 사용량과 기다린 시간은 어느 정도였는가.

두 단계를 비교한다면 가능한 한 같은 작은 작업과 같은 완료 기준을 사용하세요. 요청 자체가 다르면 결과 차이가 모델 선택 때문인지 구분하기 어렵습니다. 한 번의 성공이나 실패로 모든 작업에 대한 우열을 정하지 않는 것도 중요합니다.

실무에서는 응답 하나의 비용뿐 아니라 다시 설명하고 고치는 노력도 부담입니다. 그래서 “항상 가장 가볍게”와 “항상 가장 강하게” 사이에 내 작업별 기준이 필요합니다.
