# 화면 검수 사전점검과 재개 계약

월~금의 모든 활성 편집 계약에 적용한다. 종료 전 토요일 글의 재검증에도 적용한다. 기존 계약의 `COMPLETE` 즉시 종료나
`READY` 스테이징 안내보다 이 문서의 검수·배포 상태 구분이 우선한다.

## 예약 검수: 앱 패널 없이 전용 Playwright로 실행 (2026-11-03)

사용자는 2026-11-03 **예약 검수만 로그인 정보가 없는 전용 자동 브라우저로 전환**을
승인했다. 평소 결과 확인과 발행 도우미는 계속 앱 내에서 연다. 이 절차는 예약에서
앱 내 브라우저 연결을 필수로 요구하던 이전 지시보다 우선한다. 브라우저 제공 여부나
패널의 queued 상태를 예약 글 제작·검수·GitHub 배포의 선행조건으로 삼지 않는다.

### 제작 전에 확인

저장소 상태·기존 산출물 확인 후 **리서치·새 원고·이미지 생성 전에** 실행한다.

```bash
sh scripts/blog-env python3 -m blog_pipeline.publishing.browser_qa --preflight
```

- 실제 publish_ready 메타와 존재하는 미리보기 파일에서 원고 ID를 선택한다.
  제작·보완일로 preview/YYYY-MM-DD.html을 추측하지 않는다. 10월 30일 보완본의
  ID는 2026-08-08-automation이며 2026-10-30.html을 새로 만들지 않는다.
- 명령은 선택 HTML·WebP·CSS만 제공하는 127.0.0.1 임시 서버와 로그인 없는 새
  Chromium context를 사용한다. 포트는 OS가 배정한다. 사용자 프로필·쿠키·Chrome
  탭·앱 패널에 접속하지 않으며 선택 서버 이외의 브라우저 요청을 막는다.
- 실제 1280×900 / 390×844, HTTP 200·정확한 제목·전체 이미지 로딩·표 내부 너비를
  검사하고 PNG·측정 JSON·최종 입력 해시를 임시 폴더에 보관한다. 서버와 브라우저는
  종료 시 닫힌다. 두 화면 CAPTURED는 QA_ENV_READY이며 **당일 글의 최종 QA 통과는 아니다**.
- 최초 설치 또는 설치 파일 누락 시 저장소 .venv에서 아래 고정 의존성을 준비한다.
  매번 재설치하지 않는다. 시스템 Python·Xcode·전역 보안 설정은 바꾸지 않는다.

```bash
sh scripts/blog-env python3 -m pip install -r requirements-browser.txt
sh scripts/blog-env python3 -m playwright install chromium --only-shell
```

서버 bind·브라우저 프로세스 실행이 제한된 경우 같은 명령을 제공되는 정식 승인
절차로 요청한다. 이 명령은 이미 승인된 선택 원고의 로컬 검수이며 외부 공개·로그인·
다른 프로젝트 접속이 아니다. 명시적 승인 또는 브라우저 보안 거절은 우회하지 않는다.
앱 패널이 없다는 사실은 해당 실행에 대한 보안 거절이 아니다.

환경 준비 실패 시 QA_ENV_BLOCKED를 기록하되 허용된 조사·텍스트 집필까지 중단하지 않는다.
보존 경로는 .local-drafts/YYYY-MM-DD.md와 같은 날짜의 .status.md이며 상태는
DRAFT_QA_PENDING이다. Git 추적·Pages·발행 도우미 입력에서 제외한다. 새 이미지·최종
게시 번들·공개 배포는 실제 QA 복구 전 보류한다. 과거 채팅이나 삭제된 세션은 입력이
아니며 당일 초안이 있으면 누락된 단계부터 재개한다. 과거 날짜의 보완은 사용자 요청이
있을 때만 한다. HTTP 404·다른 글·브라우저 부재·프로세스 권한 실패를 구분해 기록한다.

### 최종 원고와 배포 후 검수

기존 글 개선은 원래 ID를 쓴다. 날짜를 오늘로 바꾸거나 복제 글을 만들지 않는다.

```bash
sh scripts/blog-env python3 -m blog_pipeline.publishing.browser_qa --draft-id ACTUAL_DRAFT_ID
```

출력한 evidence_dir/capture.json의 desktop·mobile JSON을 읽고, 대상별 PNG를
`view_image` 같은 제공된 파일 이미지 도구로 열어 실제로 검수한다. 이미지 열기에 앱 패널은
필요하지 않다. CAPTURED/METRICS_PASS는 수치·캡처 성공이며 시각 승인·8.5 점수·발행 허가가
아니다. 이미지 한글·화살표·말풍선·잘림, 표 줄바꿈·가로 스크롤, 광고 경계와 읽기 순서를
직접 확인한다. 긴 full 캡처만 보지 말고 image/table/code/heading의 화면 캡처도 본다.
검수 결과·확인한 파일·한계·capture.json의 해시를 같은 폴더의 visual-review.json 또는
실행 기록에 남긴다. 해시가 달라졌으면 영향받은 화면을 다시 검수한다. 원고가 캡처 중
바뀌면 STALE_INPUTS이고 완료가 아니다. 이전 성공 manifest로 실패를 덮지 않는다.

배치 실패는 해당 부분을 같은 실행에서 고치고 다시 검사한다. 가드·테스트와 시각 검수가
끝나야 커밋·push한다. Actions/Pages 전파 완료 후에는 다음 명령으로 최종 공개 파일
바이트와 실제 배치를 확인한다. 공개 URL은 원고 ID에서만 만들고 로컬 최종 파일과 대조한다.

```bash
sh scripts/blog-env python3 -m blog_pipeline.publishing.browser_qa --draft-id ACTUAL_DRAFT_ID --published
```

이 모드는 이미 배포한 blog-writing Pages 경로만 읽으며 선택 HTML·CSS·이미지가
로컬 최종본과 다르면 PUBLIC_ARTIFACT_MISMATCH다. 공개 전파 지연은 배포 실패와
구분하고 기존 제한 재시도 계약을 따른다. 미검수 원고를 먼저 공개하는 수단으로 쓰지 않는다.
평소 사용자가 여는 주소는 도우미 홈 또는 ?draft=실제ID다. 공개 본문 대조는 제공된
웹 조회 도구로 진행할 수 있고, Search Console의 로그인 접근이 안 되면 SEARCH_DEMAND의
유효한 관측 캐시를 사용한다. 개인 로그인 프로필을 전용 브라우저에 복사하지 않는다.

## 2026-10-28 추가: 표·이미지 배치 완료 조건

월·수·금 신규 글과 화·목 개선 모두에 적용한다. 본문·이미지를 고친 경우 해당 원고의
마지막 HTML과 CSS로 PC 1280px / 모바일 390px를 실제 확인한다. 뷰포트 설정 호출의
성공만 믿지 말고 페이지의 실제 `innerWidth`가 목표와 일치하는지도 기록한다.
CSS·HTML·이미지가 바뀌면 영향을 받은 화면만 다시 확인하며 유효한 검수를 반복하지 않는다.

### 수치로 확인할 배치

`agent/browser-layout-audit.js`는 현재 열린 본문 DOM만 읽는 측정식이다. 예약의
browser_qa 명령이 이를 실행한다. 수동 앱 내 검수에서는 `tab.playwright.evaluate`에 전달한다. 페이지 내부
앱 상태·네트워크 요청·브라우저 보안 우회에는 사용하지 않는다.
파일의 UTF-8 문자열을 그대로 `tab.playwright.evaluate(scriptText)`에 전달하면
실행 결과가 반환된다. 이 측정식은 레이아웃·스크롤·페이지 내용을 변경하지 않는다.

- PC와 모바일 각각 실제 뷰포트·문서 폭, 표별 바깥/제목/머리글/본문/행 폭,
  이미지별 원본·표시 크기와 로딩 상태를 보존한다.
- 표 내부와 바깥 폭 차이는 테두리·반올림을 고려해 2px 이내여야 한다. 2열은
  래퍼 폭을 채우며 제목은 왼쪽 정렬한다. 3열 이상은 모바일에서 래퍼 안 스크롤을
  허용하되 문서 전체를 옆으로 밀어내면 실패다. 한글 단어와 긴 URL의 줄바꿈도 읽는다.
- 이미지가 지연 로딩 중이면 `IMAGES_PENDING`이다. 해당 그림까지 실제로 스크롤해
  다시 측정한다. 스크롤 전 미로딩을 깨진 이미지라고 단정하거나, 0장 로딩 상태를
  통과로 기록하지 않는다. 로딩 실패·0 크기·문서 밖 넘침·늘어난 비율은 수정 대상이다.
- `review`의 잘림/맞춤 항목은 실제 화면에서 핵심 대상·문자가 보이는지 별도 판정한다.
  `METRICS_PASS`는 배치 수치 통과일 뿐 최종 시각 검수 통과가 아니다.

### 눈으로 확인할 이미지와 읽기 순서

1. 대표 이미지: 원본 1200×630과 목록 축소 크기에서 초점·핵심 대상·문자 잘림을
   확인한다. 대표를 바꾸지 않은 기존 글은 유효한 이전 검수를 재사용할 수 있다.
2. 본문 이미지 전부: 원래 비율, 글자·한글·화살표·말풍선, 캡션과 설명하는 문단의
   연결을 확인한다. 그림이 다른 단계 아래에 있거나 설명 없이 끼어 있으면 고친다.
   크기 규격 통과만으로 이미지의 내용·배치를 통과시키지 않는다.
3. 각 화면에서 상단, 표, 본문 이미지와 캡션을 실제로 본다. 캡처를 합쳐 여러 항목을
   검증해도 되지만 보지 않은 부분까지 확인했다고 쓰지 않는다. 긴 전체 화면 캡처
   한 장만으로 모바일의 작은 글자를 검수하지 않는다.
4. 광고 전후 첫 문단·소제목·이미지가 잘리거나 잘못 붙지 않는지 확인한다. 광고
   설정은 변경하지 않는다. 로컬 미리보기에서 확인할 수 없는 실제 광고 모양은
   확인 불가로 구분하며 티스토리 발행을 대신하지 않는다.

### 실패 복구와 검수 기록

배치 실패는 같은 실행에서 해당 HTML·이미지·범위가 제한된 CSS를 고치고 다시 확인한다.
점수·검수 플래그만 바꾸거나 원고 전체를 다시 만들지 않는다. 저장소의 CSS 수정이
필요하면 공통 스킨·미리보기 사본·회귀 검사도 맞춘다. 티스토리 스킨 저장은 예약의
자동 권한에 포함되지 않으며, 실제 스킨 반영이 필요한 경우 적용 범위를 인계한다.
도구·보안 경계로 검수가 불가능할 때만 아래의 QA_BLOCKED 재개 규칙을 따른다.

실행 메모에 초안 ID, 마지막 HTML/CSS 해시, 실제 두 뷰포트, DOM 측정 JSON 경로,
캡처 경로, 표·이미지·캡션·대표 축소 확인 결과와 남은 한계를 기록한다. 임시 측정·
캡처는 `/tmp/blog-writing-qa/<초안 ID>/`에 두어 다음 예약의 작업 트리를 오염시키지 않는다.
소스 가드·테스트·수치 검사·시각 검수·Pages 배포 확인은 별도 결과로 보고한다.
배포 후 Pages의 최종 미리보기에서도 변경 부분과 이미지 로딩을 다시 확인한다.
실제로 발행하지 않은 티스토리 새 글을 공개 검수 완료라고 기록하지 않는다.

## 최종 검수와 중단 후 재개

### 제한된 로컬 미리보기 명령

수동 앱 내 미리보기가 필요하고 도구가 localhost를 허용하며 서버 실행 권한이 승인된 환경에서는
`sh scripts/blog-env python3 -m blog_pipeline.publishing.preview_server --draft-id YYYY-MM-DD`
를 사용한다. 준비 확인에는 이미 완성된 최근 원고 ID를 쓰고, 최종 확인에는 당일 ID를 쓴다.
여러 원고의 보완 요청은 `--draft-id`를 반복 지정할 수 있다.
수동 미리보기 서버가 출력한 `Preview ready: http://127.0.0.1:<port>/preview/YYYY-MM-DD.html`
주소를 그대로 인앱 브라우저에서 연다. 포트는 실행 때 빈 값으로 자동 배정되므로
과거 주소나 8765를 추측해 열지 않는다. 출력한 주소에서 선택 원고가 열리는지
확인하고, 다른 프로젝트의 서버가 사용 중인 포트는 종료하지 않는다.
선택한 미리보기 HTML·WebP·CSS만 제공하며 저장소 디렉터리, 원고 JSON, `.git`,
환경 파일은 제공하지 않는다. 검수 종료 후 Ctrl-C로 서버를 종료한다.
서버는 127.0.0.1에만 바인딩하며 외부 공개 호스트로 바꾸지 않는다.
이 명령은 보안 거절을 해제하거나 실행 승인을 대신하지 않는다. 앞선 거절이 있다면
정식 승인이 확인되기 전 실행하지 않는다. 단순 페이지 이동 시간 초과는 실제 화면과
서버 응답을 확인하여 구분하고, 로딩된 페이지를 보안 차단으로 오진하지 않는다.

- 사전점검에서 확인한 동일한 방식으로 최종 HTML을 데스크톱·390px 모바일에서
  실제 검수한다. 이미지 누락, 가로 넘침, 한글/말풍선 가독성, 광고 전후 연결을
  확인한다. 파일이 바뀌면 영향을 받은 화면을 다시 확인한다.
- 표는 바깥 `table` 너비만 검사하지 않는다. 2열/3열 각각 실제 `caption`·`thead`·
  `tbody`·행의 너비를 대조해 내부만 좁아지지 않았는지 확인한다. PC에서는 표 제목을
  왼쪽 정렬하고 머리글·본문 행이 표 폭을 채워야 한다. 모바일 2열은 본문 폭 안에서
  줄바꿈하며, 3열 이상은 필요한 경우 표 래퍼 안에서만 스크롤되어야 한다.
- JSON 가드 `COMPLETE`, 발행 묶음 `READY`, 테스트 성공, 자동 독자 점수는
  실화면 QA를 대신하지 않는다. 실제로 보지 않은 화면에 통과를 기록하지 않는다.
- 최종 QA가 막히면 `QA_BLOCKED`로 기록하고 원고·이미지·기존 스테이징을 보존한다.
  그 콘텐츠는 커밋·푸시·Pages 공개하지 않는다. `LOCAL_COMPLETE`라고 보고하지 않는다.
- 재개 시 `publish_bundle --resume-check`와 이전 실행 메모를 함께 확인한다.
  콘텐츠 `COMPLETE`여도 QA 증거가 없으면 종료하거나 스테이징부터 진행하지 않고
  **누락된 QA부터** 재개한다. 유효한 원고·이미지는 재생성하지 않는다.
- 이미 명시적으로 차단된 대상은 이 계약을 근거로 우회하지 않는다. 허용 경로 또는
  권한 변경이 정식으로 확인되기 전까지 해당 QA는 미완료로 유지한다.
- QA와 로컬 검증이 모두 끝난 뒤에만 `REPOSITORY_SYNC.md`에 따라 배포한다.
  게시 도우미의 Pages 확인과 티스토리 실제 발행은 별도이며 티스토리는 사용자가 한다.

사전점검은 뒤늦은 실패와 불필요한 재제작을 줄인다. 실행 중 권한·도구 상태 변화까지
막거나 이후 무중단을 보장하지는 않는다.
