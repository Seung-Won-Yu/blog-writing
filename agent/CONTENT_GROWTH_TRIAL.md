# 독자가 실제로 써먹는 IT — 6주 운영 전환

2026-10-12 사용자 승인에 따른 현재 편성이다. 이 문서는 개별 계약의 과거
화·목 신규 제작 지시보다 우선한다. 원고 스키마·이미지 진위·품질·QA·전송의
기존 경계는 유지한다. 삭제된 채팅을 입력으로 요구하지 않는다.

## 목표와 편성

목적은 **AI와 디지털 도구를 쉽게 활용하고 막히는 문제를 해결하도록 돕는 것**이다.
기술 이름·최신 발표만으로 주제를 고르지 않는다. 일반 사용자와 개발자를 한 글에
억지로 섞지 않고, 어떤 상황의 누가 어떤 일을 끝낼지 먼저 정한다.

| 09:00 KST | 실제 작업 | 새 글 역할 |
| --- | --- | --- |
| 월 | 반복되는 사용·설정·개발 문제를 해결하는 새 글 | `evergreen_problem` |
| 화 | 검색 반응이 있는 기존 글 한 편 개선 | 당일 신규 원고 없음 |
| 수 | 실제 변화 때문에 독자가 확인·수정해야 하는 새 글 | `change_explainer` |
| 목 | 기존 글 한 편의 이해도·실행성·색인 상태 개선 | 당일 신규 원고 없음 |
| 금 | AI·개발 도구의 구체적인 활용·선택을 돕는 새 글 | `developer_insight` |
| 토·일 | 정규 제작 없음 | 기존 자료 보존 |

오늘 완성한 월요일 글은 다시 만들지 않는다. 2026-10-13부터 새 편성을 적용한다.
첫 6주 종료 후 2026-11-23에 성과와 조정안을 점검한다. 자동으로 매일 새 글
체제로 복귀하거나 다른 주제로 전환하지 않는다. 검수된 결과만 사용자에게 인계한다.

```bash
sh scripts/blog-env python3 -m blog_pipeline.publishing.growth_plan --today
```

위 명령은 읽기 전용이다. 계획·관찰 기준·개선 큐는 `config/content_growth_trial.json`에 있다.
`refresh_existing`이면 `daily_guard --today`로 새 화·목 글을 만들지 않는다.
`off`이면 정규 제작을 하지 않는다. 큐가 비어도 개선 슬롯을 새 글로 대체하지 않는다.

## 2026-10-28 변경: 관측 검색어를 먼저 선정

다음 예약부터 `agent/SEARCH_DEMAND.md`를 읽고 `search_demand --today`를 실행한다.
실제 검색어와 기존 글의 공백을 먼저 확인한 뒤 수집기에서 근거를 찾는다. 편집 가설만으로
신규 주제를 확정하지 않는다. 아래의 가설 허용 문구보다 이 규칙이 우선한다.
새 질문이 없으면 해당 실행은 기존 글의 확인된 공백을 개선하며 새 글 개수를 채우지 않는다.

## 새 글: 수집기 추천보다 독자의 일 우선

1. 보존한 Search Console 검색어에서 질문을 고르고 기존 글의 답과 대조한다.
   댓글·막힌 장면은 보조 맥락이며, 검색어 관측을 대체하지 않는다. 검색량·댓글 수를
   만들지 않는다. 수집기 점수와 GitHub 인기도도 실제 독자 수요를 대신하지 않는다.
2. 기존 `editorial.value_review`의 독자·질문·출처 공백·기여와 `reader_path`를
   실제 본문에 연결한다. 제목의 답을 먼저 주고 실행·설정·판단의 완료 신호를 제공한다.
3. 기술 배경은 목적 달성에 필요한 만큼 설명한다. 쉬운 제목 뒤에 문서 요약을 쌓거나
   같은 답을 요약·본문·결론에서 반복하지 않는다. 글자 수를 늘리기 위한 심화를 넣지 않는다.
4. 사용·실행 결과를 주장하는 글은 안전한 실제 화면·출력·검증으로 확인한다.
   실행하지 못한 분석은 문헌 분석이라고 밝힌다. 원리·비교 글에 불필요한 실험이나
   가짜 경험을 요구하지 않는다. 비공개·개인 자료는 안전한 테스트 데이터로 대체한다.
5. 생성 그림은 원리 설명용이다. 실제 UI·결과의 증거 위치에는 실제 화면이나 검증
   기록을 쓴다. 이미지 규격은 유지하되 장수와 스타일 때문에 장식을 추가하지 않는다.
6. 질문·결론이 기존 글과 같으면 먼저 그 글을 개선한다. 후속 글은 별개의 검색 의도와
   새 결과가 있어야 한다. 내부 링크는 독자의 다음 일에 도움이 될 때만 연결한다.

월요일은 현재 유효한 문서와 재현 근거로 오래가는 문제를 고를 수 있다. 최근 7일
발표를 억지로 끼우지 않는다. 수요일은 실제 변화·신선도 기준을 유지하고 영향받는
독자와 지금 할 일을 분명히 한다. 금요일은 넓은 생태계 목록보다 구체적인 작업에
필요한 도구·스킬·문서와 선택 경계를 먼저 다룬다.

## 화·목: 기존 URL을 지키는 개선 흐름

1. `growth_plan`의 `target`, 기존 소스 JSON, 실제 공개 본문을 대조한다.
   `in_progress`는 누락 단계만 재개한다. `ready_for_review`는 사용자 확인 대기이므로
   다시 쓰지 않는다. 매핑이 다르면 본문·원고를 확인한 후 계획을 바로잡는다.
2. 화요일에는 가능한 경우 Search Console의 최근 28일/직전 28일 비교를 갱신한다.
   **페이지 합계와 검색어 합계를 합쳐 가짜 검색어×페이지 데이터를 만들지 않는다.**
   정확한 검색어 연결은 해당 페이지 필터로 확인한다. 로그인·접근이 막히면 최신
   확인 불가를 기록하고 기존 관찰·공개 본문으로 개선을 계속한다. 날짜만 바꾸어 최신
   통계처럼 쓰지 않는다. 30일 지난 피드백은 최신 선정 점수에 쓰지 않는다.
3. 제목·답·실행 순서·실패 안내·실제 화면·관련 링크를 읽고 가장 큰 공백 하나부터
   개선한다. 반응이 있는 답·명령·실험은 보존한다. 제목 변경은 검색어 구성과 내용
   일치까지 확인한 뒤 결정한다. 단어만 바꾸거나 분량만 늘리지 않는다.
4. 기존 JSON의 `draft_id`, `publish_date`, `scheduled_at`, 역할과 공개 URL을
   유지한다. 오늘 날짜의 복제 글이나 날짜만 갱신한 새 글은 만들지 않는다. 이미지는
   유효하면 재사용하고 낡은 화면·가독성 문제·설명 공백이 있을 때만 교체한다.
5. 기존 ID로 원고 검사·HTML·미리보기·번들·실화면 QA를 수행한다. 수정 전 원고의
   `COMPLETE`는 이번 변경 검사를 생략하거나 작업을 종료하는 근거가 아니다.

```bash
# 예시 ID는 실제 target.draft_id로 바꾼다. --today를 쓰지 않는다.
sh scripts/blog-env python3 -m blog_pipeline.publishing.daily_guard --draft-id 2026-09-03 --source-only
sh scripts/blog-env python3 -m blog_pipeline.publishing.export_tistory --draft-id 2026-09-03
# 미리보기 생성·화면 QA는 BROWSER_QA.md의 기존 경로를 따른다.
sh scripts/blog-env python3 -m blog_pipeline.publishing.publish_bundle --draft-id 2026-09-03 --check
```

6. 첫 세 대상은 `/197` im-not-ai, `/221` 시크릿 모드, `/209` WMIC이다.
   기존 사실·참조·실행 예제를 확인한 후 개선한다. 이 순서는 편집 판단이며 Google
   순위 규칙이 아니다. 이후에는 현재 성과와 색인 대기 글을 읽어 큐를 보충한다.
7. 완성본은 Pages 도우미에 배포하고 **기존 공개 글 교체용**으로 인계한다.
   기존 URL·원고 ID·변경 요약·미리보기를 함께 준다. 티스토리 저장·광고 설정·
   재심사는 자동 수행하지 않는다. 동일 제목의 새 글로 발행하도록 안내하지 않는다.
   `?draft=<기존 draft_id>` 도우미 링크로 해당 원고를 바로 열 수 있다. 큐 상태를
   `ready_for_review`로 바꾼 뒤 도우미를 다시 만들면 기존 글 교체용 표시와 대상 URL이 나온다.
   이번 보완의 검수가 실제로 완료된 한국 날짜를 큐의 `refreshed_on`에
   `YYYY-MM-DD`로 기록한다. 도우미는 이 보완일과 새 글의 원고 날짜를 함께 최신순으로
   정렬하고 가장 최근 작업을 기본 선택한다. 최초 발행일·원고 ID는 바꾸지 않는다.
   단순 재빌드·재배포 때 보완일을 갱신하지 않으며, 미완성 작업을 오늘 작업으로 올리지 않는다.
8. 상태는 `planned` → `in_progress` → `ready_for_review`로 갱신한다.
   사용자 저장 확인이나 실제 공개 본문 대조 후에만 `published`로 바꾼다.
   `reports/content-refresh/<실행일>.md`에 변경·근거·검증·인계 상태를 기록한다.
   소스·산출물·계획 상태·기록만 검증 후 명시적으로 커밋해 자신의 미추적 보고서로
   다음 예약을 막지 않는다. 다른 사용자 변경은 포함·삭제·stash하지 않는다.

## 측정과 승인 경계

- 2026-10-12 관찰한 Google 웹 검색 28일 비교는 노출 2,029→2,701,
  클릭 82→68, CTR 4.0%→2.5%였다. 검색어 구성이 달라지므로 제목만 원인이라고 단정하지 않는다.
- 페이지별 클릭·노출·검색어·색인 상태를 같은 길이의 기간으로 비교한다.
  direct 트래픽 전체를 자체 방문·봇으로 단정하지 않는다.
- 글 개수·글자 수·출처 수·자동 8.5 점수는 검색 성장이나 AdSense 승인 지표가 아니다.
  클릭과 반응이 생기는 글의 범위, 독자 목적 달성에 필요한 공백을 함께 평가한다.
- 6주는 방향 조정의 자료를 모으는 기간이지 검색 성과를 보장하는 기한이 아니다.
- 색인 대기 12건은 원인을 개별 확인한다. 과거 삭제 URL의 404와 정상 중복 URL,
  아직 수집되지 않은 글을 같은 오류로 취급하거나 전부 되살리지 않는다.
- 삭제·비공개·일괄 카테고리 변경·광고 추가·AdSense 재신청은 별도 요청 없이 하지 않는다.
  GitHub main·Pages 전송과 브라우저 QA의 기존 권한·보안 정책은 그대로 유지한다.
