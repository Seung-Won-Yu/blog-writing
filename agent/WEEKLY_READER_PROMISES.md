# 요일별 독자 약속과 공통 제작 틀

이 문서는 2026-09-02 이후 월요일부터 토요일까지의 정규 글이 공유하는
편집 기준이다. 모든 글을 같은 문체로 만드는 것이 목적이 아니다. 블로그라는
한 제품의 디자인·검증 방식은 통일하고, 독자·검색 의도·난이도·이야기 전개는
요일별 편집자가 따로 책임진다.

## 공통 디자인

다음 요소는 전 요일이 같은 시각 언어와 HTML 구조를 사용한다.

- 제목 아래 짧은 도입, 기사 고유 대표 이미지, `30초 요약`, `먼저 알아둘 말`
- 1200×630 WebP 이미지와 설명형 대체 텍스트, 모바일 문단과 표 가로 스크롤
- 이미지의 공통 품질과 요일별 교육 역할은 `agent/WEEKLY_VISUAL_PROMISES.md`
  하나를 기준으로 삼는다.
- 본문 광고 1개, 참고 자료, 이어서 읽을 실제 공개 글, 마지막 행동 문장
- 과장 없는 제목, 공식·1차 근거, 원문에 없던 새 기여, 8.5 독자 품질 가드

공통 디자인을 이유로 모든 글에 같은 표·코드·소제목·분량을 강제하지 않는다.
글의 가치가 더 잘 전달된다면 표 없이 목록과 그림을 쓰고, 코드가 필요하지 않은
글에는 코드를 넣지 않는다.

| --- | --- | --- | --- | --- |
| 월요일 | 반복되는 개발 문제를 해결하려는 입문·실무 개발자 | `practitioner` | 원인과 해결 순서, 실패·되돌리기 기준을 다시 검색하지 않아도 적용한다 | 증상 → 먼저 할 일 → 원리 → 검증 → 실패 경계 → 재사용 체크리스트 |
| 화요일 | 일상 기술이 왜 그렇게 작동하는지 궁금한 비개발자 포함 일반 독자 | `general` | 한 문장 답과 바로 확인할 행동을 얻고, 원리는 비유와 그림으로 이해한다 | 장면 → 즉답 → 1분 확인 → 쉬운 예시 → 오해 경계 → 선택형 심화 |
| 수요일 | 최근 변화의 영향을 받는 개발자·서비스 사용자 | `practitioner` | 무엇이 누구에게 바뀌었고 지금 무엇을 확인할지 결정한다 | 이전 전제 → 바뀐 사실 → 영향 대상 → 지금 할 일 → 미확정 범위 → 장기 기준 |
| 목요일 | 기술 오해의 사실 여부나 지금 구조가 된 이유를 알고 싶은 일반 독자 | `general` | 판정을 먼저 얻고 직접 확인한 뒤, 오해가 생긴 이유와 예외를 이해한다 | 흔한 믿음 → 먼저 판정 → 직접 확인 → 왜 그렇게 됐나 → 예외 → 선택형 심화 |
| 금요일 | GitHub·공식 문서·Agent Skills·AI 개발 도구를 고르는 개발자와 IT 관심자 | `developer` | 도구가 어디에 쓰이고 무엇과 다르며 언제 쓰지 말아야 하는지 판단한다 | 구체적 선택 질문 → 사용처 지도 → 공식 근거 → 비교 → 적용 예 → 한계·선택 기준 |
| 토요일 | 주식 앱을 만드는 과정을 따라오는 일반 독자와 개발자 | `mixed` | 실제 갈등·실험·판단을 따라가며 자기 프로젝트에도 쓸 기준을 하나 얻는다 | 직전 질문 → 막힌 장면 → 가설 → 구현·실험 → 예상 밖 결과 → 판단 → 다음 질문 |

월요일과 수요일을 억지로 일반 생활 글처럼 쓰지 않고, 금요일의 개발자 근거를
없애 난이도를 낮추지도 않는다. 대신 필요한 배경을 앞에서 주고 어려운 세부는
독자가 목적을 달성한 뒤 읽도록 배치한다. 화요일과 목요일은 비개발자가 심화
부분을 건너뛰어도 제목의 답과 행동을 모두 얻어야 한다.

## 원고의 독자 경로

새 원고는 `editorial.reader_path`에 다음 값을 기록하고 실제 본문과 일치시킨다.

- `reader_level`: 요일 표의 `general`, `practitioner`, `developer`, `mixed` 중 정확한 값
- `entry_heading`: 본문에서 처음 보이는 소제목과 완전히 같은 문장
- `immediate_answer`: 제목 질문에 바로 답하는 30~220자의 쉬운 문장
- `action_steps`: 독자가 실행·확인·판단할 2~5개 단계. 본문 앞부분의 실제 목록과 연결
- `completion_check`: 글을 다 읽은 뒤 독자가 스스로 완료 여부를 확인할 문장
- `advanced_heading`: 화·목 글에서만 필수. 기술 용어가 늘어나는 심화 소제목과 완전히 같은 문장

화·목 글은 본문 앞 35% 안에 `action_steps`와 연결되는 목록을 둔다. 심화 소제목
전에는 핵심 검색어를 제외한 영문 약어·프로토콜·상태 코드 같은 새 기술 용어를
네 개보다 많이 꺼내지 않는다. 심화 내용은 글을 길게 보이게 하는 의무 구간이
아니며, 일반 독자가 앞부분만 읽어도 답·행동·실패 경계를 얻어야 한다.

월·수·금은 앞 절반 안에 독자의 확인·선택 단계를 보여 준다. 토요일은 이야기의
긴장을 해치지 않는 범위에서 회차 안에 행동·판단 목록을 두고 마지막에는 실제
결론과 다음 편 질문을 각각 한 번만 남긴다.

## 사람 우선 검색 기준

검색 유입을 위해 검색어만 바꾼 글을 대량 생성하지 않는다. 제목·도입·본문은
같은 질문에 답하고, 독자가 목표를 달성할 만큼 완전한 설명과 직접 만든 비교·
체크리스트·도식·실험·프로젝트 판단 중 하나를 제공한다. 출처가 많다는 이유로
원문 요약을 새 가치처럼 포장하지 않는다.

이 기준은 Google의 사람 우선 콘텐츠, 검색 기본 요건, 생성형 AI 콘텐츠,
스팸 정책을 블로그 자동화에 적용한 내부 SLO다.

- [사람 우선의 유용하고 신뢰할 수 있는 콘텐츠](https://developers.google.com/search/docs/fundamentals/creating-helpful-content)
- [Google 검색 기본 요건](https://developers.google.com/search/docs/essentials)
- [생성형 AI 콘텐츠 안내](https://developers.google.com/search/docs/fundamentals/using-gen-ai-content)
- [스팸 정책](https://developers.google.com/search/docs/essentials/spam-policies)

Google은 8.5나 본문 비율 같은 숫자를 요구하지 않으며 검색 노출도 보장하지
않는다. 이 숫자는 제목만 쉬운 글, 기술 문서처럼 쌓인 글, 근거 없이 변형한 글을
발행 전에 되돌리기 위한 이 블로그의 품질 기준이다.

## 마지막 독자 시뮬레이션

가드 점수와 별도로 다음 질문을 모두 `예`로 답해야 한다.

1. 이 요일의 주 독자가 제목과 첫 부분만 읽고 핵심 답을 자기 말로 설명할 수 있는가?
2. 독자가 다른 검색 결과로 돌아가지 않고 최소 한 가지 행동·선택·판단을 끝낼 수 있는가?
3. 어려운 용어는 먼저 쉬운 말로 설명됐고, 선택형 심화 구간 전까지 몰려 나오지 않는가?
4. 글을 다 읽은 결과가 `completion_check`와 실제 마지막 문장에 같은 의미로 남는가?
5. 같은 출처를 바꿔 말한 것이 아니라 이 블로그만의 비교·증거·그림·판단이 있는가?

하나라도 아니면 `NO_PUBLISH_QUALITY`로 사용자에게 넘기지 않는다. 같은 실행에서
해당 블록을 독자 질문 순서로 다시 쓰고 공통 독자 품질 루프를 재실행한다.
