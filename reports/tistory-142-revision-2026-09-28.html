주문 버튼을 눌렀는데 화면이 멈췄다. 다시 누르면 주문도 두 번 들어갈까? 서버가 주문을 저장한 직후 응답만 끊겼다면 충분히 가능한 일이다. 이때 필요한 것은 재시도를 없애는 기능이 아니라, ‘아까 그 주문’을 알아보는 약속이다. Idempotency-Key를 PostgreSQL 트랜잭션과 함께 쓰는 이유를 주문 한 건의 흐름으로 살펴보자.

개발 가이드

설계 설명 · PostgreSQL·Stripe 공식 문서 및 IETF 초안 참고 · SQL 실행·동시 요청 실험 결과가 아닌 구현 가이드

Idempotency-Key로 중복 주문을 막는 API 설계와 PostgreSQL 구현

먼저 결론부터: 같은 주문의 재시도는 같은 키를 보내고, 서버는 키 선점·주문 생성·응답 기록을 하나의 DB 트랜잭션으로 묶는다. 헤더 하나만 추가한다고 주문이 자동으로 한 번만 처리되는 것은 아니다.

읽기 전에: 앞부분은 재시도의 원리 설명이다. SQL 부분은 백엔드 개발자가 UNIQUE 제약과 트랜잭션을 안다는 전제로 썼다. 아래에는 테이블 정의와 드라이버용 SQL 조각이 있으며, 실행 가능한 주문 API 전체 코드는 없다. 주문 테이블·인증·HTTP 핸들러는 자신의 서비스에 맞게 구현해야 한다.

1. 주문은 성공했는데 앱은 실패라고 생각할 수 있다

서버가 주문 501번을 저장한 뒤 응답을 보내다가 연결이 끊겼다고 하자. 앱은 501번이 생겼다는 사실을 모른다. 똑같은 장바구니를 새 주문으로 보내면 502번까지 생긴다. 반대로 같은 키로 다시 보내고 서버가 501번의 결과를 돌려주면, 주문은 하나인 채 화면만 복구된다.

이처럼 같은 행동을 반복해도 추가 부작용을 만들지 않도록 하는 성질을 ‘멱등성’이라고 한다. POST는 HTTP에서 본래 멱등 메서드로 정의되지 않는다. 주문 생성 API가 재시도를 안전하게 받으려면 별도의 애플리케이션 계약이 필요하다. Idempotency-Key에 관한 IETF 문서는 초안이며, 확정된 RFC나 모든 서비스의 공통 구현이라고 보면 안 된다.

2. 같은 주문이면 같은 키, 정말 새 주문이면 새 키

클라이언트는 주문을 시작할 때 무작위 UUID처럼 충돌 가능성이 낮은 키를 하나 만든다. 응답을 받기 전 재전송·연타·앱 복구에는 그 키를 유지한다. ‘버튼을 다시 눌렀다’는 이유만으로 새 키를 만들면 중복 방지가 깨진다. 이전 주문의 성공 여부를 확인한 뒤 사용자가 별도 주문을 시작할 때 새 키를 만든다.

주문 501번의 응답이 사라졌을 때
상황키 사용기대 결과
첫 주문키 A 생성주문 501번 생성
타임아웃 후 재전송키 A 유지501번의 저장 응답
완료 확인 전 버튼 연타새 키를 만들지 않음추가 주문 방지
같은 키로 수량 변경요청 불일치거절, 새 주문 없음
성공 확인 후 별도 주문키 B 생성독립된 새 주문

서버는 키뿐 아니라 요청의 지문도 비교한다. 예를 들어 검증한 상품 ID·수량·통화 등 주문 의미를 결정하는 필드를, 서비스가 정한 순서와 형식으로 직렬화한 뒤 SHA-256을 계산한다. 단순히 JSON 원문을 해시하면 필드 순서만 달라도 다른 요청이 될 수 있다. 포함할 필드와 정규화 규칙을 버전별로 고정하고, 금액·권한은 클라이언트 값을 믿지 말고 서버에서 검증한다. 해시는 암호화가 아니므로 개인정보나 결제 수단 원문을 지문 입력·로그에 무분별하게 넣지 않는다.

3. ‘없으면 저장’ 대신 UNIQUE 제약으로 한 요청만 선점한다

두 요청이 동시에 SELECT로 ‘키 없음’을 확인하면 둘 다 주문을 만들 수 있다. 이 경쟁을 막는 경계가 DB의 유니크 제약이다. 이 글에서는 계정 + 작업 종류 + 키를 묶는다. 같은 키가 다른 계정이나 다른 API의 응답을 가져오면 안 되기 때문이다.

예시 테이블 정의: 신규 실습 DB를 위한 DDL이다. 운영 DB에 그대로 적용하는 마이그레이션이 아니다. 24시간은 보존 기간 예시일 뿐이며, 컬럼을 만들었다고 자동 삭제되지는 않는다.

CREATE TABLE idempotency_records (
  account_id bigint NOT NULL,
  operation text NOT NULL,
  key text NOT NULL,
  request_hash text NOT NULL,
  status text NOT NULL CHECK (status IN ('processing', 'completed')),
  response_status integer,
  response_body jsonb,
  expires_at timestamptz NOT NULL,
  PRIMARY KEY (account_id, operation, key),
  CHECK (status <> 'completed' OR
         (response_status IS NOT NULL AND response_body IS NOT NULL))
);

드라이버용 선점 SQL 조각: $1〜$4는 애플리케이션 드라이버가 바인딩할 값이다. psql에 그대로 붙여 넣는 완성 스크립트가 아니다. $1은 인증된 계정 ID, $2는 서버가 고정한 작업명(예: POST:/orders:v1), $3은 검증한 키, $4는 서버가 계산한 요청 해시다. 문자열 연결로 SQL을 만들지 않는다.

-- 전제: 같은 연결에서 BEGIN, 격리 수준 READ COMMITTED
INSERT INTO idempotency_records
  (account_id, operation, key, request_hash, status, expires_at)
VALUES ($1, $2, $3, $4, 'processing', now() + interval '24 hours')
ON CONFLICT (account_id, operation, key) DO NOTHING
RETURNING key;

-- RETURNING이 0행일 때, 위 INSERT가 끝난 뒤 별도 문장으로 조회
SELECT request_hash, status, response_status, response_body
FROM idempotency_records
WHERE account_id = $1 AND operation = $2 AND key = $3;

 

4. 동시 요청은 ‘처리 중 행 조회’보다 먼저 기다릴 수 있다

첫 요청이 키를 INSERT하고 아직 커밋하지 않았다면, 두 번째 요청의 INSERT는 유니크 충돌 판정 때문에 기다릴 수 있다. READ COMMITTED의 SELECT는 다른 트랜잭션의 미커밋 행을 읽지 않는다. 따라서 이 구조에서 ‘처리 중 행을 읽고 즉시 202를 반환한다’고 설명하면 실제 DB 동작과 맞지 않는다.

첫 요청이 완료 후 커밋하면 두 번째 INSERT는 0행을 반환하고, 다음 SELECT 문장에서 저장 결과를 읽는다. 첫 요청이 롤백하면 두 번째 요청이 선점에 성공할 수 있다. INSERT와 조회를 한 CTE 문장으로 합치지 않은 이유도 여기에 있다. READ COMMITTED에서는 다음 문장이 새 스냅샷으로 다른 요청의 커밋 결과를 볼 수 있다.

응용 코드가 구현할 분기: 아래는 의사 코드이며 특정 언어로 실행하는 코드가 아니다. 재고 검증·주문 쓰기·완료 응답 쓰기는 모두 같은 트랜잭션을 사용해야 한다.

인증·주문 권한·키·입력 검증 → 계정 범위와 요청 지문 확정
BEGIN (READ COMMITTED, 같은 DB 연결)
키 INSERT ... RETURNING 실행
  1행: 주문 생성 → 상태 completed와 응답 저장 → COMMIT → 응답
  0행: 별도 SELECT로 기존 결과 조회
       지문 다름 → 트랜잭션 종료 → 409 (이 서비스 예시의 계약)
       completed → 응답 접근 권한 확인 → 트랜잭션 종료 → 저장 응답
       행 없음 / 예상 밖 상태 → ROLLBACK → 제한된 재시도 또는 오류
DB 예외·잠금 타임아웃 → ROLLBACK → 같은 키로 재시도 안내
COMMIT 결과를 모르면 새 키를 만들지 말고 같은 키로 결과 확인

완료 응답을 저장하는 UPDATE도 해당 계정·작업·키·해시·processing 상태를 조건으로 하고, 변경한 행이 정확히 1개인지 확인한다. 저장 실패는 주문과 함께 롤백한다. 오류 난 트랜잭션을 그대로 두고 SELECT를 이어가면 안 된다. 잠금 대기·문장 타임아웃을 제한하고, 데드락이나 직렬화 실패는 정해진 횟수 안에서 전체 트랜잭션을 재시도한다.

위 그림과 이 서비스 예시의 본문 불일치 응답은 409로 정했다. 반면 IETF 초안은 본문 불일치에 422, 원 요청이 처리 중인 충돌에 409를 제안한다. 따라서 이 예시를 초안의 응답 규칙을 그대로 구현한 것으로 보면 안 된다. 자신의 API가 채택한 규칙을 문서에 적고 클라이언트와 테스트도 맞춰야 한다. DB 타임아웃을 전부 ‘처리 중 409’로 바꾸지는 않는다. 202와 상태 조회 URL을 쓰려면 작업을 먼저 영속화하고 워커·상태 조회·복구를 갖춘 별도의 비동기 계약이 필요하다.

5. 24시간이 지났다고 같은 주문을 다시 만들어도 될까?

expires_at 시간이 지났어도 행이 남아 있으면 유니크 제약은 그대로다. 이 예제는 남아 있는 완료 결과를 재사용하며, 만료 시각을 새 주문 허가로 쓰지 않는다. 정리 후 같은 키가 다시 들어오면 새 요청으로 처리될 수 있어 중복 방지 보장이 끝난다. 늦은 재시도가 가능한 주문 서비스는 별도의 주문 의도 ID 유니크 제약 등으로 업무상 중복도 방어해야 한다.

Stripe는 24시간 이상 지난 키를 제거할 수 있고, 제거 후 재사용한 키는 새 요청이 된다고 설명한다. 이는 Stripe의 정책이지 모든 주문 API의 권장 기간이 아니다. 클라이언트 복구 기간·장기 재전송·데이터 보존 요구에 맞춰 자신의 보장 범위를 문서화해야 한다.

  • 계정 ID는 요청 본문이 아닌 인증 결과에서 가져온다. 재생할 때도 해당 주문의 접근 권한을 확인한다.
  • 키의 형식·길이를 제한하고 개인정보를 키로 쓰지 않는다. 모든 SQL 값은 파라미터로 바인딩한다.
  • 저장 응답은 재생에 필요한 최소 정보만 보관한다. 토큰·카드 정보·민감한 원문을 넣지 않는다.
  • 실행 전 입력·권한 오류는 주문을 만들지 않는다. 최종 실패 응답을 저장할지는 API 계약으로 별도 결정한다.

6. DB 밖의 결제까지 ‘한 번만’을 보장하지는 않는다

DB가 롤백되어도 이미 승인된 외부 결제는 되돌아가지 않는다. 이 글의 트랜잭션은 같은 PostgreSQL 안의 기록을 함께 확정하는 범위다. 결제사에는 공급자의 멱등 키를 별도로 매핑하고, DB와 외부 전달 사이에는 아웃박스·재시도 워커·대사와 복구 절차를 설계해야 한다. 아웃박스도 전달이 반복될 수 있으므로 수신 측 중복 방지가 필요하다.

7. 구현했다면 주문 수와 응답을 함께 검증한다

다음은 테스트 계획과 기대 결과다. PostgreSQL 실행 및 동시성 실험 통과 기록이 아니다. 실제 API와 테스트 DB에서 두 연결을 사용해 확인해야 한다. 현재 글의 SQL은 공식 문서와 동작 전제를 대조한 조각이며, 주문 핸들러 전체의 정확성을 증명하지 않는다.

[ ] 같은 키·같은 주문 2회: 주문 1건, 같은 주문 ID와 응답
[ ] 첫 연결을 커밋 전 멈춤: 두 번째 INSERT의 대기 확인
[ ] 첫 연결 커밋: 두 번째 요청은 저장된 완료 결과 재생
[ ] 첫 연결 롤백: 두 번째 요청이 선점, 최종 주문 1건
[ ] 같은 키·다른 수량: 이 예시의 계약인 409, 새 주문 없음
[ ] 계정·작업 범위 변경: 다른 범위의 응답이 노출되지 않음
[ ] 응답 전송만 끊음: 같은 키 재시도로 기존 주문 확인
[ ] 만료 시각 경과·행 유지: 기존 결과 재생, 새 주문 없음
[ ] DB 타임아웃: 롤백 후 같은 키 복구, 새 키 생성 금지

8. 먼저 한 API의 보장 범위를 적는다

‘멱등 키를 받는다’보다 ‘누가 만든 어떤 키를, 어떤 요청 지문과 비교하고, 언제까지 어떤 결과로 돌려주는가’가 중요하다. 주문 생성 하나에서 이 계약을 정하고 테스트한 뒤 확장하자. 목표는 재시도를 금지하는 것이 아니라, 재시도해도 주문 501번으로 돌아오게 만드는 것이다.

  • SQLD 학습에서 관계와 키 이해하기주문과 요청 식별자를 구분하려면 먼저 테이블의 키가 무엇을 식별하는지 이해해야 한다.

같은 주문의 키를 유지하는 클라이언트, 한 요청만 선점하게 하는 DB 제약, 주문과 결과를 함께 확정하는 트랜잭션이 맞물려야 한다. 만료와 외부 결제는 별도의 경계다. 이 범위를 분명히 해야 헤더가 아니라 실제 동작으로 중복 주문을 막을 수 있다.

직접 확인해보려면자신의 주문 API가 타임아웃 뒤 같은 키를 유지하는지부터 확인하자. 서버는 두 DB 연결에서 커밋·롤백·대기를 재현해, 주문 수와 응답 ID를 함께 검증한다.
